# План: маршрутизация по сегментам (SSID → VLAN → выход)

**Статус:** план принят, ни один срез не начат. Документ — единственный источник
истины о прогрессе: следующий агент читает «Журнал статуса» и продолжает с
первого незакрытого среза.

**Основание:** ADR-0018 (два продукта, одно ядро), ADR-0019 (sing-box — единственный
маршрутизатор), ADR-0020 (DNS абонентов), ADR-0028 (авторизация захвата),
ADR-0029 (словарь выхода и субъекта), ADR-0031 (rule-set как назначение),
ADR-0009 (мульти-WAN отложен — здесь закрывается его часть).

**Границы:** ничего не коммитить, не пушить и не деплоить без отдельного
разрешения. Не трогать мастер `85.209.159.130` и production-ноды. Лабораторный
пир AWG на `rg3` создаётся отдельным именем и удаляется после прогона.

---

## 1. Задача и критерий успеха

Пять SSID в Omada привязаны к пяти VLAN. Трафик каждого сегмента идёт либо через
выбранный вышестоящий роутер («РФ-выход»), либо в AWG-туннель. У каждого сегмента
своя пара выходов; РФ-выходов несколько, все они лежат в одном плоском L2 с
разными адресами и разными шлюзами.

Критерий успеха: на одноразовой ВМ трафик сегмента A уходит через шлюз G1, сегмента
B — через G2, «всё остальное» — в AWG; при остановленном sing-box сегменты с
перехватом теряют выход, панель остаётся доступной; после reboot и rollback
поведение прежнее.

Гостевой Wi-Fi, SSID и VLAN-привязка — зона Omada; панель их не моделирует.

## 2. Принятые решения

| # | Решение | Почему |
|---|---------|--------|
| D1 | L3-владелец сегмента — панель. Omada — только контроллер AP; SSID→VLAN ставит AP | Иначе DHCP и шлюз оказываются на чужом хосте, и панель не видит трафик |
| D2 | SSID в панели не моделируется. `Interface.description` — свободная метка оператора, без синхронизации | Автозаполнение из Omada даёт дрейф при переименовании |
| D3 | Один транк-интерфейс, VLAN-подинтерфейсы на сегмент. Родитель — статический адрес | `interface.dhcp_on_trunk` запрещает DHCP на транк-родителе (`validators.py:193`) |
| D4 | Политика сегмента = пара выходов (РФ / туннель). Группировка — проекция по `rule.subject`, новых сущностей нет | Правила остаются плоским списком; субъекты сегментов не пересекаются |
| D5 | Захват включается на сегмент явно: `tproxy.enabled` + `ingress_interfaces` пишутся из правил с субъектом-интерфейсом | Без этого правила сохраняются, но ничего не делают (`agent/tproxy_apply.py::required`) |
| D6 | Порядок: группы сегментов в порядке `interfaces[]`, «Сам сервер» — последней. Нормализация при сохранении + валидатор смежности | Субъект `server` рендерится без source-матчера и ловит всё |
| D7 | «Всё остальное» сегмента — обычное последнее правило `0.0.0.0/0` с выходом, не `tproxy.final` | `final_outbound` принимает только тег прокси-выхода/группы |
| D8 | РФ-выход = `interface` + адрес-источник. Выбор шлюза — по `fwmark` (`routing_mark` sing-box → `ip rule fwmark`) | В одной L2 ядро выбирает маршрут по назначению; без правила источник не влияет |
| D9 | Маскарад — на выбранный адрес-источник, не на первичный адрес интерфейса | Вышестоящий роутер должен видеть ожидаемый клиентский адрес |
| D10 | Назначения: сначала IP-наборы (`ru-ips`), домены — опционально | Доменные правила слепы при клиентском DoH; IP-набор работает всегда |
| D11 | Форматы наборов на роутере — только `srs` и sing-box JSON | Материализация текстовых списков не реализована (`routing.ruleset_format`) |
| D12 | DNS сегмента — Unbound панели через DHCP; подсеть сегмента обязана быть в `dns.access_control` | Валидатор `tproxy.dns_access_control_missing`; редактора в UI нет — гэп |
| D13 | Захват IPv4-only; для сегментов с перехватом IPv6 блокируется | Полноценный IPv6-перехват вне объёма (CONTEXT.md) |
| D14 | Хост LAN-only: без ACME, nip.io и внешнего входящего доступа; локальный сертификат | `generators/caddy.py:92-101`; установщик пока требует публичное имя |
| D15 | Failover между выходами не делаем. Выход недоступен — сегмент падает в отказ | `bind_interface`/mark не работают → соединение не устанавливается; тихого обхода нет |
| D16 | Лаборатория — ESXi: портгруппа 4095 (VGT, Promiscuous/Forged/MAC changes Accept), плоский WAN с двумя шлюзами | Моделирует реальную сеть, включая путь «тег внутрь, без тега наружу» |

## 3. Целевая схема

```
AP (Omada): SSID Home/Guest/Work… → VLAN 10/20/30
        │  тегированные кадры, один провод
        ▼
[ panel host, ens_trunk, VID 4095 ]
   ens_trunk.10/.20/.30   ← зоны lan, Kea, Unbound access_control
   ens_trunk (native)     ← статический адрес, панель, SSH
   ens_wan                ← плоский L2: адреса A1..An, шлюзы G1..Gn
        │
        ├─ A1/G1 → «РФ-выход 1»      (exit: interface + source A1)
        ├─ A2/G2 → «РФ-выход 2»      (exit: interface + source A2)
        └─ awg-* → туннель            (exit: tunnel)
```

Выбор шлюза: `routing_mark` на выходе → `ip rule fwmark` → таблица с
`default via Gi src Ai`. systemd-networkd умеет это декларативно
(`[RoutingPolicyRule]` + `[Route] Table=`/`PreferredSource=`), без shell-скриптов.

### S0. Лаборатория

**Состояние: готово.** ВМ Debian 13 (`192.168.22.59`, ESXi), панель поднята в
режиме `separate-lan` с локальным CA, администратор создан, черновик v2 применён:
`ens192` — management `192.168.22.59/16`, `ens224` — WAN `192.168.170.10/16` +
`192.168.180.10/32` с дефолтами через `192.168.107.1` (metric 100) и
`192.168.116.254` (metric 200), `ens256` — транк `10.10.0.1/24` с VLAN
`1010/1020/1030` (`10.10.10-30.1/24`), Unbound отвечает на всех трёх, firewall
пропускает `lan → zone:wan`, SSH привязан к `ens192`.

Найдено и исправлено по ходу: **первый apply не мог создать собственные адреса**.
`FILES` в `agent/apply.py` ставил `unbound` раньше `networkd`, поэтому сервис
падал с `can't bind socket: Cannot assign requested address for 10.10.10.1`.
Порядок фаз теперь `nftables → networkd → wireguard → unbound → kea → caddy →
ddns → ssh`; проверено живьём: VLAN-устройства удалены, apply пересоздал их и
поднял Unbound (`docs`/тест `backend/tests/test_apply_phase_order.py`).

Отдельно зафиксировано: `management_console` в режиме `separate-lan` требует
локальной консоли (`management.local_root_console_required`) — на этой ВМ
провижининг выполнен обходом через pty с немедленным правилом SSH; это
лабораторный обход, а не штатный путь.

Клиент в VLAN делается сетевым namespace на самом роутере (`macvlan` на транке +
VLAN-подинтерфейс внутри ns), отдельная ВМ не нужна.

**Цель:** стенд, на котором проверяются все последующие срезы.

### S1. Сегменты и порядок (без смены поведения)

**Состояние: готово.** Вкладки «Сегменты» (по умолчанию) и «Порядок и применение»;
группировка правил по субъекту, состояние перехвата, предупреждение о правиле без
привязки к источнику; «Порядок» показывает плоский список с настоящими номерами,
группами, системными строками и проверками (субъект/выход/набор не объявлены,
правило без назначения, перехват выключен, серверное правило не последним).
«Добавить правило» из карточки открывает мастер на шаге «Что»; перестановка
по-прежнему в «Расширенных настройках».

**Цель:** оператор видит политику по сегментам, а не общий список.

1. `Routing.tsx`: вкладки «Сегменты», «Порядок и применение», «Устройства
   абонентов»; `RoutingMaster` разделяется на `RoutingSegments`,
   `RoutingSegmentEditor`, `RoutingOrder`.
2. `routing_rules` группируются по `rule.subject`; карточка сегмента показывает
   подсеть, зону, аренды, состояние перехвата и пару выходов, выведенную из правил.
3. Вкладка «Порядок» — read-only плоский список с заголовками групп и реальными
   номерами; предупреждения: перехват выключен, нет IPv4, набор не объявлен.
4. Никаких изменений схемы и поведения apply.

**Готово, когда:** `npm run typecheck`, `npm test`, `npm run build` зелёные;
существующая конфигурация отображается без потери правил; порядок в «Порядке»
совпадает с `configuration.routing_rules`.

**Риск:** только UI; миграции нет.

### S2. Захват по сегментам

**Состояние: частично.** Готово: тумблер «Перехватывать трафик сегмента» пишет
`tproxy.enabled` + `ingress_interfaces` (включение/выключение по сегменту),
порядок групп нормализуется на сохранении (`ordered_routing_rules`: сегменты по
`interfaces[]`, устройства, «Сам сервер» последним), карточка предупреждает, что
захват без DNS-политики TProxy не сгенерируется. Проверено живьём: порядок
`seg1020, seg1010, server` сохранился как `seg1010, seg1020, server`; apply v3
поднял весь контур (`tproxy_guards`, два Unbound, `singbox_process`,
`tproxy_interception`) со статусом `confirmed`.

Не закрыто: сквозной клиент в VLAN. Портгруппа `WIFI_DMZ` отдаёт нетегированный
трафик плоскости `192.168.0.0/16` (tcpdump на `ens256` видит только её ARP), а
тегированные кадры из `vlan 1010` до `vlan1010` не доходят — ARP до шлюза
`FAILED`. Нужна портгруппа с VLAN **4095** (VGT) и Promiscuous/Forged/MAC changes
= Accept, либо подтверждение, что теги снимает свитч.

Отдельно: включение захвата без `tproxy.dns.servers` проходит валидацию, но
падает на apply как `configuration.invalid → generator.failed (nftables)`;
в карточке сегмента теперь есть предупреждение, редактор политики — S4.

**Цель:** правила сегмента начинают действовать, и это видно.

1. Переключатель «Перехватывать трафик сегмента» пишет `tproxy.enabled` и
   добавляет/убирает интерфейс в `ingress_interfaces` (через существующий draft/apply).
2. Сохранение нормализует порядок: сегменты в порядке `interfaces[]`, затем
   остальные группы, `server` — последней; внутри группы — порядок оператора.
3. Валидатор: правила с одним субъектом-интерфейсом лежат смежно; при
   `tproxy.enabled` каждый сегмент с правилами обязан быть в `ingress_interfaces`.
4. UI предупреждает, если правила сохранены, а перехват выключен.

**Готово, когда:** на ВМ (S0) после apply сегмент попадает под захват, счётчики
nft растут, при выключенном тумблере правила не действуют и это видно в UI.

**Риск:** включение захвата меняет сетевой путь сегмента — только через
черновик + apply + подтверждение, safe mode по умолчанию.

### S3. Выход с адресом-источником и policy routing

**Цель:** «РФ-выход» выбирает не только интерфейс, но и адрес/шлюз.

1. Схема: `Exit{kind:"interface", interface, source}`; `source` — IPv4, обязан
   принадлежать адресам интерфейса; для `kind != interface` запрещён.
2. Валидатор: шлюз источника существует, адрес не дублируется между выходами,
   адрес в подсети интерфейса.
3. `generators/networkd.py`: `[RoutingPolicyRule] From=<source> Table=<N>` +
   `[Route] Table=<N> Gateway=<gw> PreferredSource=<source>`; номер таблицы — из
   реестра `generators/marks.py`, без коллизий.
4. `generators/singbox.py`: `direct` + `bind_interface` + `inet4_bind_address`
   (подтверждено для закреплённой 1.14.2, Dial Fields) и `routing_mark` из реестра.
5. `generators/nftables.py`: маскарад берёт выбранный адрес (ручное `snat` на
   источник либо `src` в таблице), а не первичный адрес интерфейса.
6. UI: выбор выхода — запись «интерфейс · адрес · шлюз»; в правилах выход
   отображается парой.

**Готово, когда:** на ВМ трафик сегмента A уходит через G1, сегмента B — через
G2 (проверка по `conntrack`/счётчикам на клиентской стороне), а трафик без
совпадения — в AWG; `sing-box check` и `nft -c` проходят на сгенерированных файлах.

**Риск:** policy routing меняет таблицу маршрутизации хоста — критерий «панель
остаётся доступной» проверяется в каждом сценарии.

### S4. Источники РФ-наборов и `access_control`

**Цель:** наборы и доступ к резолверу задаются из панели.

1. Объявленный источник `ru-ips` (`srs`/`json`) с URL и обновлением; при желании —
   встроенный источник в `BUILTIN_SOURCES` (сейчас пусто).
2. Редактор `dns.access_control` в `ServiceEditors.tsx` (сейчас read-only подпись).
3. Проверка: каждый сегмент с перехватом покрыт `access_control` и получает DNS
   по DHCP.

**Готово, когда:** apply на ВМ проходит без `tproxy.dns_access_control_missing`,
набор скачивается и правило `ru-ips → РФ-выход` срабатывает на реальном адресе.

**Риск:** внешние URL — SSRF-защита уже есть в `agent/downloader.py`; лицензии
наборов не подтверждены (см. `presets.py`).

### S5. Редактор сегмента, пресеты, проверки

**Цель:** довести UI до прототипа `mockups/routing-segments-prototype.html`.

1. Редактор сегмента: субъект подставлен, таблица «Что → Куда», ↑↓ внутри сегмента,
   «Всё остальное» — обязательное последнее правило.
2. Пресеты: «РФ напрямую, остальное в туннель», «только заблокированное в туннель»,
   «весь сегмент в туннель/напрямую»; используют выбранные выходы.
3. Проверки: выход не объявлен, шлюз не в подсети, туннель серверный, набор не
   объявлен, перехват выключен, нет IPv4, домены при чужом DoH.

**Готово, когда:** прототип воспроизведён на реальных компонентах (`Card`,
`DataTable`, `FlowChain`, `Badge`, `Toggle`, `WizardProgress`, `useDraftEditor`),
проверки блокируют сохранение невалидной политики.

### S6. LAN-only установка и приёмка

**Цель:** хост без публичного имени и внешнего доступа.

1. `install-release.sh`: режим `--lan-only` — без определения внешнего IPv4, без
   nip.io, без `:80`, адрес панели по LAN IP, локальный сертификат.
2. Документ установки: раздел «хост только в LAN», импорт сертификата на клиентах.
3. Приёмка по чек-листу: A→G1, B→G2, остальное→AWG; kill sing-box → сегменты
   блокированы, панель жива; reboot не подтверждает pending; rollback возвращает
   прежний контур; IPv6 на сегментах с перехватом заблокирован.

**Готово, когда:** чек-лист пройден на ВМ, результаты записаны в «Журнал статуса»
с уровнем доказательства.

## 6. Не входит

- Управление Wi-Fi, SSID и точками доступа (Omada).
- Failover и резервирование между РФ-выходами.
- Политика на отдельного DHCP-клиента (субъект — интерфейс или устройство абонента).
- Полноценный IPv6-перехват.
- Материализация текстовых списков доменов/CIDR на роутере.
- DHCP relay.
- Список клиентов с пометками в дашборде (отдельная модель, к сплиту не нужна).
