# DNS: потеря тестового stub при двух работающих Unbound

## Сценарий

Продолжение `docs/lab-21-tproxy-unbound-output-uid.md`. В разрешённой одноразовой Debian VM работали два настоящих Unbound под numeric UID `29092`/`29093` в изолированном router namespace, source-scoped INPUT/PREROUTING guards и заранее установленный UID OUTPUT guard. Выбранный resolver направлял unmatched DNS на отдельный fake UDP/TCP loopback stub `127.0.0.1:15353`; обычный — на внешний тестовый origin `198.18.0.3:53`, explicit forward обоих — на `198.18.0.2:53`. Это **не** sing-box и не продуктовый lifecycle. Исходная VM не меняла root-network, Unbound был временно установлен только в госте.

После здоровых UDP/TCP положительных контролей stub остановлен, а оба Unbound и все guard-таблицы оставлены работать. Проверялось:

| Контроль при отказе | Наблюдение |
| --- | --- |
| Ранее закэшированное unmatched имя выбранного источника | Ответ `203.0.113.8` продолжил выдаваться из кэша selected Unbound. **Не считать DNS полностью заблокированным при отказе.** Это не отправило новый запрос в WAN, но показывает, что один OUTPUT guard не отзывает уже готовый ответ. |
| Новое, заведомо не закэшированное имя selected по UDP и TCP | Клиент получил timeout в обоих случаях. Fake ordinary и explicit origin не зарегистрировали это имя во время отказа и после восстановления; обычный Unbound по **другому** новому имени продолжил получать `203.0.113.7` от обычного origin. Один timeout без этих положительных/отрицательных контролей не был бы доказательством отсутствия утечки. |
| Локальная запись и новый explicit forward выбранного источника | Оба работали при остановленном stub по UDP и TCP; forward подтверждён у разрешённого origin. |
| Повторный запуск stub без перезапуска Unbound | Новое selected имя по UDP, затем другое новое имя по TCP получили `203.0.113.8`; stub зарегистрировал запросы, origin их не видел. |

Финальный VM-прогон завершился `guest exit: 0` (первые проходы выявили необходимость точнее разделить имена ordinary-контроля и selected fault для проверки поздней доставки; затем добавлен TCP recovery). Для отказа использовались отдельные свежие QNAME, а не повторный кэшированный запрос. После опыта процессы, namespaces, nft-таблицы и временные Unbound-конфиги удалены; VM откатана к `pre-singbox-20261002` и выключена.

## Что это **не** доказывает

- Нет автоматического обнаружения потери sing-box, перевода DNS в host-owned режим блокировки, атомарного apply/boot/rollback и независимой классификации разрешённых локальных записей/forwards после смерти resolver. Кэш selected Unbound продолжил отвечать во время отказа; строгая трактовка ADR-0006 о блокировке всего не исключённого выбранного трафика требует отдельного решения для таких ответов.
- Тестировался fake stub, не DNS sing-box; не проверены реальный proxy outbound, UDP/TCP перехват, IPv6, фрагменты, DoH, privileged UID/nft bypass или endpoint на разрешённом explicit-forward IP. OUTPUT guard по UID/IP/порту не видит QNAME и не может отличить подменённый запрос к разрешённому upstream от настоящего explicit forward.
- Ограниченные окна packet/receiver-отсутствия и последующие положительные контроли доказывают только наблюдаемые запросы в этих namespaces, не формальную гарантию отсутствия будущей утечки.

Публичное `tproxy.not_available` оставлено; включать TProxy нельзя.

Позднее offline selected-конфиг ограничил обычное кэширование (`docs/lab-23-tproxy-dns-selected-cache-off.md`). Этот отчёт сохраняет исходное наблюдение со **старым** конфигом; текущий fixture/probe использует новые опции и больше не воспроизводит ответ из кэша без их удаления.
