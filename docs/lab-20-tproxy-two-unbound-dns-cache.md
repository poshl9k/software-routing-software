# Два процесса Unbound: источник до кэша в изолированной VM

## Объём

На разрешённой одноразовой Debian 13 VM `vsr-verify-20261002` пакет Unbound 1.26.1-0+deb13u1 временно установлен в госте. Четыре namespace: router (`lan0` 10.212.1.1, `lan1` 10.212.3.1, `wan0` 10.212.2.1), выбранный клиент, обычный клиент, origin `198.18.0.2`. Два **реальных отдельных** Unbound-процесса запускаются вручную внутри router namespace с конфигами, построенными `generate_tproxy_unbound_split` из test-only `model_copy(enabled=True)`; ordinary firewall и offline listener/direct-DNS guards также генерируются из того же snapshot. Каждый конфиг прошёл `unbound-checkconf`, каждый nft-файл — `nft -c` до применения **внутри namespace**. Root namespace VM и хост не менялись.

Вместо отсутствующего sing-box DNS использован отдельный **тестовый loopback DNS-stub** на `127.0.0.1:15353` (ответ A `203.0.113.8`). Синтетический внешний DNS origin на `198.18.0.2:53` отвечает A `203.0.113.7`. Это не TProxy, не proxy-route и не проверка sing-box. DNS-клиенты отправляли корректные запросы A по UDP и TCP; ответы проверялись по ID, QNAME и адресу. Тестовые upstream-процессы фиксировали QNAME/источник; прямые запросы и доступ к чужому listener проверялись таймаутом, счётчиком drop и отсутствием сообщения у upstream.

## Наблюдения

Каждая строка ниже прошла **по UDP и TCP**:

| Сценарий | Наблюдение |
| --- | --- |
| Локальная запись `router.test.` у обоих клиентов | Оба получили `192.0.2.77`, ни stub, ни origin не получили запрос. |
| Одинаковое неподходящее имя `shared-<transport>.vsrprobe.org.` | Выбранный получил `203.0.113.8` через loopback stub; обычный получил `203.0.113.7` через WAN origin. Повтор того же имени сохранил разницу ответов, не вызвав повторного запроса upstream: кэши процессов независимы в этой пробе. |
| Явный forward `forward.vsrprobe.org.` | Оба клиента получили ответ тестового origin; stub не получил запрос. Это разрешённое исключение, а не утечка. |
| Запрос к DNS-IP *другого* listener | Таймаут и рост нужного INPUT-drop counter; upstream не получил QNAME. |
| Выбранный напрямую к внешнему `198.18.0.2:53` | Таймаут и рост PREROUTING-drop counter; upstream не получил QNAME. |

Первый VM-прогон использовал `shared-udp.test.` и получил `NXDOMAIN`: `.test` обрабатывается специальной локальной зоной Unbound, поэтому это не доказательство поломки split. После перехода на синтетическое имя `*.vsrprobe.org.` полный повторный прогон завершился `guest exit: 0`; финальный прогон с отрицательными UDP/TCP контролями тоже завершился `guest exit: 0` (23 именованных шага). Процессы, namespaces, nft-таблицы и временные конфиги очищены; VM возвращена к `pre-singbox-20261002`, выключена.

## Граница вывода

Два отдельных Unbound действительно обслужили разные DNS-пути и кэши на разных IPv4 listener в этой VM. Не проверены: клиентские устройства *на одном интерфейсе*, IPv6/фрагменты, сбой или смерть stub/Unbound, автоматическое переключение/rollback, UID-разделение двух Unbound и безопасное правило OUTPUT для selected процесса, DNS при реальном sing-box, конфликт маршрутов/DNAT и доступ к loopback stub извне (для него отдельный nft-rule прошёл лишь syntax check ранее). Результат не доказывает, что выбранный DNS не уйдёт в WAN при отказе; explicit forwards преднамеренно идут к origin. Все изменения — test-only, live apply не изменён, `tproxy.not_available` не открывать.

Следующий отдельный опыт ввёл разные UID и OUTPUT guard (`docs/lab-21-tproxy-unbound-output-uid.md`). Текущий fixture/probe дополнен этими проверками и отдельным IP для ordinary upstream; исходное наблюдение данного отчёта относится к предыдущему прогону до такого расширения.

Ещё позже в offline selected-конфиге отключено обычное кэширование (`docs/lab-23-tproxy-dns-selected-cache-off.md`): текущий probe ожидает повторный запрос к stub, а не cache hit выбранного процесса. Этот отчёт фиксирует раннюю, кэширующую конфигурацию.
