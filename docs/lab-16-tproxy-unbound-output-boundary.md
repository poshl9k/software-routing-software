# DNS: FORWARD guard не ограничивает OUTPUT общего Unbound

## Объём и подготовка

Одноразовая Debian 13 VM `vsr-verify-20261002`, снимок `pre-singbox-20261002`. В исходном снимке Unbound отсутствует; для этой пробы внутри гостя установлен пакет Debian `unbound` 1.26.1-0+deb13u1. Пакет не устанавливался на хост или рабочий роутер. Три временных namespace: router (`lan0` 10.212.1.1, `wan0` 10.212.2.1), client (10.212.1.2), origin (198.18.0.2). Сервис DNS origin — ограниченный тестовый UDP/TCP-сервер, а не внешний публичный resolver.

`backend/tests/lab/generate_tproxy_dns_cases.py` создаёт обычный действующий Unbound/firewall-конфиг при **выключенном TProxy**: локальная запись, явный `forward-zone` для `forward.test.` и отказ для неизвестного имени. `backend/tests/lab/tproxy_dns_baseline_probe.py` добавляет **только в namespace** лабораторный `FORWARD`-guard для `lan0` и узкий следующий allow UDP/53 к origin (положительный контроль). Продуктовый `generate_tproxy_containment` не подключается; никакого sing-box, TProxy, mark и policy route в пробе нет. Сначала конфиги проходят `unbound-checkconf` и `nft -c` в namespace. Исполнять probe только на разрешённой disposable VM от root.

## Наблюдения

| Проверка | Результат |
| --- | --- |
| До guard: клиентские UDP/TCP запросы локальной записи и явного forward, отказ для неизвестного имени, прямой DNS через обычный firewall | Восемь этапов `PASS`: локальный ответ, upstream wire и origin receiver для forward, отсутствие выхода для локальной/неизвестной записи, direct timeout и счётчик обычного FORWARD drop. |
| После установки `FORWARD iifname lan0 counter drop`: новое имя `guard.forward.test.` через локальный listener Unbound по UDP | Клиент получил A `203.0.113.7`; ingress увидел запрос с `10.212.1.2`; WAN-захват и DNS origin получили upstream-запрос от `10.212.2.1` с совпадающим upstream ID. Счётчик выбранного FORWARD guard **не вырос**. |
| Прямой UDP DNS на тот же origin при узком allow после guard | Клиентский запрос виден на ingress; ответ timeout; счётчик guard вырос; ни WAN-захват, ни origin receiver запроса не получили. |

После исправления ошибочного сравнения счётчика в первой версии probe повторный VM-прогон завершился `guest exit: 0`, все десять этапов `PASS`. Ошибку probe нельзя считать сетевой неудачей: первые восемь этапов и получение ответа через Unbound уже прошли, но первая версия сравнивала счётчик обычного drop вместо guard. После окончательного прогона namespaces и nft-таблиц нет, временного Unbound-конфига нет.

## Граница вывода

Это **пакетное подтверждение** того, что source-scoped FORWARD-drop не покрывает выход общего локального resolver: транзитный запрос остаётся в FORWARD и блокируется, но клиентский запрос к Unbound попадает в INPUT, затем Unbound создаёт собственный OUTPUT к WAN. Это не доказательство утечки при *включённом* TProxy, краше sing-box или в продакшен-схеме с иными правилами; ни разделение кэша между выбранными/невыбранными источниками, ни TCP под guard здесь не проверялись. Явный forward согласно согласованной семантике может быть разрешён, поэтому наблюдаемый upstream сам по себе не является нарушением политики; он доказывает недостаточность **одного FORWARD guard** для её обеспечения. Требуются развилка до общего кэша и независимая авторизация Unbound OUTPUT с сохранением разрешённых explicit forwards и DNS невыбранных клиентов. `tproxy.not_available` остаётся.
