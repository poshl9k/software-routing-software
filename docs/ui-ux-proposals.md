## Executive summary

Каркас уже крепок: сессия проверяется до рендера (`App.tsx:256-269`), формы и
таблицы идут через общие примитивы, firewall сортирует по `order`, TProxy
честно помечен недоступным, SSH подтверждает WAN-риск. Основные потери —
**на уровне модели интерфейса, а не стиля**. Семь сквозных проблем:

1. **Навигация плоская и местами вводит в заблуждение.** 13 ссылок подряд
   (`App.tsx:125-139`); «Маршруты» и «Маршрутизация» звучат синонимами, а
   «Маршруты» ведёт к пустой таблице без модели API (`Network.tsx:453-461`);
   «Прокси» открывает Caddy-сайты, а не правила выхода
   (`App.tsx:131-134`). Keenetic группирует меню по задачам — это главный
   структурный ход.
2. **Не видно, что применено, что в черновике, что реально работает.** Верхний
   badge (`App.tsx:200`) показывает версию, но не факт работы на машине; а часть
   экранов рисует `—` там, где нет данных (туннели, сайты, DHCP-аренды),
   смешивая «пусто» с «недоступно». Нужен постоянный статус-элемент и честные
   состояния `unknown/loading/error/applied/draft`.
3. **Обзор обещает live-телеметрию, но показывает конфигурацию.**
   `Dashboard.tsx:27-146` выдаёт «скорость неизвестна / статус недоступен» плюс
   таблицы черновика. Keenetic-решение — статусный hero «Интернет», а не дашборд.
4. **Применение (самый критичный сценарий) раздвоено и непоследовательно.**
   Верхняя кнопка `command("apply")` (`App.tsx:100-122`) не показывает diff;
   на самой странице выбор показывает один черновик в diff, а `apply`
   вызывается **без выбранного id** — просмотр и применение могут разойтись
   (`ApplyScreen.tsx:49-60,228`); рядом шесть конкурирующих действий
   (`ApplyScreen.tsx:210-262`).
5. **Форма вместо объекта.** Сеть редактируется как общая таблица из 9
   колонок (`Network.tsx:175-342`), туннели — стопка форм (`ConnectionEditors.tsx:576-859`),
   firewall — 10 колонок (`Firewall.tsx:194-307`). Keenetic-паттерн: список
   объектов → один объект с короткими вкладками.
6. **Жаргон в лицо пользователю.** `pass/block/reject`, `fail-closed`,
   `host override`, `forward-zone`, `Upstreams`, `direct/block/route`,
   `valid_lifetime`, `tls_insecure`, `physical/static`. Тех-термины на латинице
   сохраняем, но подписи и основную поверхность нужно перевести на человеческий.
7. **Деструктив без подтверждения и обход единого сохранения.** Удаление
   интерфейса — без диалога и списка зависимостей (`Network.tsx:102-103,338-341`);
   импорт алиасов немедленно пишет черновик в обход `EditorFooter`
   (`Firewall.tsx:63-66,606-608`).

Во всех предложениях инварианты безопасности **не ослабляются**: first-match и
default-deny, fail-closed интерфейсы, единый атомарный apply/rollback, окно
подтверждения, запрет нового цикла до завершения предыдущего, скрытие секретов,
TProxy остаётся недоступным до отдельной приёмки.

## Приоритетный план

### P0 — быстрые победы (объём S, без смены модели)

- Переименовать верхний «Применить» в «Проверить изменения» → ведёт на `/apply` (`App.tsx:100-122`).
- Передавать показанный id в `command("apply", shownDraft.id)` либо убрать нерабочий выбор черновика (`ApplyScreen.tsx:49-60,228`).
- Привести `/events` к полноценной странице: `PageHeader`, честный `EmptyState` «Журнал пока недоступен», без пустой таблицы (`Dashboard.tsx:10-20`).
- Firewall: `pass/block/reject` → «Разрешить/Запретить/Отклонить с ответом»; «Правила проверяются сверху вниз; первое совпадение решает» вынести над списком (`Firewall.tsx:258-263,335-342`).
- Убрать фиктивные колонки `—`: DHCP «Аренд»/«Конфликт», туннели «Статус»/«QR», сайты «Статус», DDNS «Статус» — заменить на «Статус недоступен» (`Services.tsx:46-86`; `ConnectionEditors.tsx:570-575,901-907`).
- Пустые таблицы маршрутов/диагностики → честный `EmptyState` + одна осмысленная ссылка (`Network.tsx:453-470`).
- Подтверждение удаления интерфейса/туннеля/пира с показом зависимостей (`Network.tsx:338-341`, `ConnectionEditors.tsx`).
- Ошибки keygen — в `editor.setError`/`ErrorNotice`, а не в скрытый при QR `qrError` (`ConnectionEditors.tsx:665-677`).
- Единицы и подписи: «Keepalive, с», «/24 = 255.255.255.0», «Протокол/Адрес/Порт DNS-сервера», `TTL`/срок аренды в секундах, русские режимы NAT и сертификата.
- Пояснения к риску рядом с полем: `tls_insecure` «снижает защиту от подмены сервера»; SSH-WAN — постоянная заметка о пароле ОС и защите от перебора.
- Вынести тона `Badge` и shadow онбординга в `theme.ts` (`Badge.tsx:7-12`; `styles.css:284`).
- Обзорную кнопку «Настроить» → «Проверить черновик»; в `noConfiguration`-notice добавить ссылку на первый запуск (`Dashboard.tsx:62-64`; `App.tsx:246-251`).

### P1 — структурные изменения (объём M)

- **Новая IA:** сгруппированное меню (Обзор / Интернет / Домашняя сеть / Безопасность / Сервисы / Управление) + закреплённый блок «Конфигурация → Проверка и применение»; убрать «Маршруты» из меню до появления модели; переименовать «Прокси» → «Входящие сайты» (часть A).
- **`ApplyStatusRail`** — постоянный статус на каждой защищённой странице: черновик/подтверждённая/pending-таймер/выполняется/ошибка, с честными «время подтверждения недоступно» (часть A).
- **Статусный hero «Интернет»** на обзоре + 3–4 спокойные карточки, без выдачи конфигурации за live-состояние (часть A).
- **Объект + вкладки** для интерфейсов и туннелей: «Общие / IP / Подключение / Дополнительно», карточка доступа с «сейчас / после применения» (части A/B).
- **Компоновщик правил firewall** «Откуда → Куда → Протокол/порт → Разрешить/Запретить/Отклонить → Позиция»; Port Forward/NAT/алиасы — только в своих вкладках; импорт алиасов — внутри общего редактирования (часть D).
- **Мастер быстрого подключения** DHCP/static/VLAN/мост с дефолтами и обзором до сохранения; сценарный выбор WG-клиент/сервер/импорт `.conf` (часть B).
- **Onboarding-wizard** с осмысленными ступенями и восстановлением после перехода admin→draft; повтор предупреждения о первом применении без автоотката на финале (часть A).
- **Вкладки обслуживания** «Резервные копии / Диагностика / Выпуск установки», переименовать «Применить обновление» → «Установить выпуск» (часть A).
- **DHCP как «Устройства с постоянным IP»** (устройство→IP), DNS на «Локальные имена» и «Домены с отдельным DNS», TProxy-политика как связная цепочка «источник → набор → действие → выход» (части C/D).
- **Новые примитивы:** `StatusHero`, `StatTile`, `InlineStatus`, `ApplyStatusRail`, `WizardProgress`, `DiffReview`, `ApplyStage`/`CountdownStatus`, `SafetyReview` (MUI Dialog), `ServiceStatusHeader`, `ExpertDisclosure`, `PageSection`, `LoadingSkeleton`, `StickyActionBar` — с обновлением `docs/ui-rules.md`, `docs/ui-refactor.md`, ADR-0011.
- **Адаптивность и движение:** мобильный drawer вместо многострочной ленты (`styles.css:461-492`), `prefers-reduced-motion`, aria-live только на смену фазы.

### P2 — крупные ставки (объём L, требуют backend/контракта)

- **Контракт diff** с серверной редакцией секретов + резюме по разделам и последствиям для панели/WAN/LAN (часть A).
- **Модель статических маршрутов** (schema/API/generator/валидация) и честный CRUD-редактор (части A/D).
- **Runtime-телеметрия** сервисов, интерфейсов, туннелей и DDNS (состояние, handshake, последняя ошибка) через разрешённые RPC агента; `ServiceStatusHeader` поверх реального статуса (части C/D).
- **Полный UX TProxy** после приёмки fail-closed/DNS/IPv6: статус «применено ≠ работает», проверка ссылок выход/список до удаления, версии/откат rule-set (часть D).
- **DHCP-объект** резервации и `valid_lifetime`; PPPoE — только после схемы секретов и проверок (части B/C).
- **Устойчивое выделение адресов туннелей** вместо зависимости от алфавитного порядка имён (`ConnectionEditors.tsx:91-106`).

## 0. Метод и источники

Прочитаны полностью, в порядке brief: `docs/ui-rules.md`, `CONTEXT.md`, `frontend/src/theme.ts`, `frontend/src/styles.css`, все 15 `frontend/src/components/*.tsx`, назначенные `pages/Dashboard.tsx`, `ApplyScreen.tsx`, `Onboarding.tsx`, `Maintenance.tsx`, `App.tsx`. Дополнительно проверены `state.tsx:206-359`, `hooks/useApplyStatus.ts:5-72`, `preferences.ts:1-28`, вкладки `pages/Network.tsx:41-46,140-151,453-456`. Это проектное предложение, не тест/изменение кода; runtime-телеметрия, контракты будущего журнала и визуальная проверка на устройствах не исследованы. Все характеристики *текущего* UI ниже привязаны к коду; отсутствующие данные не выдаются за рабочие.

## 1. Общая оценка раздела

Оболочка уже защищена сессией до рендера (`App.tsx:256-269`), формы и таблицы имеют общие примитивы (`docs/ui-rules.md:23-39`), но навигация плоская, статус черновика смешан с состоянием агента, а два пути «Применить» обходят чтение diff (`App.tsx:100-122`; `ApplyScreen.tsx:199-230`). Для роутера важнее читаемая последовательность «сохранил черновик → сверил последствия → применил целиком → при необходимости подтвердил», чем максимум информации на одном экране. Берём дружелюбную структуру и статусный hero Keenetic; у pfSense — различимость состояний и контроль ошибки; у LuCI — единый маршрут к конфигурации, но не дублирующее «сохранить/применить» в каждом редакторе. Визуально сохраняем существующий тёмный токенизированный каркас (`theme.ts:8-42,49-76`), уменьшаем плотность первого экрана, не меняем модель безопасности ради «красивого» статуса.

## 2. Постраничный разбор

### Оболочка, IA и Protected — `frontend/src/App.tsx`

- Текущее состояние: 13 ссылок подряд, «Маршруты» = `/network?tab=routes`, «Маршрутизация» = `/routing`; активная ссылка определяется ручным разбором `pathname/search` (`App.tsx:125-139,157-159,168-192`). Верхняя строка содержит breadcrumb, badge версии, поиск, ApplyTopButton, имя, выход и refresh (`App.tsx:195-236`). `Protected` ожидает проверку сессии и не монтирует Layout без пользователя (`App.tsx:256-269`); `/login` и `/onboarding` расположены вне защищённого дерева (`App.tsx:276-291`).
- Проблемы UX:
  1. Соседние «Маршруты» и «Маршрутизация» звучат как один объект, но означают статические маршруты и TProxy-политику; первая вкладка сейчас прямо помечена неподключённой к модели API (`App.tsx:130-131`; `Network.tsx:453-456`). Поиск скрывает несоответствие, не устраняет его (`App.tsx:168-192`).
  2. Badge `vN · черновик/подтверждена` сообщает версию, но не говорит, действует ли она на машине; когда draft поверх confirmed, пользователю нужен статус обоих (`App.tsx:200-208`; `state.tsx:206-214,275-287`). При `noConfiguration` кнопка Apply вообще скрыта, а текст отправляет в «Первый запуск» без ссылки (`App.tsx:63,246-251`).
  3. Верхний «Применить» исполняет `command("apply")` без показа diff, тогда как подробности доступны отдельно; при первом применении критическая оговорка существует только в Tooltip (`App.tsx:100-122`; `ApplyScreen.tsx:67-73,199-209`). Не ставить safety-critical решение за hover.
- Предложения:
  1. Что: единое дерево навигации с обычными русскими именами, максимум два уровня: «Обзор» `/`; «Интернет» → «Подключения и адреса» `/network`, «Статические маршруты» `/network?tab=routes` (пока неподключён API — оставить вкладкой внутри сети и не выводить самостоятельной ссылкой до появления модели), «Туннели» `/tunnels`, «Выборочная маршрутизация» `/routing`; «Домашняя сеть» → «DHCP» `/dhcp`, «DNS» `/dns`; «Безопасность» → «Правила firewall» `/firewall`, «Доступ по SSH» `/ssh`; «Сервисы» → «Сайты и прокси» `/proxy`; «Управление» → «Журнал событий» `/events`, «Обслуживание» `/maintenance`. Отдельный закреплённый нижний блок «Конфигурация» → «Проверка и применение» `/apply`, рядом краткое состояние черновика; это *не* ещё один редактор сети. Зачем: группировка Keenetic по задачам, точность терминов pfSense там, где домашнее название опасно. Как: заменить `navigation[]` на типизированные группы с `route + optional tab`; breadcrumb = путь группы и листа, route-aware active по `URLSearchParams.get('tab')`, без `search.includes('routes')`; текстовый поиск фильтрует листья, сохраняет заголовки непустых групп. Существующие маршруты сохранить для deep links; при реализации статических маршрутов можно ввести `/network/routes` с redirect из старого URL, но не сейчас. Объём M; риск: обновить тесты навигации и `docs/ui-refactor.md`; новые маршруты не должны обходить `Protected` (`docs/ui-rules.md:123-127`).
  2. Что: `ApplyStatusRail` — один постоянный статусный элемент на каждой защищённой странице, текст + метка + действие: «Черновик vN не применён · стабильная vM» → «Проверить изменения»; «Ожидается подтверждение · MM:SS» → `/apply` и доступное подтверждение; «Выполняется / состояние агента неизвестно» → проверить состояние; «Подтверждена vM · время подтверждения неизвестно/из API»; «Откат/ошибка» → `/apply`. Никогда не называть `created_at` временем применения или подтверждения. Зачем: Keenetic — статус виден всегда, pfSense — состояния несмешиваемы. Как: данные `versions` + `useApplyCommands`; статус агента только через существующий императивный `useApplyStatus` (его RPC может вызвать откат: `hooks/useApplyStatus.ts:5-14`), единственный владелец чтения на маршруте, никакого Query-поллинга. Не подменять unknown зелёным; при ожидаемом подтверждении предпочесть дедлайн агента и пометить приблизительный локальный расчёт. ## 1. Общая оценка раздела

Модель интерфейса уже хранит тип, зону, адресацию, список адресов, VLAN/мост и описание в одном объекте (`types.ts:5-17`), но на экране это девять колонок редактирования всей сети сразу (`Network.tsx:175-342`), а не Keenetic-подобное подключение с короткими вкладками и видимым состоянием. Концепция черновика и фактически полученный DHCP-адрес существуют (`Network.tsx:72-78,168-174,368-374`), но связь между портом управления, IP панели и последствиями сохранения не показана рядом с действием. Туннель — отдельный объект, редактор с автогенерацией ключей и импортом `.conf` (`ConnectionEditors.tsx:467-560`), однако открывается как длинная стопка карточек, а колонка «Статус» заполнена «—» (`ConnectionEditors.tsx:377-395,570-859`). Хороший ориентир — Keenetic: список читаемых объектов → один объект с вкладками → обзор «применено / в черновике / в ОС»; полезное у OpenWrt — явные экспертные поля в отдельной области, но не его плотная форма; у pfSense — различение runtime и конфигурационного статуса, без его сеточной плотности. Сохранение карточки меняет общий черновик, не сеть на хосте: только общий цикл применения и, при смене панели, безопасное подтверждение/откат (`CONTEXT.md:33-48`).

## 4. Спорные вопросы к заказчику

1. Какой источник истины возвращает назначенный с консоли первичный LAN, его MAC и фактический адрес/порт панели после применения? Сейчас `Interface` не хранит эту роль (`types.ts:5-17`), но для безопасного before/after нужна не эвристика «первый lan».

4. Какую телеметрию действительно отдаёт агент для интерфейсов, WG/AWG и DDNS (линк, адрес, handshake, последняя ошибка)? До появления API показывать «нет данных», не «Подключено» (`ConnectionEditors.tsx:570-575,1095-1099`).

Проверка визуального рендера, backend-статусов и G2-редактора не проводилась; это предложение, не реализация. Ссылки ниже — на текущее состояние. Семантика: конфигурация — черновик, сохраняется целиком и только затем применяется; аренда — runtime, резервация — конфигурация (`CONTEXT.md:32-47,60-65`).

## 1. Общая оценка раздела

Отдельные пункты DHCP/DNS/Туннели/Прокси уже есть, но вкладки и глобальный режим «Редактировать» скрывают добавление объектов (`frontend/src/App.tsx:125-139,280-286`; `frontend/src/pages/Services.tsx:19-24,96-119,180-207`; `frontend/src/pages/ServiceEditors.tsx:176-192,413-429`). Читаемые таблицы полезны при 500 арендах, но резервации и DNS-записи требуют контекстных действий возле списка. Текущие `—` и статусы конфигурации могут выглядеть как live-мониторинг, которого здесь нет (`frontend/src/pages/Services.tsx:57-84`; `frontend/src/pages/ConnectionEditors.tsx:570-575,901-907`). Базовый паттерн: статус сервиса сверху; ниже настройки и списки с одним входом «Добавить»; редактирование конкретной строки/объекта, затем единый `EditorFooter` и напоминание «Сохранено в черновик; примените конфигурацию». Заимствуем ясность списка Keenetic, статусную определённость pfSense и структурность страниц LuCI — без перегруженных таблиц и сырых полей.

## 2. Постраничный разбор

### DHCP — `Services.tsx` / `ServiceEditors.tsx`

- Текущее состояние: `/dhcp` обёрнут в `DHCPEditor`; обзорные вкладки «Подсети / Резервации / Аренды» (`frontend/src/pages/Services.tsx:19-45`). Подсеть — таблица с пулом, шлюзом/DNS и фиктивной колонкой «Аренд» = `—`; резервации дублируются на первых двух вкладках, «Конфликт» всегда `—` (`frontend/src/pages/Services.tsx:46-86`). Аренды запрашиваются только при открытии третьей вкладки, доступны ручное обновление и поиск MAC/IP/hostname; 502/503 обозначаются как недоступность Kea ctrl-agent (`frontend/src/pages/Services.tsx:26-37,88-92`). Редактор — карточки подсетей с ID, интерфейсом, CIDR, многострочными шлюзами/DNS, таблицами пулов и резерваций; кнопки добавления доступны лишь после «Редактировать» (`frontend/src/pages/ServiceEditors.tsx:186-250,253-373`). `valid_lifetime: 3600` задаётся при создании, но не редактируется и не показан (`frontend/src/pages/ServiceEditors.tsx:355-369`).
- Проблемы UX:
  1. Резервацию видно в двух вкладках, но её добавление спрятано внутри карточки подсети в режиме редактирования; MAC указан как «Идентификатор» в обзоре и `Hostname` в редакторе (`frontend/src/pages/Services.tsx:68-86`; `frontend/src/pages/ServiceEditors.tsx:296-349`). Устройство → IP не является первичной единицей работы.
  2. Пустые `—` в «Аренд» и «Конфликт» создают впечатление проверенных значений; число резерваций — реальное, а два других поля нет (`frontend/src/pages/Services.tsx:49-64,71-84`). Недоступный ctrl-agent сейчас отмечен Badge, но таблица одновременно сообщает «Аренды не загружены», хотя это ошибка, а не пустая аренда (`frontend/src/pages/Services.tsx:88-92`).
  3. Нет представленного включения DHCP; у подсети есть диапазоны и lifetime в модели редактора, но срок аренды скрыт; CIDR, внутренний ID и списки «построчно» стоят раньше понятного действия «выдать адрес устройству» (`frontend/src/pages/ServiceEditors.tsx:194-250,253-295,355-369`). Не обещать переключатель до проверки модели/schema/API.
- Предложения:
  1. Что: сделать первой вкладкой «Устройства с постоянным IP»: компактная читаемая таблица `Устройство | MAC | Постоянный IP | Подсеть | Действия`, заголовочное `Card action=«Добавить устройство»`; форма одной резервации — имя (текущий `hostname`, не свободное display-name), MAC, IP, подсеть; открывать из строки. Зачем: Keenetic — устройство→IP как объект вместо обхода подсетей. Как: `Card`, `DataTable` в просмотре, `Field`/`Select` + `FormGrid` + `EditorShell`/`EditorFooter` в редакторе; не вводить новое поле «заметка» без синхронизации schema/types/API. Объём M. Риск: смена точки входа, проверка переноса новой резервации в `dhcp_subnets[].reservations` и уникальности MAC/IP; `docs/ui-rules.md:67-78` — не превращать читаемую таблицу в произвольный inline-edit.
  2. Что: «Подсети и диапазоны» — отдельный блок настроек с дружелюбными подписями «Диапазон адресов», «Адрес роутера», «DNS для клиентов», «Срок аренды»; ID показывать как служебный (автоматическая генерация уже есть), поддерживать несколько пулов и резервации вне пула. Зачем: LuCI — связная страница сервиса; Keenetic — основное прежде продвинутого. Как: текущие `FormGrid`, `Field`, `InterfaceSelect`, `DataTable` для пулов; `valid_lifetime` привязать к полю только после проверки единиц и backend-валидации. Объём M. Риск: не фильтровать интерфейсы до LAN на одном лишь UI — ограничения адресации описаны в `CONTEXT.md:69-70`.
  3. Что: живые аренды — отдельная поисковая таблица с различимыми состояниями «загрузка / нет аренд / ctrl-agent недоступен / данные получены», счётчик только по успешному ответу; убрать фиктивные «Аренд» и «Конфликт», пока нет данных проверки. Зачем: pfSense — чёткий runtime-статус без ложных метрик. Как: существующие `useQuery`/`queryKeys.dhcpLeases`, `ErrorNotice`, `EmptyState`, `Badge`; «обновить» остаётся локальным действием карточки (`frontend/src/pages/Services.tsx:31-36,88-92`). Объём S. Риск: не выдавать отсутствие доступного API за отсутствие конфликтов.

### DNS — `Services.tsx` / `ServiceEditors.tsx`

- Текущее состояние: вкладки «Записи и переадресация / Upstream и режим / Журнал запросов»; записи и доменные переадресации — две таблицы; карточка режима/привязки видна на первых двух вкладках, а чтение DNS-журнала и live-диагностика недоступны (`frontend/src/pages/Services.tsx:103-175`). Редактор заменяет обзор целиком, добавляет запись A/CNAME с TTL, доменную переадресацию с вложенными карточками UDP/DoT/DoH, режим рекурсии, логирование и интерфейсы; `access_control` только отображается (`frontend/src/pages/ServiceEditors.tsx:380-412,431-608`).
- Проблемы UX:
  1. Буквальные «host overrides», `forward-zone`, `Upstreams`, «dnscrypt-proxy» и «Режим прокси-сервера» подменяют задачи администратора реализацией Unbound; DoH-строка при этом не адрес обычного upstream (`frontend/src/pages/Services.tsx:123-139`; `frontend/src/pages/ServiceEditors.tsx:74-123,500-543`).
  2. Вложенный `UpstreamRows` целиком размещён в ячейке таблицы доменов: ширина и высота строк непропорциональны, действие удаления трудно соотнести с доменом (`frontend/src/pages/ServiceEditors.tsx:500-531`; `frontend/src/styles.css:416-429`).
  3. Валидатор понимает AAAA, но выбор типа даёт только A/CNAME (`frontend/src/pages/ServiceEditors.tsx:387-395,450-455`). Кнопка «Журнал запросов» включает сбор, хотя открываемая вкладка не умеет его читать (`frontend/src/pages/ServiceEditors.tsx:556-560`; `frontend/src/pages/Services.tsx:171-175`). Редактируются интерфейсы, но ACL лишь текстом — нельзя заявлять, что выбор интерфейса гарантирует доступ клиента (`frontend/src/pages/ServiceEditors.tsx:562-607`).
- Предложения:
  1. Что: страница «Локальные имена» (имя→IP/другое имя) и «Домены с отдельным DNS» как два `Card` со своим `action=«Добавить…»`, записи оставить таблицей, forward-зону редактировать отдельной формой: домен + список DNS-серверов. Убрать `forward-zone` из основного текста; «технические детали» — пояснение, не сырой `local-data`. Зачем: Keenetic — понятные записи; LuCI — группы настроек без field soup. Как: переиспользовать `Card`, `DataTable`, `FormGrid`, `UpstreamRows` вне ячейки; редактор записи в том же draft lifecycle. Объём M. Риск: одна точка добавления на список (`docs/ui-rules.md:80-88`); без второго сохранения записи как отдельной применённой конфигурации.
  2. Что: в глобальных настройках назвать `forwarding` «Через указанные DNS-серверы», рекурсию «Самостоятельный поиск»; интерфейсы — «Где отвечает DNS» плюс read-only «Каким сетям разрешён доступ» из `access_control`; логирование — «Записывать DNS-запросы (для диагностики)», рядом честное «просмотр здесь пока недоступен». Зачем: Keenetic — человеческие опции; pfSense — видимая граница факта/настройки. Как: `Toggle`/`InterfaceSelect`/`InfoNote`, сохранить точную семантику ACL (`CONTEXT.md:51-57`). Объём S для текста, M для пересборки. Риск: не создавать toggle «DNS включён», пока поле и операция не подтверждены; решение о read-only ACL обсудить с backend.
  3. Что: протоколы UDP/DoT/DoH оставлять в раскрываемых «Дополнительно» DNS-сервера с русскими видимыми метками адреса/порта/TLS-имени, валидным отображением AAAA лишь после проверки API и генератора; исправить специфическое имя поля «прокси-сервер» (`frontend/src/pages/ServiceEditors.tsx:85-123,136-139`). Зачем: LuCI — экспертные опции доступны, но не перегружают первый экран. Как: `Field`, `Select`, `FormGrid` без нового UI-кита. Объём M. Риск: DoH `doh_server` не переименовывать на уровне payload без синхронизации контракта.

### Прокси / сайты — `Services.tsx` + граница `ConnectionEditors.tsx` / `Routing.tsx`

- Текущее состояние: `/proxy` — именно Caddy, вкладки «Сайты», «DDNS», «Журнал»; журнал — заглушка (`frontend/src/pages/Services.tsx:180-205`). `Sites` — коллекция с таблицей `Имя | Hostname | Upstream | Сертификат | Статус`, добавление только в общем режиме редактирования; статус сайта всегда `—`. Редактор сайта принимает hostname, свободный текст upstream, режим сертификата, WAN-адрес и секреты; конфликт HTTP-01 с port forward уже предупреждается (`frontend/src/pages/ConnectionEditors.tsx:231-245,340-445,871-995`). `DDNS` там же отдельная коллекция (`frontend/src/pages/ConnectionEditors.tsx:998-1094`). Выбор «трафик по признакам → выход/туннель» находится не здесь, а в `/routing`: мастер выбирает `direct/block/route` и outbound из `proxies.outbounds`/groups (`frontend/src/App.tsx:131-134,284-286`; `frontend/src/pages/Routing.tsx:103-109,225-241`).
- Проблемы UX:
  1. Слово «Прокси» навигирует в Caddy-сайты, а не к правилам выхода; админ, ожидающий «домен → туннель», попадает на «Hostname → Upstream» сайта (`frontend/src/App.tsx:131-134`; `frontend/src/pages/Services.tsx:185-194`; `frontend/src/pages/ConnectionEditors.tsx:925-940`). Не смешивать входящий reverse proxy и TProxy в одной таблице.
  2. `certificate_mode` и `upstream` показаны сырыми строками, при этом `Статус` не измеряется; «Добавить сайт» доступно после «Редактировать» (`frontend/src/pages/ConnectionEditors.tsx:340-445,901-907,925-954`).
  3. В мастере TProxy выход — только tag без доказательства, что это именно нужный клиентский туннель; сам TProxy сейчас недоступен, сохранённые правила не действуют (`frontend/src/pages/Routing.tsx:103-108,169-175,225-242`). Обещание проверки живого пути сейчас было бы ложным.
- Предложения:
  1. Что: переименовать пункт `/proxy` в «Сайты и DDNS» (или «Входящие сайты»), внутри оставить «Сайты / DDNS», заглушку журнала не предлагать как рабочий журнал; вход в «Правила выборочной маршрутизации» — явной ссылкой на `/routing`, не новый редактор в G3. Зачем: Keenetic — плоское меню понятных объектов. Как: `PageTabs`, `Card`, существующие маршруты; G1 согласовать названия навигации. Объём S/M. Риск: не путать Caddy HTTP-upstream с TProxy-outbound.
  2. Что: карточка сайта в просмотре «Домен → внутренний сервер», «Сертификат: авто/ручной/passthrough», «WAN-адрес», строковое действие «Редактировать»; таблица допустима для 20 сайтов, карточка-строка предпочтительна для проверки связи. «Добавить сайт» прямо в `Card action`. Зачем: Keenetic — один объект и его понятная цель. Как: переиспользовать `Card`/`DataTable`, `EditorShell` и `FormGrid`; не показывать секреты сертификатов (`CONTEXT.md:132-137`). Объём M. Риск: сохранить целостность `Collection`/общего черновика; новый list-row primitive — только после решения G1 и обновления `docs/ui-rules.md`, `docs/ui-refactor.md`, ADR-0011.
  3. Что: в G4-owned `/routing` показывать у правила читаемую цепочку «совпадение → тип выхода → имя/интерфейс туннеля» и предупреждать «выход не выбран/не связан/перехват пока недоступен»; переход к конкретному туннелю по идентификатору, без заявления о live-проверке. Зачем: Keenetic — понятный исходящий путь; pfSense — различимые конфиг/состояние. Как: согласовать с G2/G4 селектор с типизированными `outbound`/tunnel references; runtime-проверка — только после отдельного API. Объём M/L (межгрупповое). Риск: `AllowedIPs` не маршрут (`CONTEXT.md:104-129`); fail-closed TProxy и выключенный перехват не менять.

### Сквозное состояние сервисов — DHCP / DNS / Caddy / DDNS / туннели

- Текущее состояние: DHCP знает только об ошибке чтения аренд (`frontend/src/pages/Services.tsx:88-92`), DNS показывает опции черновика (`frontend/src/pages/Services.tsx:145-163`), Caddy и туннели рисуют `—` (`frontend/src/pages/ConnectionEditors.tsx:570-575,901-907`); общий topbar помечает draft/confirmed, но не говорит о runtime конкретного сервиса (`frontend/src/App.tsx:200-208`). Публичные API-клиенты здесь дают аренды/поиск/QR, но отдельного `serviceStatus` в рассмотренном участке нет (`frontend/src/api.ts:91-108`).
- Проблемы UX:
  1. «вкл/выкл» DNS относится к логированию, не к службе; перенести его визуально в блок параметров, а не на статусную строку (`frontend/src/pages/Services.tsx:157-163`).
  2. Метрики и ошибки нельзя смешивать с desired state черновика (`frontend/src/pages/Services.tsx:57-64,88-92`; `frontend/src/App.tsx:200-208`).
- Предложения:
  1. Что: единый тонкий status-header «Служба: работает/остановлена/неизвестно», время получения, последнее подтверждённое применение, 1–2 профильных показателя (DHCP аренды, DNS запросы только при реальном счётчике, Caddy доступные сайты, туннель handshake); при ошибке — «Последняя ошибка» и ссылка на журнал. Отдельная строка «В черновике: …; ещё не применено». Зачем: pfSense — состояние видно сразу; Keenetic — один ясный статус без дашборда из метрик. Как: до появления backend-диагностики только `Card`+`Badge`+`InfoNote` с «Статус недоступен»; G1 согласовать общий `ServiceStatusHeader` как новый примитив и контракт `unknown/loading/error/stopped/running`, добавить Query key отдельно от apply status (`docs/ui-rules.md:114-120`). Объём M UI, L с runtime API. Риск: новый примитив требует обновления `docs/ui-rules.md`, `docs/ui-refactor.md`, ADR-0011; `apply/status` не превращать в Query и не использовать как health endpoint; агент — whitelist RPC (`CONTEXT.md:171-178`).
  2. Что: переключатели службы показывать только при наличии реального поля включения для конкретного сервиса и подписью «После применения»; сейчас DNS `log_queries` и туннель `open_port` не равно выключению службы (`frontend/src/pages/ServiceEditors.tsx:551-560`; `frontend/src/pages/ConnectionEditors.tsx:699-703`). Зачем: Keenetic — прямое «Вкл/Выкл» только когда оно правдиво. Как: существующий `Toggle` + схема/API/типы/backend одновременно; без ручного systemctl из UI. Объём L. Риск: общеконфигурационный apply/rollback и fail-closed неизменны.

## 1. Общая оценка раздела

Каркас безопасный: firewall сортирует правила по `order`, TProxy явно помечен недоступным и не может быть включён, SSH выбирается по интерфейсам с подтверждением WAN (`Firewall.tsx:86-110`, `Routing.tsx:137-175`, `SSH.tsx:19-21,64-73`). Но главным интерфейсом управления firewall остаётся десятиколоночная таблица с `pass/block/reject` и строковым синтаксисом `@алиас`; порядок виден, смысл конкретного совпадения — нет (`Firewall.tsx:194-307`). В «Маршрутизации» соседствуют неподключённый перехват, настройка выходов и read-only downloader, тогда как отдельный пункт «Маршруты» ведёт к пустой таблице (`Routing.tsx:498-520`, `RoutingProxy.tsx:718-785`, `App.tsx:130-131`, `Network.tsx:453-459`). Рекомендуем Keenetic-подобные именованные объекты и человекочитаемые действия, но сохраняем pfSense-видимость приоритета и OpenWrt-экспертную глубину; никаких обещаний, что TProxy или статические маршруты уже работают. Все изменения конфигурации остаются черновиком для общего атомарного применения/отката, не отдельной кнопкой «применить здесь» (`CONTEXT.md:33-47`, `App.tsx:99-123`).

## 2. Постраничный разбор

### Правила — `Firewall.tsx`

- Текущее состояние: вкладки зон плюс `Port Forward`, `Outbound NAT`, `Псевдонимы`; внутри каждой вкладки зоны повторяются также три остальные карточки (`Firewall.tsx:75-89,175-185,345-346,472-473,604-605`). Правила сортируются по `order`, переставляются стрелками, сохраняются с новой нумерацией; показаны предупреждение first-match/default deny и индикатор anti-lockout (`Firewall.tsx:86-110,194-225,335-342`). Таблица в просмотре показывает технические поля, но не счётчики, хотя `counters` есть в типе (`Firewall.tsx:194-306`, `types.ts:39-50`).
- Проблемы UX:
  1. Первый экран — широкая таблица из 10 колонок; действие `pass/block/reject`, `src/dst` в виде `any`, `zone:lan`, `@алиас`, лог через `●` не рассказывают «кому → куда → что случится» (`Firewall.tsx:194-206,244-263,293-305`). При создании сразу появляется активное `block any → any`, что может перекрыть все нижние правила до исправления (`Firewall.tsx:309-327`); это риск именно из-за first-match (`CONTEXT.md:77-79`).
  2. Порядок нулевой, показан как `r.order` и понятен только из приписки под таблицей; default deny не показан последней строкой, нет видимого выделения выключенного правила и счётчиков попаданий (`Firewall.tsx:211,294-305,335-338`; `types.ts:47-50`). «Вверх/Вниз» — текстовые кнопки с Unicode-стрелкой вопреки `docs/ui-rules.md:35`, а в `Outbound NAT` тоже сказано «First match wins», но видимого порядка и перестановки нет (`Firewall.tsx:495-570,599-601`).
  3. На вкладке зоны постоянно дублируются Port Forward, Outbound NAT и алиасы; метка `авто` в строке port forward может читаться как статус всей операции, хотя обозначает автоматически созданное filter-правило (`Firewall.tsx:345-470,431-440`). Сгенерированные правила туннелей перечислены отдельной заметкой, а не в контексте приоритетного списка (`Firewall.tsx:186-193`).
  4. Импорт алиасов немедленно вызывает отдельный `saveDraft({...c, aliases})`, доступен и при локальном редактировании firewall/NAT; локальный редактор затем меняет только `aliases`. Это позволяет расходиться видимым несохранённым правкам и сохранённому черновику (`Firewall.tsx:63-66,606-608`, `useDraftEditor.ts:41-54`). Выбор режима NAT и translation также показывает `automatic/hybrid/manual/disabled`, `primary` без русского объяснения эффекта (`Firewall.tsx:473-483,536-543`).
- Предложения:
  1. Что: в просмотре зоны — компактные именованные строки «1. Разрешить · Домашние устройства → роутер · TCP/443», для `reject` — «Отклонить с ответом», явно «Выключено»; внизу неизменяемая строка «По умолчанию: запретить». Служебные `zone:`, `@`, протокол, порт и лог — во второй строке/раскрытии, но не исчезают. Зачем: Keenetic даёт понятное действие, pfSense — порядок и default deny. Как: `Card` + `DataTable` для просмотра, `Badge` для действия/состояния, `InfoNote` для семантики; источники/назначения форматировать из существующих значений, не изменяя payload. Порядковый номер показывать с 1, при изменении явно сообщать «выше = проверяется раньше», не сортировать по имени; счётчики показывать только при подтверждённой привязке к реальному правилу, иначе честно «нет данных». Объём M. Риск: не подменить реальную последовательность правилами NAT/авто-правилами и не выдавать нулевые счётчики черновика за runtime (`docs/ui-rules.md:31-32,67-78`).
  2. Что: отдельный последовательный компоновщик «Имя → Откуда → Куда → Протокол/порт → Разрешить/Запретить/Отклонить → Позиция», выбор «Любой / зона / адрес или алиас», после сохранения — сразу итоговая фраза. Зачем: Keenetic снижает потребность знать синтаксис, OpenWrt оставляет экспертное поле `@алиас` и спецрежим. Как: `FormGrid` + `Field`, `Select`, `InterfaceSelect` только там, где выбирают интерфейс, `EditorFooter`; редактирование одной строки в карточке, остальные в списке, позиция first-match видна до сохранения; добавлять неполную строку выключенной либо не включать до заполнения и явно показывать это. Не отменять `block/reject`, лог, порядок и валидацию. Объём L. Риск: смена способа редактирования не должна менять порядок/семантику сопоставления и нарушать единый `useDraftEditor` (`Firewall.tsx:90-146,309-329`; `docs/ui-rules.md:47-65`).
  3. Что: Port Forward, Outbound NAT и алиасы — только соответствующие вкладки; в WAN-зоне оставить ссылку и короткую пометку «авто-разрешение к перенаправлению», в NAT показать позицию и русские режимы с фразой «NAT не выбирает маршрут». Зачем: Keenetic упрощает список, pfSense различает filter/NAT и их порядок. Как: убрать условия `zone || …`, использовать `Card`, `DataTable`, существующие `ValueTabs`, `Badge`, `InfoNote`; адрес translation выбирать с учётом реального списка WAN-адресов, `primary` остаётся значением контракта. Объём M. Риск: встроенная зона `router` и приоритет port forward перед локальным сервисом должны остаться объяснёнными (`Firewall.tsx:175-181,345-470,472-601`; `CONTEXT.md:76-83`).
  4. Что: импорт алиасов — только как операция внутри общего редактирования, с предпросмотром затрагиваемых имён и одним сохранением черновика; запретить немедленное сохранение в обход `EditorFooter`. Зачем: OpenWrt-целостность конфигурации без второго Save/Apply. Как: использовать уже имеющиеся предпросмотр, `ErrorNotice`, `useDraftEditor`, `EditorFooter`; подтверждать замену затрагиваемых имён согласно `docs/ui-rules.md:80-88`. Объём M. Риск: не терять текущие локальные правки firewall/NAT и не показывать импорт как применённый к системе (`Firewall.tsx:63-66,606-608`).

### Маршрутизация / статические маршруты — `Routing.tsx` и контекст `Network.tsx`

- Текущее состояние: `Routing.tsx` — «Маршрутизация» с вкладками `sing-box TProxy`, «Прокси-выходы», `Rule-set`, без списка статических маршрутов (`Routing.tsx:498-520`). В sidebar отдельно есть «Маршруты» → `/network?tab=routes`; там всегда пустая таблица «Сеть назначения / Шлюз / Интерфейс / Метрика» с честной пометкой об отсутствии модели API (`App.tsx:125-135`, `Network.tsx:453-461`, `types.ts:265-284`). Не путать DNS `forwards` (сервер разрешения домена) с выбором сетевого пути (`types.ts:79-89`, `CONTEXT.md:53-58,113-116`).
- Проблемы UX:
  1. Пункт «Маршруты» обещает работающий редактор, но показывает заголовки и ноль строк; подмена таблицы примером была бы фабрикацией (`App.tsx:130`, `Network.tsx:453-459`).
  2. Соседние названия «Маршруты» и «Маршрутизация» не объясняют различия между сетью назначения через шлюз/метрику, доменным DNS forward и TProxy-политикой источника; в `Routing.tsx` поля `domain_suffix` относятся именно к TProxy, а не к обычной таблице маршрутов (`Routing.tsx:20-36,301-325,395-469`, `CONTEXT.md:113-129`).
- Предложения:
  1. Что: пока маршрутов нет в контракте — честное `EmptyState` «Статические маршруты пока не поддерживаются», без пустой шапки таблицы; в навигации убрать отдельный пункт до реализации либо явно пометить «планируется». Зачем: Keenetic не предлагает неработающее действие. Как: существующий `EmptyState` вместо `rows={[]}`; не добавлять фиктивную кнопку. Объём S. Риск: изменение навигации затрагивает привычные ссылки; согласовать с владельцем меню (`App.tsx:130`, `Network.tsx:453-459`).
  2. Что: после появления backend/schema-модели — простой список «Сеть назначения → через шлюз / интерфейс · метрика», composer из сети/шлюза/интерфейса/метрики, отдельно текущее WAN и пояснение «меньшая метрика = предпочтительнее при одинаковом префиксе; более точная сеть имеет приоритет». Не выводить «маршрут по домену» как обычный static route: доменная привязка — правило TProxy к выходу после реального включения функции; DNS forward — выбор DNS-сервера, а не outbound. Зачем: Keenetic для простоты, OpenWrt для явной метрики. Как: будущие `DataTable`/`Card`, `FormGrid`, `Field`, `InterfaceSelect`, `EditorFooter`; изменения только общим черновиком. Объём L (backend schema/API/generator/validation обязателен). Риск: зависимость от туннельных маршрутов и `AllowedIPs ≠ маршрут` (`CONTEXT.md:113-116`; `types.ts:265-284`).
  3. Что: названия/подзаголовки «Маршруты по сети» и «Правила выбора выхода (TProxy)», рядом однострочное «маршрут выбирает шлюз; TProxy выбирает выход для перехваченного трафика». Зачем: Keenetic-категории понятнее двух почти синонимов, pfSense сохраняет строгую семантику. Как: `PageHeader`/`InfoNote` в существующих разделах, без нового маршрутизатора. Объём S. Риск: не писать, что TProxy уже доступен (`Routing.tsx:170-175`, `App.tsx:130-131`).

### Выборочная маршрутизация, выходы, списки — `Routing.tsx` + `RoutingProxy.tsx`

- Текущее состояние: TProxy имеет «Простой / Мастер / Эксперт» внутри вкладки «sing-box TProxy»; предупреждение «недоступен», кнопка включения disabled, оба пути сохранения принудительно ставят `enabled: false` (`Routing.tsx:74-81,137-158,170-186`). Эксперт показывает источники, ordered rules, конечное действие, bypass, DNS-серверы/правила и окно обновления (`Routing.tsx:289-490`). Выходы, подписки, группы — отдельный `ProxiesEditor` (`RoutingProxy.tsx:99-161,170-706`); `RuleSets` — read-only список источников и ручное обновление (`RoutingProxy.tsx:718-785`). Именно `RoutingProxy.tsx` имеет 787 строк, но большая часть формы политики находится в `Routing.tsx:61-496`; нельзя приписывать inbounds/rules/schedules одному файлу.
- Проблемы UX:
  1. «Простой» представляет конечное действие как код `direct/block/route`, строку `источники → sing-box → выходы`; это выглядит как работающий путь, хотя над ней предупреждение о недоступности.
