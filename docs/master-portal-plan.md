# План: мастер-портал (`vs_master`) — ADR-0035

Решения зафиксированы в ADR-0035 (`docs/adr/0035-master-portal-architecture.md`); термины — в `CONTEXT.md` (раздел «Мастер-портал»). Этот документ — рабочий план и статус.

## Принятые решения (кратко)

| # | Решение |
| --- | --- |
| D1 | Мастер = единственная БД абонентов; локальные публичные порталы нод закрываются |
| D1a | Фолбэк = постоянная read-only реплика на нодах, без авто-режимов; ручной failover — будущая опция |
| D2 | Канал мастер→нода: HTTPS к internal bridge, bearer-токен; авто-ротация через `token-rotate` (старый токен — канал выдачи нового); онбординг/ревок — ручные |
| D3 | Регистрация: бот (открытая саморегистрация, tg id = идентичность) ИЛИ админ; врата = активная Subscription |
| D4 | Метрика загрузки = активные устройства / ёмкость (задаёт админ); автораспределение только при создании устройства; автомиграций нет |
| D5 | Существующие абоненты — разовая миграция локальных БД в составе онбординга ноды; `Device.node_id`; суррогатный PK у Account, имя — display-текст |
| D6 | Нода скрыта от абонента |
| D7 | Телеметрия: опрос ~30–60 с, состояния `ok`/`stale`/`down`; в распределение — только `ok`; device-op к недоступной ноде копятся и повторяются |
| D8 | rg1 = только мастер; поддомен + reserve `<ip>.nip.io`; caddy standalone |
| D9 | Админ-панель ноды остаётся; portal-процесс ноды остановить (не снести до успешной миграции) |
| D10 | Бот: `/start` → регистрация из TG-данных, magic-ссылка на вход; long polling; токен в зашифрованных настройках БД |
| D11 | Подписку назначает админ вручную (MVP); нода = атрибут Device, подписка = атрибут абонента; уведомление об истечении — портал + бот |
| D12 | Отдельный пакет `vs_master`; профиль мастера — отдельная строка `MODULE_PROFILES`; footprint → ADR-0021 |
| D13 | Отдельный фронтенд `frontend-master/` (ноды, абоненты, настройки) |
| D14 | Бэкапы: timer на мастере → ноды + pull со станции + в чат админу ботом (предпочтительно `age`-шифрование) |
| D15 | Этапность: (1) мастер+ноды+миграция, (2) бот/регистрация, (3) реплики-фолбэк, (4) операционка |

## Этапы

### Этап 1 — мастер работает, ноды подключены

- [ ] Пакет `vs_master`: БД + миграции (`alembic-master`), модели (Node, Account+tg id, Device.node_id), реестр нод
- [ ] Bridge-клиент мастера + `token-rotate` на ноде; bearer-аутентификация bridge для мастера
- [ ] Воркер DeviceOp мастера против удалённого bridge (повторы при недоступной ноде)
- [ ] Скрипт миграции локальной портал-БД ноды → мастер (в составе онбординга)
- [ ] Публичный портал мастера (вход, устройства, QR/конфиг) + админка: ноды + абоненты
- [ ] Смена пароля абонентом на своей странице портала: текущий пароль, новый пароль и подтверждение; проверка текущего пароля, запись только хеша нового пароля
- [ ] Смена пароля абонента администратором из карточки абонента в админ-панели: задание нового пароля без знания старого; старый пароль и хеш не показывать. После обоих способов смены отозвать прежние сессии абонента, записать событие аудита без пароля; покрыть API и UI тестами
- [ ] Caddy мастера: поддомен + reserve-имя
- [ ] Онбординг rg2…rgN: токен, миграция, ёмкость; остановка локальных portal-юнитов + снятие публикации
- [ ] Профиль мастера в `MODULE_PROFILES` + запись в ADR-0021
- [ ] Миграция существующих абонентов проверена на реальных данных нод

### Этап 2 — регистрация

- [ ] TG-бот: саморегистрация, уведомления (назначение подписки, истечение), magic-ссылки
- [ ] Врата на подписке в портале («ожидает назначения тарифа»)

### Этап 3 — фолбэк

- [ ] Read-only реплика на нодах (снапшот мастер-БД), действия disabled с пояснением

### Этап 4 — операционка

- [ ] systemd timer бэкапов: на ноды + в чат админу (`age`)
- [ ] Pull-бэкап со станции; разовая проверка восстановления
- [ ] Авто-ротация токенов по расписанию (в этапе 1 — кнопки вручную)

### После MVP — отказоустойчивость подключений абонентов (исследование)

- [ ] Спроектировать перенос подключений устройств с недоступной или заблокированной ноды на другую работоспособную ноду **без переэкспорта и ручного изменения клиентского конфига**. Сравнить варианты стабильной точки входа (адрес/домен, порт, маршрутизация) с учётом ключей сервера, адресов пиров, протокола и его параметров; проверить, какие из них действительно работают при блокировке IP/домена, а не только при отказе сервиса. Определить обнаружение отказа по доступности клиентского трафика (одной телеметрии bridge недостаточно), порядок безопасного переноса `Device.node_id` и состояния пира, защиту от двух активных копий, повторы операций и возврат после восстановления. Зафиксировать допустимый перерыв: восстановление новых подключений не означает сохранение уже открытых сессий. Результат — отдельный контракт/ADR, прототип на одноразовых нодах и сквозные тесты отказа, восстановления и повторного отказа; до принятия решения не считать автоматическую миграцию реализованной. Текущие D4/ADR-0035 сохраняются: автораспределение только при создании устройства, автомиграций нет.

## Открытые вопросы

- Имя поддомена мастера (`portal.poshl9k.ru` / `my.poshl9k.ru` …) — рабочий вариант по умолчанию `my.poshl9k.ru`; подтвердить перед публикацией.
- Схема сессий/админа мастера — переиспользовать портал-схему ADR-0032 (ожидаемо да; проверить при имплементации).
- Контракт `token-rotate` (идемпотентность, переходный период двух токенов) — РЕШЁН и реализован на ноде (`vs_router/internal_app.py`): аутентификация текущим токеном; тело `{new_token}`; идемпотентный повтор старым токеном → 200 `{'rotated': False}` если предложенный токен уже текущий, иначе 403 (токен отозван); предыдущее поколение живёт до подтверждения ротации мастером. Клиент мастера — `vs_master/bridge.py`.
- Node bridge в кандидате резолвит устройства по присланному мастером key material и хранит отдельный execution cache; локальная portal DB для этих операций не требуется. Сквозная проверка с остановленным локальным portal-процессом на одноразовой VM и онбординг реальных нод остаются открытыми.
