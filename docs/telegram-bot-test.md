# Telegram-бот локального портала `panel`

Это бот локального `vs_portal`, **не** бот единого `vs_master` из ADR-0035.
Мастер-бот (magic-вход, уведомления) остаётся отдельным этапом. В локальном
боте саморегистрация экспериментальна и по умолчанию выключена: только настройка
`self_registration_enabled=1` в портальной БД показывает кнопку и разрешает
`/register`. Создаётся аккаунт без подписки и без доступного веб-пароля; сама
регистрация **не выдаёт сетевой доступ**. Не включать для клиентов до появления
автопровижининга в конфигурацию панели и проверки выдачи доступа. Оплата Stars
и цена тарифа пока не реализованы; не выставлять счета от этого бота.

## Выпуск и включение

Новая установка `panel` требует собранный `frontend-portal/dist` вместе с
`frontend/dist` и wheel. `make-release.sh` собирает оба фронтенда и кладёт их в
проверяемый архив. `install.sh` разворачивает портал в
`/var/lib/vs-router/portal/ui`, мигрирует БД до ревизии `0006` и перезапускает
`vs-router-portal` и `vs-router-telegram`. Без портального bundle установка
`panel` завершается ошибкой, а не публикует API без интерфейса. У `router`
этого требования нет. Не запускать установщик ради проверки на рабочем VPS:
сначала собрать выпуск и проверить его на одноразовой Debian VM.

Токен Telegram задаётся администратором через `PUT /api/portal-admin/settings`
(`{"bot_token":"<token>"}`) по аутентифицированной HTTPS-сессии панели.
Новый токен шифруется ключом панели перед записью в БД; API возвращает только
`bot_token_configured`, не сам токен. Консольный мастер первого запуска
принимает токен скрытым вводом или позволяет пропустить его. Старое открытое
значение БД шифруется воркером при первом чтении. Никогда не помещать токен
в командную строку, URL, чат или логи.

## Привязка и проверка

1. В портале активировать инвайт и войти под аккаунтом абонента.
2. В этой же защищённой сессии вызвать `POST /api/portal/telegram/link`;
   ответ `code` действителен 10 минут. Новый код отменяет предыдущий.
   Показывать код только самому абоненту; не записывать в логи.
3. В личном чате с ботом отправить `/start <code>`. Логин абонента сам по себе
   **не привязывает** Telegram-чат. Код одноразовый, в БД хранится только SHA-256.
4. После привязки `/start` и `/menu` показывают кнопки «Статус», «Устройства»,
   «Поддержка», «Помощь». Нажатия обновляют то же сообщение; кнопка «Назад в меню»
   возвращает к разделам. Команды `/status`, `/devices`, `/support`, `/help`
   остаются доступными. Обычный текст бот игнорирует. Для неподключённого чата
   `/status` и `/devices` не выдают сведения об абоненте.

Для одного токена допускается только один активный polling-воркер. Ответ API 409
на `getUpdates` означает конфликт с другим получателем обновлений; воркер делает
паузу 60 секунд, но не определяет адрес второго процесса. Перед живой проверкой
остановить прежний экземпляр (в том числе запущенный вне VPS) либо перевыпустить
токен в BotFather и настроить его только у одного воркера. Токен не публиковать.

Проверка с `httpx.MockTransport` и временной SQLite-БД не доказывает реальный
Telegram polling. Для живой приёмки нужен отдельный тестовый бот с токеном,
введённым оператором в админке, и тестовый абонент. Нельзя включать старую
версию бота с привязкой по одному логину.
