# Лабораторная проба предварительной авторизации TProxy

Дата: 3 октября 2026. Одноразовая Debian VM `vsr-verify-20261002`, ядро `6.12.107+deb13-amd64`, исходный snapshot `pre-singbox-20261002`.

## Что реализовано

`backend/src/vs_router/generators/nftables.py:generate_tproxy_preauthorization` — экспериментальный отдельный генератор, **не подключённый** к apply/API/boot restore. Общие матчеры, алиасы, порядок `(order, name)`, порты и logging вынесены в `_FirewallCompiler`; действующий `generate_nftables` продолжает выдавать побайтно прежние golden-файлы.

Предварительный фильтр стоит в PREROUTING с priority `-90`, после стандартного DNAT (`-100`) и до будущего перехвата/его mark. Для выбранного ingress локальное назначение и `ct status dnat` возвращаются без выдачи разрешающего marker; последующий перехват обязан повторить эти исключения. Для поддержанного IPv4 TCP/UDP транзита действует положительная проверка назначенного выходного интерфейса, затем first-match firewall и default drop. Нераспознанный маршрут не должен попасть в широкое `pass`.

**Отличия прототипа от конечного продукта:** нет conntrack established/related shortcut (правила проверяются на каждом пакете); `reject` консервативно превращается в `drop`, поскольку PREROUTING не поддерживает такой reject. IPv6/остальные протоколы выбранного нелокального, не-DNAT трафика блокируются. Это не завершённая семантика IPv6/bypass. Проход через preauth не является разрешением перехвата, авторизацией фактического proxy OUTPUT или готовностью службы.

## Изоляция и воспроизведение

Все пакетные изменения выполнены внутри **трёх новых namespace VM**, не в её основном пространстве: `vsr-pa-client` → `vsr-pa-router` → `vsr-pa-origin`. Физические NIC, default route и firewall хоста/основного пространства VM не менялись. sing-box в этой пробе не запускался.

Артефакты:
- `backend/tests/lab/generate_tproxy_preauth_cases.py` создаёт тестовые файлы настоящим генератором; offline `model_copy` обходится с намерением enabled только в этих фикстурах, публичная валидация остаётся закрытой.
- `backend/tests/lab/tproxy_preauth_probe.py` запускается root **только на явно разрешённой одноразовой VM**. Создаёт namespace, принимает JSON с правилами, выполняет `nft -c` и live-применение только в `vsr-pa-router`, затем удаляет namespace/процессы.

Из `backend/` с установленными зависимостями:

```sh
env -u PYTHONPATH .venv/bin/python tests/lab/generate_tproxy_preauth_cases.py "$TMPDIR/preauth-cases.json"
```

Скопировать JSON и probe на одноразовую VM; там выполнить `sudo python3 tproxy_preauth_probe.py preauth-cases.json`. Не выполнять probe на хосте или рабочем роутере. В этой сессии передача/запуск выполнялись через QEMU guest agent, без SSH/паролей.

Origin имеет `198.18.0.2/32` на loopback, а router — маршрут к нему через `10.212.2.2 dev wan0`. Поэтому разрешение `dst=zone:wan` проверяет **маршрут**, а не попадание назначения в адресную подсеть `wan0`.

## Ошибка FIB, найденная реальными пакетами

Первоначальный вариант `fib daddr . mark . iif oifname` прошёл `nft -c`, но **не пропустил разрешённый UDP**: ingress видел отправленный payload, origin не видел ни кадра, ни запроса, сработал default drop до цепочки правил. `ip route get 198.18.0.2 from 10.212.1.2 iif lan0` при этом показывал правильный `wan0`.

Причина подтверждена исходником Linux v6.12: [nft_fib_ipv4.c](https://github.com/torvalds/linux/blob/v6.12/net/ipv4/netfilter/nft_fib_ipv4.c), строки 80–85 и 138–143. Флаг `NFTA_FIB_F_IIF` ограничивает результат устройства входящим интерфейсом, а не передаёт его как обычный ingress в полный forwarding lookup.

После замены на `fib daddr . mark oifname` разрешённый маршрут заработал. Исправлено в обоих местах: assigned-egress gate и destination-zone matcher. Добавлены регрессионные unit-проверки; окончательная проба использовала **не модифицированный текст**, а прямой результат исправленного генератора.

**Ограничение:** lookup без `.iif` не воспроизводит iif-/L4-зависимые policy rules и все ECMP-сценарии; это не доказательство соответствия произвольной конфигурации ядра. Перед интеграцией нужен runtime gate неподдерживаемой топологии или другая точка авторизации.

## Реальные результаты UDP

Одновременно работали AF_PACKET-наблюдатели на ingress router и интерфейсе origin, UDP echo receiver origin. Каждый запрос содержал уникальный токен; отправитель фиксировал число отправленных байтов. Готовность процессов проверялась явно, положительные контроли выполнены до/после блокирующих случаев. Числа wire включают запрос/ответ; это не число независимых запросов.

| Случай | ingress wire | origin wire | получено приложением | ответ |
| --- | ---: | ---: | ---: | --- |
| baseline без preauth | 2 | 2 | 1 | `vsr-pa-baseline` |
| разрешающий firewall | 2 | 2 | 1 | `vsr-pa-allow` |
| block до pass | 1 | 0 | 0 | нет |
| без правил, default deny | 1 | 0 | 0 | нет |
| pass до block | 2 | 2 | 1 | `vsr-pa-allow-first` |
| off: удалена только preauth-таблица | 2 | 2 | 1 | `vsr-pa-off` |

Для запрещённых случаев отсутствие токена у origin сопоставлено с его наличием на ingress и успешными контрольными запросами. Вывод ограничен наблюдаемыми запросами в этом тесте; окна ожидания ответа 0.7 секунды плюс 0.2 секунды наблюдения. Это **не полное доказательство fail-closed TProxy**, поскольку самого перехвата/процесса здесь нет.

## Совместная проба с обычным firewall: INPUT и DNAT

Дополнительный запуск на той же одноразовой VM использовал настоящий `generate_nftables` вместе с preauth. Обычный firewall: default deny, без anti-lockout и NAT исходящего трафика; явный UDP INPUT pass на 19090. Для port-forward генератор создал DNAT `wan0:19091` → `10.212.1.2:19090` и связанное FORWARD-разрешение `auto_wan_udp`.

AF_PACKET и UDP receiver работали одновременно на router LAN, client и origin. Каждый запрос имел уникальный payload и отдельный явно назначенный source port, чтобы избежать established-flow shortcut между случаями. Положительные проверки подтвердили исходный tuple ответа и post-DNAT tuple запроса. Receiver привязан к конкретному адресу назначения: wildcard UDP socket изначально отвечал с основного адреса origin вместо его loopback; тест это обнаружил, binding исправлен.

| Случай | wire отправителя | wire получателя | получено приложением | ответ |
| --- | ---: | ---: | ---: | --- |
| локальный INPUT, явный pass | 2 | 2 | 1 | есть |
| локальный INPUT, default deny | 1 | 1 | 0 | нет |
| связанный WAN port-forward | 2 | 2 | 1 | есть |
| несвязанный WAN DNAT | 1 | 0 | 0 | нет |
| несвязанный DNAT с выбранного LAN ingress | 1 | 0 | 0 | нет |
| контрольный port-forward после отказов | 2 | 2 | 1 | есть |
| контрольный локальный INPUT после отказов | 2 | 2 | 1 | есть |

Для INPUT drop кадр виден до INPUT, но UDP-приложение его не получает. Связанный port-forward увеличил счётчик сгенерированного `auto_wan_udp` на 1; ответ сохранил tuple `10.212.2.1:19091`. Несвязанный DNAT добавлен отдельной лабораторной NAT-таблицей **без** FORWARD-разрешения. Post-preauth observer подтвердил перевод WAN назначения и проход выбранного LAN DNAT через исключение preauth (по 1 пакету); получатели payload не увидели. Таким образом, исключение DNAT не стало blanket-accept: обычный FORWARD продолжил блокировать эти новые UDP-потоки.

Это ограниченная проверка UDP INPUT/DNAT без настоящего перехвата, containment или sing-box; не проверены hairpin NAT, established TCP, все интерфейсы и совместимость с будущим TProxy hook. Probe завершился exit 0, cleanup подтвердил удаление namespace и отсутствие тестовых nft-таблиц в основном пространстве VM. VM выключена и возвращена к исходному snapshot.

## Проверки и оставшиеся gates

- Backend: **297 passed**, включая сохранение golden-output действующего firewall. `git diff --check` прошёл.
- Синтаксис FIB и все использованные сгенерированные политики прошли `nft -c` на VM; исправленный UDP probe завершился exit 0.
- Cleanup проверил отсутствие тестовых namespace и preauth-таблиц в основном пространстве VM; затем VM выключена и возвращена к `pre-singbox-20261002`.

Ещё не доказаны: preauth вместе с настоящим TCP/UDP TProxy, включая сохранение local/DNAT исключений при перехвате; policy routing/марки/ECMP; фактический proxy egress; уже установленные TCP/UDP; DNS/Unbound; IPv6 WAN guard; crash/interception loss; apply/rollback/boot restore. Включение по-прежнему отвергается `tproxy.not_available`.
