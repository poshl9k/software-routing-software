# DNS OUTPUT: отдельные UID двух Unbound в одноразовой VM

## Объём

Продолжение `docs/lab-20-tproxy-two-unbound-dns-cache.md`. Два Unbound запущены внутри изолированного router namespace под **разными numeric UID**: выбранный `29092`, обычный `29093`. `setpriv` сбрасывает группы; в `/proc/<pid>/status` проверены real/effective/saved UID и нулевые `CapEff`/`CapAmb`. Для привязки `:53` без capabilities только в router namespace выставлен `net.ipv4.ip_unprivileged_port_start=0`; root namespace гостя и хост не изменялись.

Новый **offline-only** `generate_tproxy_dns_output_guard()` компилирует отдельную nft OUTPUT-таблицу для UID выбранного resolver. До общего drop разрешены: ответы его DNS listener (source IP выбранного интерфейса, `oifname` того же интерфейса, source port `53`); запросы к fake loopback DNS-stub `127.0.0.1:15353`; запросы к точным IPv4-адресам **явных** Unbound forwards на `:53`. Глобальный upstream ordinary resolver в исключения не входит. Disabled intent удаляет только таблицу. Генератор проверяет не-root UID и отвергает IPv6 explicit upstream, пока нет соответствующей политики. Он не подключён к bundle/apply/boot; `tproxy.not_available` остаётся.

Использован реальный Unbound 1.26.1-0+deb13u1 во временной VM, но DNS-stub — **тестовый ответчик, не sing-box**. Ordinary default upstream размещён на `198.18.0.3:53`, явный forward — на `198.18.0.2:53`. Это позволяет проверить: прямой выход выбранного UID к ordinary upstream запрещён, а разрешённый явный forward выбранного UID не ломается. Перед применением всех правил прошёл `nft -c` в namespace; оба Unbound-конфига прошли `unbound-checkconf`.

## Пакетные результаты

Финальный VM-прогон завершился `guest exit: 0`. Проверены UDP **и** TCP:

- Локальная запись у двух клиентов возвращает `192.0.2.77`; счётчик разрешённых DNS-ответов выбранного UID растёт.
- Одинаковое неподходящее имя направляется выбранным Unbound на stub (`203.0.113.8`, счётчик OUTPUT-stub растёт), обычным — на ordinary origin (`203.0.113.7`). Повтор возвращается из отдельных кэшей без второго upstream-запроса.
- Явный forward обоих экземпляров достигает `198.18.0.2`; у выбранного растёт только счётчик разрешённого explicit-forward OUTPUT.
- Прямой DNS клиента к внешнему `:53` и перекрёстный доступ к чужому listener останавливаются независимыми ingress/INPUT guards.
- **Один и тот же destination `198.18.0.3:53`:** отдельный процесс под UID `29092` получил timeout, OUTPUT-drop counter вырос, тестовый origin имени не получил; процесс под UID `29093` получил корректный DNS-ответ по тому же адресу/порту, а счётчик выбранного UID больше не вырос. Использовалось свежее имя, чтобы кэш не замаскировал OUTPUT.

Первый запуск с UID выявил, что без разрешения **ответов выбранного resolver клиенту** OUTPUT guard блокировал даже локальную запись. Добавлено узкое правило по UID, исходному адресу/порту и выходному интерфейсу; после исправления три последовательных пакетных прогона прошли. После опыта namespaces, nft-таблиц и временных конфигов нет; VM откатана к `pre-singbox-20261002` и выключена.

## Граница вывода

`meta skuid` различает наблюдаемые сокеты двух непривилегированных процессов в этой VM; это **не** доказательство привязки каждого исходящего запроса к политике исходного клиента. Разрешённый explicit-forward destination остаётся потенциальным путём для любого запроса процесса под выбранным UID к тому же IP/порту: OUTPUT не видит QNAME. Root или процесс, который может сменить UID/подменить nft, вне модели этой пробы. Не проверены IPv6, фрагменты, нестандартные DNS-порты, реальные процессы sing-box, отказ stub/Unbound, автоматическая установка защиты до запуска процессов и согласованный rollback/reboot. Нельзя активировать TProxy по этому результату.
