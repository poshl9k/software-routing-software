# Граница источника DNS перед интеграцией TProxy

**Статус:** анализ действующего кода и генераторов, не пакетная проверка DNS при включённом TProxy. Публичное включение отвергается `tproxy.not_available`.

## Проверенный контрпример к прямому использованию общего Unbound

`backend/src/vs_router/generators/unbound.py:6–29` строит один Unbound-конфиг по `configuration.dns`: общие `interface`, `access-control`, `local-data` и `forward-zone`. Если `dns.upstreams` задан, появляется глобальный `forward-zone` с `name: "."`. Генератор не читает `configuration.tproxy`, источник отдельного запроса или runtime-готовность sing-box. `backend/src/vs_router/generators/nftables.py:180–234` пока выдаёт только экспериментальную предварительную авторизацию транзита; отдельной авторизации DNS-выхода Unbound она не создаёт.

Host-free проверка через реальный `ConfigurationVersion` (искусственный `model_copy(enabled=True)` **только внутри offline эксперимента**) при LAN DNS listener `10.212.1.1`, общем upstream `198.18.0.2` и выбранном TProxy ingress `lan0` вернула:

```text
global_forward= True
unbound_same_with_intent_change= True
ordinary_firewall_same_with_intent_change= True
public_gate_rejects= ValueError tproxy.not_available
```

Значит, простое включение TProxy в намерении **не превращает** общий resolver в источник-ориентированный DNS-контур. Запросы выбранного и невыбранного клиентов к одному Unbound listener попадают в один конфиг/кэш; после передачи запроса Unbound его OUTPUT — трафик процесса роутера, не исходного клиента. UID-scoped OUTPUT drop для sing-box не авторизует и не классифицирует Unbound. Отдельная VM-проба при TProxy off (`docs/lab-14-tproxy-dns-off-baseline.md`) показывает, что явный forward выходит с WAN-адреса роутера, а Unbound меняет upstream DNS ID и отвечает из кэша. Она **не** доказывает, что DNS выбранного источника при TProxy on закрыт от прямого WAN.

## Обязательный дизайн перед включением

1. Определить, где **до общего кэша/forward** различается выбранный источник, как локальные записи и явные forwards сохраняют приоритет и куда идут оставшиеся запросы при готовом движке. Если запрос попадает в общий Unbound без метки/изоляции, после кэша нельзя восстановить его источник по socket UID или upstream DNS ID.
2. Сделать независимую от процесса блокировку внешнего DNS для выбранных источников при отказе, не ломая локальное управление, явные Unbound forwards и запросы самого роутера. Нельзя просто запретить весь router OUTPUT `:53`: это нарушит исключения и затронет невыбранных клиентов.
3. Проверять отдельными пакетными сценариями: локальная запись, explicit forward, unmatched query (выбранный и невыбранный клиент с одинаковым именем), повтор через кэш, UDP/TCP, прямой внешний DNS, отказ процесса до/после установления потока, восстановление и explicit off. Успешный клиентский TCP-запрос не означает upstream TCP-запрос.

Этот аудит не добавляет DNS planner, nft-правила или путь вокруг существующего gate. Для пробы с настоящим Unbound на VM нужен установленный пакет: snapshot `pre-singbox-20261002` его не содержит; зависимость не устанавливалась в рамках этого шага.
