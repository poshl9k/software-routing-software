# UX/UI-логика Keenetic — сводка для переноса в vs-router

Выжимка из семи референсов (`01`–`07`). Каждый пункт выведен из наблюдаемых экранов
или явного текста документации; ссылки на детали — в самих разделах.
Обозначения: **[О]** — подтверждено скриншотом/статьёй, **[слабо]** — вывод по фрагменту,
**[не подтв.]** — в источниках нет, не выдавать за паттерн Keenetic.

## 1. Каркас: задача → список → форма в отдельном окне

**[О]** Keenetic почти нигде не редактирует ячейку таблицы по месту. Правило firewall,
правило port forward, DNS-сервер, пользователь, карточка DHCP-клиента — всё открывается
отдельным окном-формой с явными «Сохранить» / «Отменить» (`05`, `03`, `04`, `07`).
**[О]** Открытие карточки — клик по строке или карандаш, не инлайн-поля.
**[О]** Плитка/строка в списке остаётся компактной: тумблер, имя, состояние, иконка, chevron/карандаш.

→ Наш аналог: `DataTable` (только чтение) + `EditorShell`/`EditorFooter` с `useDraftEditor`.
Инлайн-редактирование допустимо лишь там, где у нас это уже принятая норма, и точечно.

## 2. Список правил: выбор ≠ включение ≠ порядок

**[О]** В таблице firewall независимо живут три вещи: чекбокс выделения строки, тумблер
«включено» и drag-маркер порядка. Порядок сверху вниз = порядок проверки, permit выше deny;
позицию можно задать селектом при создании («Конец», «Приоритет») (`05`).
**[О]** Кнопок ↑/↓ на изученных кадрах нет — перестановка перетаскиванием или приоритетом.
**[О]** Групповые операции: «Удалить выделенные», «Переместить в …», «Копировать в …» с выбором
целевого интерфейса (`05`).
**[О]** Приоритеты подключений: порядок строк тянут за ручку, верхнее — основное; назначение
политики клиентам — тоже перетаскиванием либо выпадающим списком (`02`, `06`).

→ Наш аналог: порядок правил — явный признак (число или drag), выделение и включение —
разные контролы; `DeleteButton` для одиночного удаления, массовые действия — отдельно.

## 3. Статус — текст + индикатор + действие, и он не бинарный

**[О]** Различаются: «Работает», «Отключено», «Не настроено», «Подключено», «ПОДКЛЮЧЕНО»,
«Проверьте кабель», «Резервное соединение», «Загрузка», «Ошибка (сообщение)». Цвет всегда
сопровождается текстом (`01`, `02`, `06`).
**[О]** Отдельно различаются «не установлен компонент», «установлен, но не настроен»,
«настроен, но выключен», «работает» (`06`).
**[О]** У проблемного состояния рядом стоит исправляющее действие («Включить», «Подключить»,
«Подтвердить права», «Зарегистрировать»), а не только красный цвет (`01`, `03`).
**[О]** Служба в обзоре — строка: тумблер + имя + текстовое состояние + описание, описание
ведёт в настройку (`01`).

→ Наш аналог: `Badge` + `InlineStatus` + `ServiceStatusHeader`; состояния описывать через
`ApplyStatusRail`-подобную модель (`draft` / `pending` / `applied` / `error` / `unknown`),
а не сводить к вкл/выкл. Переключатель показывать только если backend реально применяет.

## 4. Сводка → деталь, действия ведут к разделу

**[О]** Обзорные карточки короткие; заголовки и описания карточек — сами по себе ссылки на
детальные страницы («Монитор Wi-Fi», «Монитор трафика», настройка службы) (`01`).
**[О]** Метрики разделены по назначению: мини-график и totals на карточке, Топ-5 на обзоре,
полный монитор — на отдельной странице с выбором режима и интервала (`01`).
**[слабо]** График скорости за 3 минуты — не пропускная способность канала; Keenetic это
прямо оговаривает.

→ Наш аналог: `Card` с `to=…`, `StatTile` для компактных метрик, `StatusHero` для главного
состояния. Не показывать метрику без реальной телеметрии — сейчас в `Dashboard.tsx` так и сделано.

## 5. Пустое состояние — всегда текст + действие

**[О]** «Нет правил.»; «Ни одного правила еще не создано. Добавить правило» (кликабельно);
«Нет клиентов» / «Нет подключений» + кнопка добавления рядом (`05`, `06`).
**[слабо]** Формулировки пустого состояния обзора без Интернета в источниках нет.

→ Наш аналог: `EmptyState` + первичное действие, `InfoNote` для пояснений.

## 6. Навигация и шапка

**[О]** Левый компактный rail с гамбургером (внизу слева на ПК, вверху слева на мобильном);
группы меню по задачам («Статус», «Интернет», «Мои сети и Wi-Fi», «Сетевые правила»,
«Управление»); состав зависит от модели и установленных компонентов (`01`).
**[О]** Поиск справа вверху: результаты отдельно по веб-конфигуратору и отдельно по базе
знаний; у отдельных полей — значок контекстной помощи (`01`).
**[О]** Переключение языка — в шапке и на странице входа; доступны только установленные
языковые компоненты (`01`).
**[не подтв.]** Хлебные крошки, сохранение scroll, анимации меню как паттерн Keenetic — не
подтверждены. Наши breadcrumbs проектируем по своей иерархии, не ссылаясь на Keenetic.

→ Наш аналог: текущая группировка в `App.tsx` уже совпадает по духу с Keenetic.
Наш поиск по разделам (`TextField` в шапке и drawer) — правильная линия, но сейчас фильтрует
только пункты меню.

## 7. Раскрытие «дополнительно»

**[О]** Второстепенное скрыто: «Показать дополнительные настройки» (MTU для PPPoE/PPTP/L2TP),
раскрытие DHCP-параметров (видимы только IP роутера и режим), «Показать настройки» у ping,
раскрытие VLAN внутри формы Ethernet (`02`, `03`, `07`).

→ Наш аналог: `ExpertDisclosure`; ключевое поле оставлять видимым до раскрытия.

## 8. Опасные и необратимые действия отделены от обычного сохранения

**[О]** Безопасный режим настройки: держит живую, но **несохранённую** конфигурацию, показывает
видимый счётчик и требует **двух** подтверждений («Сохранить» и «Отменить») (`07`).
**[О]** Заводской сброс требует буквального ввода `RESET` (`07`).
**[О]** Перед опасной сменой роли порта статья советует сохранить `startup-config.txt` (`02`).

→ Это прямой ориентир для нашей «безопасной настройки» (`ApplyStatusRail`, `ConfirmDialog`):
подтверждение отката/подтверждения — отдельное действие с видимым таймером, а не тот же
клик, что «Сохранить». Наш текущий `ApplyTopButton` с таймером `mm:ss` этому соответствует.

## 9. Переиспользуемые объекты вместо плоских таблиц

**[О]** DNS: сначала создаётся **список** доменов, потом **правило** на этот список; в таблице
списка — счётчики доменов/IPv4/IPv6, в таблице правил — выбранный список и путь (`04`).
**[О]** Политики: политика → назначение клиентам/сегментам с перетаскиванием (`02`, `06`).
**[О]** Таблица firewall — это правило на интерфейс, а не глобальный список (`05`).

→ Наш аналог: алиасы (список) → правила firewall/NAT (ссылаются на алиас); пресеты сервисов →
правила TProxy. Держать это разделение в UI явным: «объект» и «правило» — разные экраны.

## 10. Расписания — один переиспользуемый редактор

**[О]** Селект «Работает постоянно» / «Добавить расписание»; редактор — имя + текущие часы +
сетка Пн–Вс × 0–24; в форме существующее расписание показывается мини-сеткой с
«Редактировать расписание»; применимо к firewall, port forward, подключениям, клиентам (`05`, `02`, `03`).

→ У нас расписаний пока нет; если появятся (обновление списков TProxy) — один общий редактор,
а не поле cron-строкой.

## 11. Форма меняется по выбранному типу

**[О]** Селект типа (протокол / тип адреса / тип DNS-сервера / пресет сервиса) меняет состав
полей; для port forward — радиовыбор «Одиночный порт» / «Диапазон портов» и пара
«Открыть порт» ↔ «Направлять на порт»; пресет DMZ отключает поля отдельных портов (`05`, `04`).
**[О]** Ошибка обязательного поля — красная рамка и «Заполните это поле»; «Сохранить» неактивно
на пустой форме (`04`).

→ Наш аналог: `Field` (`valid`/`hint`, без `error`/`helperText`), `Select`, условный рендер
полей по типу, кнопка сохранения блокируется по `valid` из `useDraftEditor`.

## 12. Честность производных объектов и отложенных эффектов

**[О]** Keenetic **не** показывает отдельную строку «авто-правило firewall» для port forward,
хотя port forward сам открывает нужное разрешение; авто-NAT некоторых сервисов вообще не видны
в веб-конфигураторе (`05`).
**[О]** Изменение правил firewall не пересматривает уже установленную сессию — сработает после
разрыва/истечения (`05`).
**[О]** IPIP/GRE/EoIP — stateless: настройка не доказывает, что трафик идёт (`06`).

→ Не рисовать в UI связи и «авто»-объекты, которых нет в нашей модели; не показывать
«применено» там, где эффект отложен (у нас — только после цикла apply/confirm).

## 13. Мастер первого запуска

**[О]** Приветствие → шаги с «Далее» → «Завершить», проверка подключения по завершении;
при заводских настройках запускается автоматически (`01`).

→ Наш аналог: `Onboarding` + `WizardProgress`. Держать тот же каркас: приветствие, шаги,
проверка результата в конце.

## Что НЕ копировать

- **CLI-only функции как веб-контролы.** TTL (`system 3.1+`), DHCP option 121/15 задаются
  только через CLI — веб-формы для них в Keenetic нет (`02`, `03`). Не рисовать у нас
  переключатель, которого нет в нашем backend.
- **Аппаратное.** Wi-Fi-монитор, спектр-анализатор, USB-диски, телефония, Wi-Fi-система —
  у нас нет этого железа и соответствующих измерений (`01`).
- **Облачные статусы.** Палитра и статусы Netcraze RMM (`35338`) — другой продукт, не
  контракт локальной панели (`01`).
- **Неподтверждённые детали.** Хлебные крошки, анимация меню, тексты пустых состояний обзора,
  поле поиска по клиентам, кнопки сохранения в обрезанных кадрах форм — по источникам не
  установлены; не выдавать за паттерн Keenetic (`01`, `03`, `05`).
- **Цветовые конвенции как догму.** Наблюдаемы зелёный/синий/серый + текст; единой
  документированной палитры состояний локальной панели в источниках нет (`01`).
