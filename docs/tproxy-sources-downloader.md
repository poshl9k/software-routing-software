# Источники списков: downloader подписок и rule-set (agent)

**Статус:** механизм реализован в агенте (оффлайн/тестово), **не** подключён к
конфигурационному gate и не активирует перехват. Публичный `tproxy.not_available`
остаётся закрытым; `tproxy.enabled=True` по-прежнему отвергается
`validators.validate_configuration`. Этот модуль не пишет в продуктовый bundle и
не меняет пути `apply`/`boot_restore`. Реального сетевого фетча в тестах нет —
весь транспорт мокирован.

Основание: `docs/sing-box-tproxy-plan.md` §«Источники списков и обновления»
(allowlist для встроенных, отдельное разрешение и защита от
перенаправления/DNS-rebinding для пользовательских, лимит размера, таймаут,
проверка формата, контроль TLS, атомарная активация с откатом, история версий).

## Что реализовано

| Слой | Файл | Суть |
| --- | --- | --- |
| Агент-модуль | `backend/src/vs_router/agent/downloader.py` | SSRF-защита, фетч с редиректами, лимиты, проверка формата, атомарная активация, история |
| RPC-контракт | `agent/rpc.py` | типизированные методы `update_source`, `source_status` |
| Проводка агента | `agent/daemon.py` | handlers `update_source`/`source_status`; updater инъектируемый |
| Тесты | `backend/tests/test_downloader.py` | 60 тестов на мокированном транспорте (без сети) |

## Схема защиты от SSRF

Поток одного фетча (`downloader.fetch`), по каждому hop'у редиректа:

1. **Схема.** Разрешён только `https`. `http` отвергается
   (`download.https_required`) — TLS обязателен для внешних источников.
   Исключение включается только явным `allow_plaintext=True` **и** хостом из
   allowlist встроенного источника; сейчас таких записей нет, то есть внешний
   plaintext фактически запрещён.
2. **Хост.** Имя проверяется регуляркой (или принимается IP-литерал);
   пустой/битый хост → `download.invalid_host`.
3. **Авторизация хоста.**
   * Встроенный источник: хост обязан входить в `BuiltinSource.hosts`, иначе
     `download.host_not_allowed`. URL встроенного источника берётся из реестра,
     а не из запроса; расхождение → `download.builtin_url_mismatch`.
   * Пользовательский источник: обязателен явный флаг `authorized=True`
     (`download.user_authorization_required`), а допустимый хост — ровно тот,
     что в URL.
4. **Резолв и проверка адресов.** `resolve_public()` резолвит хост (или берёт
   IP-литерал) и отвергает весь хост, если **любой** адрес запрещён:
   loopback, private/RFC1918, link-local (`169.254.169.254` — cloud metadata),
   multicast, reserved, unspecified, CGNAT `100.64/10`, IPv6 ULA/site-local и
   IPv4-mapped формы любого из перечисленных (`download.forbidden_address`).
   Смешанный ответ (публичный + внутренний ADR) отвергается целиком.
5. **Пиннинг адреса (DNS-rebinding).** Хост резолвится **ровно один раз на
   hop**; транспорт получает уже проверенный IP (`connect_ip`) и подключается к
   нему, а SNI/`Host` оставляет исходное имя. Между проверкой и соединением
   подмена DNS-ответа невозможна.
6. **Редиректы.** Следуются вручную, максимум `MAX_REDIRECTS=5`. Каждый late
   hop заново проходит шаги 1–5, поэтому редирект на неразрешённый хост
   (`download.host_not_authorized` / `download.host_not_allowed`) или на
   внутренний адрес (`download.forbidden_address`) отвергается.

Ограничение честно: политика защищает агент от превращения фетча в сканер
внутренней сети. Она **не** заменяет проверку прав на переупаковку сторонних
списков и не гарантирует доверие к содержимому — источник может быть внешне
валиден и вредоносен по данным.

## Лимиты

| Лимит | Значение | Где |
| --- | --- | --- |
| Размер тела | `max_bytes` (по умолчанию 5 МБ; RPC 1 КБ..50 МБ) | транспорт читает `max_bytes+1`, затем повторная проверка `len(body)` → `download.size_exceeded` |
| Таймаут | `timeout` (по умолчанию 20 c; RPC 1..120 c) | транспорт; `socket.timeout`/`TimeoutError` → `download.timeout` |
| Число редиректов | 5 | `download.too_many_redirects` |
| Число адресов в резолве | 16 | `download.too_many_addresses` |
| История | 200 записей | `HISTORY_LIMIT` |

Ошибки транспорта (`OSError`, `ssl.SSLError`) → `download.transport_failed`;
отказ/не-200 → `download.http_error`; не-UTF-8 → `download.decode_failed`.

## Проверка формата

`validate_content(content, declared)` возвращает эффективный формат или падает
`download.invalid_format` (`download.format_unknown`,
`download.format_unsupported`). Поддержаны: `sing-box` (JSON с `outbounds`),
`rule-set` (JSON с `version` и `rules`), `clash` (`proxies:`), `v2ray`/`base64`
(BASE64 со схемой), `json`, `text` (домены/IP/CIDR с префиксами
`domain:`/`full:`/`keyword:`/`regexp:`). `auto` пробует их в порядке
специфичности. `.srs` распознаётся как реальный формат, но **не активируется**
(см. ниже) → `download.format_unsupported`.

## Атомарная активация с откатом и историей

`SourceUpdater.update()`: `build_spec` → `fetch` → `validate_content` →
(инъектируемый `config_validator` собирает минимальный sing-box-документ с новым
набором; отказ → `download.config_invalid`) → `SourceStore.activate`:

1. содержимое пишется в версионный путь `versions/<name>/<sha256>` и во
   временный `staging/<name>`;
2. `atomic_move` заменяет `active/<name>.<kind>`;
3. при любой ошибке записи/перемещения предыдущий активный файл
   восстанавливается (или удаляется, если его не было) — рабочего набора не
   остаётся в полузаписанном состоянии.

Каждая попытка (успех и неудача) добавляется в `history.json` (`name`, `kind`,
`status`, `url`, `format`, `sha256`, `size`, `at`, `error`). `status()`
возвращает историю. Внешние сбои оборачиваются в `download.activation_failed`.

Ошибки типизированы: `DownloadError` наследует `ApplyError`, поэтому RPC-дисптч
отдаёт их как упорядоченный код ошибки без произвольного shell и без новых
веток исполнения.

## RPC (типизированный whitelist)

* `update_source` — ручное обновление. Поля: `name`, `url`, `kind`
  (`subscription`/`rule_set`), `format`, `authorized` (bool, явное разрешение
  для пользовательского источника), `max_bytes`, `timeout`. Передаются только
  данные; URL никогда не попадает в shell, политику allowlist/SSRF агент
  применяет сам (`build_spec`).
* `source_status` — без параметров, возвращает историю обновлений.

Оба метода добавлены в `Method`/`PARAMS`; handlers создаются в
`make_handlers(engine, database, updater=None)` и лениво инстанцируют
`SourceUpdater`, если не передан. Никакого произвольного shell/параметров
командной строки не появилось.

## Что НЕ реализовано (сознательно вне объёма)

* **Планировщик по расписанию** (`TProxyUpdateSchedule`: interval/window,
  backoff/джиттер, условные HTTP-запросы, «не догонять» после простоя, показ
  следующего времени) — только контракт в схеме; исполнителя нет.
* **UI** — раздел «Маршрутизация» и ручной запуск из панели не подключены;
  read-only runtime API для web-процесса отсутствует.
* **Каталог пресетов** — `BUILTIN_SOURCES` пуст. Механизм allowlist
  реализован и тестируется на инъектируемом реестре; наполнение реальными
  источниками (SagerNet/v2fly/RockBlack/hoaxisr/geoip-geosite) требует
  провенанса, лицензии и версии/хеша на запись и не сделано.
* **Бинарные `.srs`** — нет байт-точного хранилища и закреплённого компилятора;
  запрос `.srs` падает закрыто.
* **Реальный `sing-box check`** — `config_validator` инъектируемый; бинарник
  не выбран/не закреплён (ADR-0005), поэтому живой проверки собранного конфига
  нет. В тестах используется фейковый валидатор.
* **Сериализация активации с apply/rollback** — downloader не сериализует свою
  активацию с общим циклом применения (это требование этапа 2 плана).
* **Живая сетевая проверка** — весь транспорт мокирован; проверка на
  одноразовой VM не выполнялась.
* **Открытие `tproxy.not_available`** — gate не тронут.
