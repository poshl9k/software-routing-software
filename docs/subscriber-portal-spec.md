# Спека: Портал абонента (`vs-panel`)

**Status:** MVP-объём согласован (гриль 2026-10-23); ADR-0032, ADR-0033 — предложены.

Решения о том, *почему* так — в ADR-0032 (архитектура публикации) и ADR-0033
(учётная запись, приглашение, применение). Здесь — объём и поведение.

## Позиционирование

Кабинет абонента `vs-panel`: доступ **только по приглашению**. Учётные записи
создаёт администратор панели (или оператор с доступом к панели). Это не
публичный сервис с саморегистрацией.

## Учётная запись и доступ (ADR-0033)

- Учётка = существующий `Subscriber` из конфигурации; логин — имя абонента.
  Пароль/email/тариф/срок/статус — в БД портала, вне конфигурации.
- **Дефолт:** одноразовая ссылка-приглашение `portal.<имя>/invite/<токен>` →
  абонент задаёт пароль (email опционально) → токен сгорает. Приглашение можно
  отозвать до активации; у токена есть срок действия.
- **Опция «активировать»:** галка при создании — ссылка содержит готовый пароль.
  Выбор и риск администратора, в UI маркируется предупреждением о перехвате.
- **Сброс пароля в MVP — через админа** (новая инвайт-ссылка; механика та же).
- Сессии портала отдельны от админских; rate limit на login, аудит действий
  абонента — обязательны (публичная поверхность).

## Публикация (ADR-0032)

- Отдельный процесс на VPS, без доступа к админ-API и агентному RPC.
- MVP: DNS вручную; резервное имя `portal.<ip>.nip.io`, затем
  `portal.<свой домен>` (модель двух имён — по образцу ADR-0025).
- После MVP: DNS-API (первый адаптер Cloudflare) + wildcard DNS-01 на основной
  домен; работает одинаково для основного домена и портала.

## Устройства (пиры абонента)

Абонент сам, без подтверждения админа:

- **создаёт** устройство: задаёт только метку («телефон», «ноутбук»); ключи,
  адрес (/32 из сети туннеля), preshared key, DNS и выход — система по
  настройкам админа. Выбор туннеля скрывается, пока он один;
- **удаляет** устройство — безвозвратно (ключи не восстановить), с диалогом
  подтверждения; слот тарифа освобождается;
- **деактивирует/активирует** устройство — временно, ключи и адрес сохраняются.

Все операции — через штатный контур применения (черновик → применение),
запускаемый системой; при занятом цикле применения операция ждёт в очереди со
статусом «ожидает применения». Админ видит результат постфактум.

Экспорт конфига устройства — `.conf`, QR, Amnezia `vpn://` (ADR-0022);
генераторы переиспользуются из панели.

## Тариф и подписка

- **Тариф** создаёт админ: имя, лимит устройств, срок подписки (дни), поле цены
  (заложено, в MVP не используется). У абонента один тариф.
- **Смена тарифа — только админ.** У абонента в MVP кнопки смены нет.
- **Понижение тарифа:** существующие устройства живут; абонент не может
  создавать новые, пока не влезает в лимит — уведомление об этом в кабинете
  («на этом тарифе разрешено N устройств…»).
- **Истечение подписки:** авто-блокировка — пиры абонента снимаются с
  применённой конфигурации тем же системным механизмом; абонент видит статус
  «подписка истекла» и устройства как «отключены». Продление возвращает **те
  же** устройства (ключи и адреса сохраняются).
- **Предупреждение об истечении в MVP — в кабинете** (плашка «истекает через
  N дней» / «истекла»).

## Статусы и метрика

- MVP: факт применения устройства + время последнего handshake
  («недавно / N дней назад»). Источник — агент (`wg show` dump).
- Следующая итерация: счётчики трафика (RX/TX, фоновый сборщик в БД).
- После MVP: квоты/ограничения скорости (enforcement через nftables).

## Оплата

В MVP отсутствует. В модели данных заложены цена тарифа и статус подписки;
способы оплаты — отдельное решение после MVP.

## После MVP (отложено сознательно)

1. Email-самообслуживание (сброс пароля) и уведомления об истечении по email —
   один SMTP-контур на оба сценария; адаптеры мессенджеров (Telegram и т.п.)
   как дополнительные каналы.
2. DNS-API автоматизация (Cloudflare + wildcard DNS-01).
3. Выбор выхода/страны абонентом при создании устройства.
4. Счётчики трафика, затем квоты/скорости.
5. Способы оплаты.
6. 2FA (TOTP) — общий график с панелью.

## Приёмочные проверки MVP

1. Создание абонента админом → непринятое приглашение отзывается; принятое
   создаёт вход по логину+паролю; готовый пароль по галке «активировать» тоже
   работает.
2. Создание устройства абонентом при свободном цикле применения → устройство
   в применённой конфигурации, экспорт `.conf`/QR/Amnezia отдаётся.
3. Создание устройства при занятом применении → статус «ожидает применения»,
   применение завершается после освобождения цикла.
4. Превышение лимита тарифа → создание отклонено с человеческим текстом.
5. Понижение тарифа админом ниже текущего числа устройств → устройства живы,
   создание новых заблокировано с уведомлением в кабинете.
6. Истечение подписки → пиры сняты с применённой конфигурации без участия
   админа; продление возвращает те же устройства с теми же ключами/адресами.
7. Удаление и деактивация устройства абонентом → отражаются в применённой
   конфигурации; деактивация обратима, удаление нет.
8. Админ-API и агентный RPC недоступны с публичного имени портала.
9. Rate limit на login портала работает; действия абонента попадают в аудит.
