# ADR-0035: Мастер-портал (`vs_master`) — единая база абонентов, master→node через bridge

- Статус: предложен
- Дата: 2026-10-24
- Контекст: несколько работающих `vs-panel` VPS (rg1…rgN), каждый со своим публичным порталом абонентов и локальной портал-БД. rg1 свободен.

## Решение

### 1. Мастер — единственный источник правды об абонентах (вариант A)

Единая БД абонентов (`Account`, `Tariff`, `Subscription`, `Device`) живёт на **мастере** — отдельном VPS (rg1), отдельным процессом `vs_master` со своей БД и миграциями. Локальные публичные порталы нод закрываются (юнит остановлен, публикация снята; БД-файлы хранятся до успешной миграции, снос — отдельный шаг). Нода сохраняет админ-панель роутера и internal bridge; мастер не касается нод ничем, кроме bridge.

**Альтернатива (агрегатор над живыми локальными порталами) отвергнута**: два источника правды, распределённый каскад удаления, ручная синхронизация тарифов.

### 2. Фолбэк — постоянная read-only реплика на нодах, без режимов

На каждой ноде постоянно работает read-only реплика абонентских данных (снапшот мастер-БД): абонент видит свои устройства, QR и конфиги даже при недоступном мастере. Никаких авто-режимов «standalone»: запись возможна только через мастера, состояние «локальный write-режим» не существует в принципе — тем самым исключён split-brain при восстановлении мастера. Ручной failover (промоушен реплики в write) — будущая опция, не MVP.

**Альтернатива (авто-standalone при недоступности мастера) отвергнута**: ненадёжная детекция «мастер лежит» и split-brain при возврате мастера в момент аварии; второй полный кодовый путь, который никто не тестирует в мирное время.

### 3. Канал мастер→нода: HTTPS к internal bridge, bearer-токен с само-ротацией

Мастер ходит к нодам напрямую по HTTPS в bridge-эндпоинты (`state`/`device-op`/`expire`/`renew`) с долгоживущим bearer-токеном на пару (мастер, нода). Воркер DeviceOp (`process_pending`) переезжает в мастер и работает против удалённого bridge по `node_id` устройства.

Ротация токена автоматическая через `POST /internal/token-rotate` на ноде, аутентифицируемый **текущим** токеном (токен сам себе канал; идемпотентно: недошедший ответ распознаётся повтором со старым токеном — 200 «уже применено» либо 401 «уже отозван»). Онбординг ноды (первичная доставка токена) и экстренный ревок — ручные.

**Альтернативы**: pull-модель (агент ноды опрашивает мастера) — не нужна для публичных VPS; mTLS/короткоживущие JWT — избыточная PKI для внутренней администрации.

### 4. Идентичность абонента: tg id + суррогатный ID; имя — display-текст

`Account` в мастер-БД получает суррогатный уникальный ID (PK); **имя — только display-текст без требования уникальности**. Идентичность — Telegram ID (уникальный ключ). Это контрактное расхождение с текущей моделью (где имя фактически ключ); миграция учитывает. Display-имя берётся из TG (снапшот при регистрации, обновляется на `/start` — TG-имя юзер может сменить в любой момент).

### 5. Регистрация: открытая саморегистрация ботом ИЛИ админом; врата — подписка

Два параллельных пути создания `Account`: саморегистрация через TG-бота (без инвайтов, без вопросов юзеру) и ручное создание админом. Account без активной Subscription не даёт доступа: врата в сервис — наличие активной подписки, не регистрация. Уведомления об истечении подписки — и в портале, и в бота. Бот: long polling, токен в зашифрованных настройках мастер-БД; вход по одноразовой magic-ссылке со сроком жизни; управления устройствами из бота на MVP нет.

### 6. Распределение по загрузке: пиров/ёмкость, только при создании устройства

Метрика — число активных устройств против заданной администратором ёмкости ноды. Телеметрия — опрос мастером раз в ~30–60 с, кэш `last_seen`/`active_peers`; состояния ноды `ok` / `stale` / `down`. Автораспределение — только при создании устройства, среди нод в состоянии `ok`; админ может переназначить вручную. **Автомиграций устройств между нодами нет**: устройство прикреплено к ноде до ручного переезда. Нода скрыта от юзера: портал не показывает и не просит выбирать ноду (адрес ноды в конфиге устройства скрыть нельзя, но UI решений о ноде не строит).

**Альтернативы**: трафик/CPU как метрика (нет счётчиков / CPU VPS врёт), балансировка в реальном времени (недоступная нода блокирует решение), авто-миграции (юзер переимпортирует конфиг без предупреждения).

### 7. Модель: нода — атрибут Device, подписка — атрибут абонента

`Device.node_id` определяет ноду исполнения device-op. `Subscription` принадлежит абоненту и может покрывать устройства на разных нодах. Истечение/продление — семантика ADR-0033, исполняет воркер мастера.

### 8. Топология мастера: только оркестрация, отдельный поддомен + reserve

Мастер (rg1) не несёт нодной роли: портал + БД + бот. Публикация — отдельный поддомен (не `rg1.poshl9k.ru` — адрес не зависит от машины) + постоянное reserve-имя `<ip>.nip.io`. Caddy мастера — standalone, вне apply-циклов нод.

### 9. Код: отдельный пакет `vs_master`, отдельный админский фронтенд

`vs_master` — новый пакет в том же репозитории: свой процесс, БД, миграции; модели переиспользуются импортом из `vs_portal`/`vs_router` где совпадают, расходящиеся — свои. Профиль мастера — отдельная строка `MODULE_PROFILES`; footprint отражается в ADR-0021. Админский UI — отдельное мини-приложение `frontend-master/` (ноды, абоненты, настройки), по образцу `frontend-portal/`.

### 10. Миграция существующих абонентов — в составе онбординга ноды

Онбординг ноды = сервисный токен + разовый перенос её локальной портал-БД в мастер (Device получает `node_id`) + задание ёмкости. Пиры в конфигах нод не трогаются — мастер узнаёт о них через bridge.

### 11. Бэкапы

`sqlite3 .backup` по systemd timer (WAL) → последний дамп на каждую ноду; pull со станции по cron; ежедневно — в личный чат администратора через бота (`sendDocument`, предпочтительно после `age`-шифрования; ключ вне мастера и вне TG). Ключ шифрования приложения в дампы не входит, бэкапится отдельно. Разовая проверка восстановления на тест-машине.

## Этапы (согласованы)

1. **Мастер работает, ноды подключены**: `vs_master` (БД, Node-реестр, bridge-клиент, воркер DeviceOp), онбординг нод, caddy/поддомен, админка (ноды + абоненты), публичный портал, миграция старых абонентов, остановка локальных порталов.
2. **Регистрация**: TG-бот (саморегистрация, уведомления, magic-ссылки).
3. **Фолбэк**: read-only реплики на нодах.
4. **Операционка**: бэкапы по п. 11; авто-ротация токенов по расписанию (в этапе 1 — ручные кнопки).

## Реализация (этап 1, по мере попадания в код)

- Реализовано: пакет `vs_master` (модели/движок/миграции `alembic-master`), bearer-канал мастер→нода с идемпотентным `token-rotate` на ноде, воркер DeviceOp против удалённого bridge, телеметрия (`/internal/master/state`), разовая миграция локальной портал-БД ноды в мастер с перешифровкой секретов, приложение и админ-API мастера (сессии, ноды с одноразовым онбординг-токеном, тарифы, абоненты, подписки), скелафр и админские экраны `frontend-master/`.
- Контракт `token-rotate` зафиксирован: аутентификация текущим токеном; повтор недошедшей ротации старым токеном — 200 «уже применено» либо 403 «отозван»; предыдущее поколение живёт до подтверждения мастером.
- Не реализовано (открытый gap): node bridge резолвит устройство по таблице `portal_devices` — в целевой схеме portal-процесс ноды остановлен; нужен key-material resolution на ноде. Мастер уже шлёт материал ключей.
- Не реализовано: публичный портал абонента мастера и онбординг нод (в работе), caddy/поддомен, остановка локальных порталов.

## Что это НЕ решает

- Оплата и самосмена тарифа абонентом — после MVP.
- Автоперебалансировка и авто-failover мастера — не делаются сознательно.
- Netmaker/mesh-сеть между нодами — отвергнута: мастер→нода достаточно обычных HTTPS-вызовов; mesh добавляет центр отказа без решаемой им проблемы.
- IPv6-аспекты распределения и полная i18n — вне этого решения.
