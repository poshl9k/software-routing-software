# ADR-0026: Профиль продукта — явный маркер, сверяемый с возможностями хоста

**Status:** предложен

**Date:** 2026-10-16

**Deciders:** пользователь, Hermes

## Context

ADR-0018 требует, чтобы профиль продукта был **зафиксирован при установке
неизменяемым маркером** и проверялся при каждом применении. Пока этого нет: в
документе конфигурации поля `profile` не существует.

Фактически разделение уже пошло другим путём. Реализован пункт ADR-0021 про Kea:
набор **фаз** применения стал свойством хоста — `apply.host_files()` выкидывает
фазу, движок которой на хосте отсутствует (`PHASE_TOOLS`), конфигурация с
заявленными `dhcp_subnets` на таком хосте отвергается `kea.unavailable`, а
установщики пропускают блоки Kea. На живом VPS это работает: `kea-dhcp4` удалён,
раздел DHCP скрыт, все сервисы живы.

То есть «профиль» сегодня **выводится из возможностей** и нигде не заявлен. Это
проверяемо (единственная правда — что установлено), но не отвечает на вопросы
«какой это продукт» и «правильное ли на этой машине установлено»: хост с
удалённым Kea и хост-панель выглядят одинаково, а установка роутера без DHCP не
отличима от панели.

## Decision

Профиль — **явные данные, сверяемые с возможностями**; ни одно из двух не
отменяет другое:

1. **Маркер продукта** — `/etc/vs-router/profile` со значением `router` или
   `panel`, записывается **установщиком** (не панелью, из панели неизменяем):
   ISO/bootstrap-путь — `router`, онлайн-путь — `panel`.
2. **Поле документа** — `ConfigurationVersion.profile` (`router` по умолчанию,
   аддитивно, старые снапшоты читаются как `router`).
3. **Набор фаз остаётся свойством хоста** (`host_files()`). Объявленный профиль
   не даёт права запускать фазу, движка которой нет.
4. **Сверка при применении, до любых изменений системы:**
   - документ чужого профиля → `configuration.profile_mismatch`;
   - маркер `panel` на хосте с DHCP-сервером → `profile.capability_mismatch`;
   - маркер `router` на хосте без DHCP-сервера → `profile.capability_mismatch`;
   - **маркера нет — поведение прежнее** (решают возможности), чтобы уже
     работающие хосты, включая живой VPS, не начали падать.

## Rationale

- **Только маркер, как в ADR-0018 буквально.** Отвергнуто: он не мешает
  установить роутер и удалить с него Kea, а заявленное «правильно» на неподходящей
  машине опаснее, чем честный отказ.
- **Только возможности (как сейчас).** Отвергнуто: продукт остаётся неназванным,
  а ошибочная установка (роутер без DHCP, панель с DHCP) неотличима от штатной.
- **Запрещать запуск фазы, если маркер её не предполагает.** Отвергнуто: маркер —
  про продукт, а не про наличие бинарника; источник правды о фазах — сам хост.
- **Строгая проверка при отсутствии маркера.** Отвергнуто: сломало бы живой VPS
  (панельный по факту, без маркера) при первом же применении.

## Consequences

- Появляется `profile.py` (чтение/запись/сверка), поле в схеме и миграция,
  `GET /api/host/profile`, CLI для установщиков.
- Установщики обязаны записывать маркер; сбой записи — громкое предупреждение,
  но не срыв установки (отсутствие маркера деградирует к проверке возможностей).
- Живой VPS продолжает работать; перевод его в профиль `panel` (фаза E) — это
  запись маркера, а не перенос данных.
- Фазы B–D (границы модулей, артефакты, UI) строятся на одном допущении: профиль
  есть данные, возможности — факт, и оба проверяются.

Связанные: ADR-0018 (два продукта, одно ядро), ADR-0021 (границы владения),
ADR-0025 (публикация панели).
