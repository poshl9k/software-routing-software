# ADR-0022: Экспорт конфига в формате приложения Amnezia (`vpn://`)

**Status:** предложен

**Date:** 2026-10-16

**Deciders:** пользователь, Hermes

## Context

Наш экспорт клиентского конфига — это wg-quick `.conf`: `[Interface]` с
параметрами AWG 3 и `[Peer]`. Приложение Amnezia такой файл как *свой контейнер*
не импортирует: оно принимает собственный документ `vpn://`. Пользователь
прислал реальный экспорт приложения, и он вскрыт: это

```
vpn:// + base64url( uint32_be(uncompressed length) + zlib(JSON) )
```

с JSON-контейнером: `hostName`, `port`, `dns1`/`dns2`, `container:
"amnezia-awg2"`, `protocol_version: "3.1"` и блок протокола `awg` — параметры
обфускации **строками**, плюс `last_config` (строка JSON) с текстом `.conf`.
Внутри `.conf` DNS записан как `DNS = $PRIMARY_DNS, $SECONDARY_DNS` —
подстановки приложение берёт из `dns1`/`dns2` верхнего уровня. Именно поэтому
ранняя правка «добавить строку DNS в свой экспорт» была не тем вопросом.

## Decision

Панель умеет отдавать конфиг пира как документ Amnezia: генератор
`generators/amnezia.py` строит `vpn://`, эндпоинты
`GET /api/tunnels/{name}/peer/{peer}/amnezia` (текст) и `.../amnezia/qr` (PNG)
отдают его. Форма документа повторена по реальному экспорту (наборы ключей
верхнего уровня, `awg` и `last_config` совпадают ключ-в-ключ).

Значения, которых у панели нет, выбраны явно и документированы:

- **`dns1`/`dns2`** — параметры запроса; по умолчанию `dns1` = адрес туннеля
  (резолвер, достижимый внутри туннеля), `dns2` = `1.0.0.1`. Значение
  проверяется как IP; мусор отвергается, а не вписывается в конфиг.
- **`mtu`** — константа `1376` (наблюдаемое значение приложения) до появления
  поля MTU на туннеле.
- **Область** — только `awg`-сервер: для plain WireGuard контейнера мы не
  наблюдали, и генератор не выдумывает форму, а отказывает
  (`amnezia.role_unsupported`).

Адрес подсети контейнера берётся из сети **туннеля** (`/24`), адрес клиента —
из `/32` пира: приложение так и делает (`client_ip` /32 при `subnet_address`
сети).

**Endpoint.** На живом хосте (DHCP-аплинк) у туннеля не задан собственный
endpoint, и экспорт без него был бы шаблоном. Поэтому адрес берётся из записи
управления у агента (`hostname`, иначе `address` без маски) — но только когда
свой endpoint не задан: явно указанный адрес оператора всегда главен.
Это же правило применено к экспорту `.conf`/QR, у которых была та же дыра.

## Rationale

- **Оставить только `.conf`** отвергнуто: ровно ради импорта в приложение и
  задан вопрос, а `.conf` приложение как контейнер не берёт.
- **Угадать формат** отвергнуто: структура снята с живого экспорта, а не
  восстановлена по догадке.
- **Выдумать значения DNS/MTU** отвергнуто: они вынесены в параметры или
  константы с комментарием, а не зашиты как «правильные».

## Consequences

- Появляется второй формат экспорта того же пира; `.conf` остаётся, потому что
  его понимают `awg-quick` и другие клиенты.
- Ключ, который панель не сгенерировала (пир без собственного приватного ключа),
  экспортировать нельзя: приложение требует приватный ключ клиента, и генератор
  отказывает (`amnezia.peer_private_key_required`) вместо подстановки
  заполнителя.
- Проверено сопоставлением ключей с реальным экспортом и юнит/API-тестами;
  **живой импорт в приложение Amnezia не выполнялся** — это следующий шаг.
- Когда появится поле MTU/DNS на туннеле (см. ADR-0020 про DNS абонентов),
  константы заменяются полями без смены формата.

## Дополнение: `Tunnel.dns_servers` и `tunnel_dns()`

К моменту написания дополнения на vs-panel уже поднят DNS-резолвер внутри
серверного WireGuard-туннеля: `unbound` слушает адрес сервера в туннеле,
sing-box форвардит в него `hijack-dns`, nft-контур разрешает только источникам
из подсети туннеля. Экспорт Amnezia-контейнера при этом продолжал отдавать
публичный `1.0.0.1` — клиент получал работающий резолв через перехват, но
адресатом в документе стоял не наш резолвер.

Чтобы оба экспорта (`.conf` и `vpn://`) указывали один и тот же DNS, добавлено
явное поле `Tunnel.dns_servers: tuple[str, ...]` (server-only, ≤2 адресов,
fail-fast валидация: `tunnel.dns_server_invalid` / `tunnel.dns_server_limit` /
`tunnel.dns_servers_server_only`) и общая чистая функция `tunnel_dns()` в
`generators.wireguard`. Логика:

1. если задан `dns_servers` — он и есть `dns1`/`dns2` (по одному или двум);
2. иначе для server-туннеля — адрес сервера в туннеле (`tunnel_addresses(tunnel, configuration)[0]` без маски);
3. иначе — публичный fallback `1.0.0.1`/`1.1.1.1`, экспорт не падает.

В оба экспорта (`generate_wg_bundle` и `amnezia_uri`) ушла строка
`DNS = $PRIMARY_DNS, $SECONDARY_DNS` для `.conf` и `dns1`/`dns2` для `vpn://`,
вычисленные одной и той же функцией. UI-редактор серверного туннеля получил
поле «DNS для клиентов» (до двух IP через запятую; пусто — резолвер туннеля).

**Установщик ничего про это не знает**: ни `install.sh`, ни `online-install.sh`
не пишут в `dns` и `tunnels`. Серверный туннель создаётся через UI онбординга,
поскольку установщик не может знать публичный адрес оператора, выбор протокола
и обфускации AWG. Поведение «по умолчанию DNS = адрес серверного туннеля» —
естественный результат пустого `dns_servers`, оно работает без правок
установщика; явное поле нужно только тем, кто хочет переопределить.

Связан: ADR-0016 (параметры AWG 3), ADR-0020 (DNS абонентов).
