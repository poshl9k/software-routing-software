# ADR-0010: Канал онлайн-обновлений — зафиксированный release-манифест и tar-артефакт

**Статус:** принят
**Дата:** 2026-10-06
**Участники:** владелец продукта и Hermes Agent

## Контекст

ADR-0008 сделал ISO самодостаточным: он несёт `git archive` зафиксированного
коммита и распаковывает его локально, поэтому в `/opt/vs-router` **нет `.git`**.
ADR-0008 также обещал, что панель предложит онлайн-обновление до более нового
проверенного выпуска. Однако механизм получения исходников при обновлении
остался git-ориентированным: `update.sh --release <sha>` выполняет
`git fetch origin` и `git checkout --detach <sha>`. На дереве без репозитория
`fetch` невозможен — то есть обещанное обновление сейчас не работает, а
«обновление из ветки» прямо запрещено ADR-0005.

Нужно определить, что такое **выпуск «по проводу»** и как `update.sh` его
получает и проверяет — не прибегая к веткам и `latest`.

## Решение

**Выпуск по проводу описывается манифестом** (например `release.json`):

```json
{ "commit": "403ab3a1d8f8…", "semver": "0.1.1",
  "source_url": "…/vs-router-403ab3a.tar.gz",
  "source_sha256": "…", "min_os": "debian-13" }
```

**Артефакт выпуска — тот же `git archive` tar.gz того же коммита**, что ISO
вендорит внутрь себя. Один формат — два канала доставки:

| Канал | Артефакт | Назначение |
| --- | --- | --- |
| Offline baseline | ISO (несёт tar + sha + `REVISION`) | первичная установка, сети может не быть |
| Online update | `release.json` + `vs-router-<commit>.tar.gz` | обновление кода на работающей системе |

**Проверка (read-only).** Панель/CLI берёт манифест, сравнивает `commit`/`semver`
с локальным `/etc/vs-router/version.json` и показывает «доступен выпуск X».
Ничего не меняет. Это дополняет существующий `GET /api/release` (локальная
идентичность выпуска).

**Применение (только по явному согласию, через привилегированный агент).**
`update.sh --release <40hex>` (или `--manifest <url>`):

1. скачивает артефакт по `source_url`;
2. сверяет `source_sha256` **и** то, что `REVISION` из архива равен запрошенному коммиту;
3. распаковывает в `/opt/vs-router`, сохраняя прежнее дерево (для отката), пишет `REVISION`;
4. пересборка frontend+backend, установка wheel, `alembic upgrade head`, деплой UI/systemd-units, рестарт сервисов — эта часть в `update.sh` уже есть.

Никакого `git fetch`, никаких веток, никакого `latest` (ADR-0005).

## Рассмотренные варианты

- **Оставить git-обновление (клон/fetch):** требует держать репозиторий на хосте
  или клонировать историю (~940 МБ), снова завязывает обновление на сеть и на
  опубликованный коммит — ровно то, что отверг ADR-0008. Отвергнуто.
- **Переустанавливать ISO при каждом обновлении:** воспроизводимо, но это
  переустановка ОС и потеря конфигурации. Отвергнуто для рутинных обновлений;
  ISO остаётся baseline.
- **Манифест + tar-артефакт (принято):** ~2 МБ, тот же формат, что уже вендорит
  ISO, пиннится по коммиту и проверяется по sha256.

## Последствия

- `update.sh` перестаёт быть git-скриптом и становится «скачать → проверить →
  распаковать → собрать». Проверка формата `^[0-9a-f]{40}$` дополняется сверкой
  `REVISION` с запрошенным коммитом.
- Требуется **хост выпусков** (assets GitHub Release на тег либо статический
  каталог); URL манифеста делается настраиваемым. Это отдельное решение.
- Панель получает «проверить обновление» (read-only) и «применить» (через
  whitelisted RPC агента) — привилегированное действие только после согласия.
- **Откат:** прежнее дерево сохраняется; миграции БД должны быть обратимы, иначе
  обновление обязано отказаться.
- **Безопасность:** sha256 — всегда; сверка коммита — всегда; подпись артефакта —
  будущее усиление; `latest`/ветка запрещены.
- ADR-0010 раскрывает обещанное в ADR-0008 онлайн-обновление и подтверждает
  ADR-0005.
