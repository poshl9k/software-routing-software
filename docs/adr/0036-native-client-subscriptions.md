# ADR-0036: Нативная выдача подписки для Vell Client без Telegram

**Status:** принят; серверная часть реализована и покрыта тестами
**Date:** 2026-11-22
**Deciders:** пользователь, Hermes

## Context

Vell Client (`D:/code/vell-client`) — нативный клиент WireGuard/AmneziaWG на
Rust (Tauri 2 + React), а не mihomo/Clash Meta. Ему нужен `wg-quick`-совместимый
`.conf` (или `vpn://` для Amnezia), а не YAML-профиль. Сейчас публичная ссылка
подписки мастера выдаёт `mihomo` по умолчанию и `singbox` через `?format=`.
Второй канал получения — бот Telegram, но пользователь прямо потребовал, чтобы
выдача работала при недоступном Telegram; iOS пока вне объёма (нет аккаунта
разработчика), цели — Windows, Linux, Android.

Факты из кода:

- все аккаунты абонентов создаются со случайным паролем, которого абонент не
  знает (`register_telegram`, `create_subscriber`) — вход по паролю не вариант;
- у абонента есть стабильный токен кабинета (`PortalLink`): долгоживущий, без срока
  действия, заменяет пароль, выдаётся ботом и может быть выдан администратором;
- `DeviceSubscription` — уже отзываемый per-device токен; удаление устройства,
  ротация или истечение подписки гасят ссылку на стороне сервера;
- роутинг за reverse proxy означает, что `request.base_url` может быть внутренним
  http-адресом — ссылки должны строиться из `master_public_url`.

## Decision

1. **Один токен — все форматы.** Публичный endpoint
   `GET /api/portal/sub/{token}?format=…` получает форматы `conf` (нативный
   wg-quick AWG/WG) и `amnezia` (`vpn://`) в дополнение к `mihomo` и `singbox`.
   По умолчанию остаётся `mihomo`: уже установленные Clash-клиенты не ломаются.
   Новый токен для нативного клиента не mintится — ротация и отзыв по-прежнему
   гасят все форматы сразу. Ответы отдаются с `Cache-Control: no-store`.
2. **База ссылок — `master_public_url`.** Все выдаваемые наружу URL строятся из
   настроенного публичного origin; `request.base_url` — только фолбэк для
   разработки. Иначе за Caddy клиент получил бы недостижимую ссылку.
3. **Обнаружение устройств без сессии и без бота:**
   `POST /api/client/subscriptions` принимает стабильный токен кабинета в теле
   JSON (никогда в URL) и возвращает список per-device `conf`-ссылок, статус
   подписки и те же ссылки в других форматах. Сервер не создаёт сессию: клиент
   хранит токен кабинета в OS keychain и повторяет вызов для обнаружения новых
   устройств. Ограничение частоты — то же, что у входа по ссылке (5 попыток на
   15 минут на адрес); неверный токен — 401, истёкшая подписка — 200 с пустым
   списком профилей и `status: expired`.
4. **Выдача токена администратором:** `POST /api/master-admin/subscribers/{id}/portal-link`
   возвращает стабильный токен и ссылку на кабинет. Это снимает последнюю
   зависимость онбординга от Telegram: админ передаёт токен любым каналом.
5. **Клиентская сторона** реализует `ProfileProvider` поверх этих двух вызовов;
   протокол AWG/WG и ключи разбираются из `.conf`, секреты не попадают в модель
   профиля, отображаемую в UI. Подробности — ADR-0005 в репозитории клиента.
6. **Регистрация без администратора и без Telegram:** `POST /api/client/register`
   принимает имя; открытый доступ защищён одноразовым proof-of-work вызовом
   (`GET /api/client/register/challenge`, сложность 20 бит), лимитом 3 аккаунта
   с IP в сутки и общим rate limit. При регистрации автоматически выдаётся
   демо-тариф (`Demo`, 7 дней, 2 устройства, 500 МБ/сутки).
7. **Публичная конфигурация:** `public/portal.json` в этом же GitHub-репозитории
   содержит master URL и Telegram-handle; приложение читает raw-файл и кэширует
   его, с fallback на встроенную копию и ручной ввод. Telegram
   `@master_vsr_bot` — дополнительный, а не обязательный способ регистрации.
8. **Покупка:** админ задаёт `PUT /api/master-admin/payment-settings`
   (только HTTPS checkout URL и имя провайдера), авторизованный абонент получает
   его через `POST /api/client/checkout`. Сам агрегатор, вебхуки и начисление
   тарифа после оплаты будут подключены после получения данных провайдера.
   Дневной лимит хранится в тарифе и отражается в discovery; реальное ограничение
   трафика требует учёта байт на ноде и пока не реализовано.

## Rationale

- **Просить абонента вручную копировать ссылку из бота** — отвергнуто как
  основной путь: при недоступном Telegram канал исчезает. Оставлено как
  резервный путь (вставка готовой подписки в приложении).
- **Вход по логину/паролю в приложении** — отвергнуто: пароли абонентов
  случайные и неизвестны им; потребовался бы новый UX сброса пароля.
- **Новый per-app токен с отдельным lifespan** — отвергнуто: он стал бы вторым
  credential на устройство и выпал бы из уже работающей модели отзыва
  `DeviceSubscription`. Стабильный токен кабинета уже имеет нужные свойства
  (постоянный, ротируемый, заменяет пароль).
- **Отдавать нативному клиенту mihomo YAML** — невозможно: у Vell Client нет
  движка mihomo, он управляет AWG-туннелем напрямую.

## Consequences

- PresharedKey остаётся свойством канала выдачи: `.conf` и `vpn://` его несут,
  mihomo-профиль — нет (несовместимость mihomo с `amneziawg-go` peer с PSK).
- Новые поля ответа (`conf_url`, `amnezia_url`) добавлены во все ветки ответов
  кабинета, включая пустую; старые поля сохранены.
- `/api/client/subscriptions` не трогает состояние ноды: справка об устройствах
  берётся из БД мастера, поэтому discovery работает и при недоступной ноде;
  зато статус `active` устройства может не совпадать с фактом на ноде —
  клиент видит его только после запроса `.conf` (503 при недоступной ноде).
- Токен кабинета приравнен к паролю: админский endpoint выдаёт его в открытом
  виде один раз, аудит фиксирует выдачу; ротация пользователем гасит доступ
  всем ранее выданным копиям.
- Живая приёмка на реальном клиенте (Windows/Linux/Android) не проведена;
  покрыты только контракт, генерация `.conf` и HTTP-пути тестами мастера.
