# ADR-0037: Суточный учёт трафика и ограничение демо-тарифа на мастере

**Status:** принят; реализовано в мастере, проверено тестами
**Date:** 2026-11-22
**Deciders:** пользователь, Hermes

## Context

Демо-тариф из ADR-0036 даёт 7 дней доступа и 500 МБ в сутки, но одного поля в
тарифе недостаточно: нужен счётчик факта и механизм, который реально отключает
устройство после превышения. При этом нельзя плодить аккаунты бесконечно, а
платный агрегатор ещё не выбран.

Оказалось, что узел **уже** считает байты: `vs_router.agent.services.TunnelActivity`
читает `wg show <iface> dump` / `awg show <iface> dump` и возвращает
`{public_key, latest_handshake, rx_bytes, tx_bytes}`. Master bridge отдаёт эти
данные в `GET /internal/master/state` полем `tunnels`, а `BridgeClient.node_state()`
уже получает его. До ADR-0037 воркер мастера это поле игнорировал.

## Decision

1. **Источник счётчиков — существующая телеметрия узла.** Никаких новых правил
   nftables и никаких изменений на узле не требуется: master читает
   `result['tunnels']` в `vs_master.worker.process_pending` и передаёт его в
   новую функцию `sync_traffic_usage`.
2. **Кумулятивные счётчики → дневная дельта.** Таблица `master_traffic_usage`
   хранит по устройству и UTC-дате: `bytes` (списано за день), `rx_total`,
   `tx_total` (последние кумулятивные значения `wg dump`). Delta =
   `max(0, rx - rx_total) + max(0, tx - tx_total)`. Первое наблюдение — только
   базовая линия: трафик до начала наблюдения не списывается. Уменьшение
   счётчика (пересоздание пира) не даёт отрицательной дельты.
3. **Принудительное ограничение — через существующий `DeviceOp`.** Если
   `bytes >= tariff.daily_traffic_limit_mb * 1 MiB`, воркер ставит в очередь
   `deactivate` с `detail = 'daily_limit_deactivate'`. Операция проходит обычный
   путь replay и реально убирает пир на узле. Marker сохраняется в `detail`
   даже после `status='applied'`, чтобы не путать автоматическое отключение с
   ручным.
4. **Возврат на следующий день.** Если устройство `inactive`, последняя
   применённая операция — auto-`deactivate`, а дневной счётчик новой даты ниже
   лимита, воркер ставит в очередь `activate` с `detail = 'daily_limit_activate'`.
   Повторных операций не создаётся: проверяются pending/applied по marker.
5. **Видимость абоненту.** `POST /api/client/subscriptions` теперь отдаёт
   `subscription.daily = {used_bytes, limit_mb}` и статус `limit` при превышении;
   клиент показывает «дневной лимит трафика исчерпан» отдельно от `expired`.
6. **Миграции:** `0016` создаёт таблицы PoW/usage и тариф `Demo`, `0017` добавляет
   `rx_total`/`tx_total`. Миграции репетируются на копии боевой БД до установки.

## Consequences

- Лимит — **мягкий по времени**: он применяется на следующем цикле воркера после
  чтения телеметрии, а не на границе каждого пакета. Для жёсткого realtime-лимита
  нужны per-peer nftables quota rules на узле — это отдельное решение.
- Счётчики WireGuard не привязаны к дате; дневная граница — UTC (`now.date()`).
- Если узел не отвечает, счётчики не обновляются; предыдущее состояние и
  отключение сохраняются, ложного «разблокировать» не происходит.
- Тариф без `daily_traffic_limit_mb` не ограничивается: поведение для платных
  тарифов не меняется.
- Ручное отключение абонента не будет автоматически включено: у него нет marker
  `daily_limit_deactivate`.
- Payment checkout из ADR-0036 остаётся каркасом: агрегатор, вебхуки и выдача
  тарифа после оплаты подключаются после получения данных провайдера.

## Verification

`uv run --no-sync pytest -q tests/test_master_worker.py tests/test_master_portal.py
tests/test_master_migrations.py` — 55 passed. Отдельный тест прогоняет три цикла
воркера: базовая линия → 1,2 МБ и auto-deactivate → следующий UTC-день и
auto-activate. Заодно обновлён устаревший тест: master намеренно не генерирует
PSK (mihomo не handshake'ит с AWG-пиром, у которого есть PSK).
