# ADR-0032: Портал абонента как отдельный публичный процесс

**Status:** предложен

**Date:** 2026-10-23

**Deciders:** пользователь, Hermes

## Context

Панель (`vs-panel`) получает контур для абонентов: веб-кабинет, где абонент видит
свои устройства (пиры), срок подписки и создаёт/удаляет устройства в пределах
тарифа. Панель уже публикуется в интернете по имени (ADR-0025), но панель и
портал — разные модели риска: панелью пользуется один администратор, порталом —
множество внешних людей с высланными учётными данными.

Вариант «один процесс, два корня URL» отвергнут: изоляция тогда держится только
на правильности реверс-прокси (Caddy не должен проксировать админ-роуты), а
ошибка маршрутизации сразу открывает админ-API атакующему с интернета.

## Decision

Портал абонента — **отдельный процесс** на том же VPS:

- Публичный портал-процесс не имеет доступа к админ-API и агентному RPC; он
  работает с собственной БД (учётные записи, приглашения, тарифы, подписки) и
  узким внутренним интерфейсом для операций над устройствами.
- Публикация — отдельное имя по образцу ADR-0025: резервное
  `portal.<ip>.nip.io`, позднее `portal.<свой домен>`; TLS через Caddy.
- DNS в MVP задаётся вручную; автоматизация через DNS-API хостеров — после MVP
  по существующей плагинной архитектуре DDNS (первый адаптер — Cloudflare,
  wildcard DNS-01 на основной домен покрывает и портал).
- Панель администратора не меняется: свои сессии, свои куки, свой rate limit на
  login. Гигиена (Secure/HttpOnly/SameSite, origin-проверки, аудит) переносится
  на портал в полном объёме; портал — публичная поверхность, лимит перебора
  обязателен.

## Rationale

- **Один процесс** отвергнут: взлом публичного контура не должен давать даже
  теоретического пути к админ-API; изоляция процессом дешевле и надёжнее, чем
  изоляция конфигом Caddy.
- **Отдельный хост под портал** отвергнут: второй сервер ради MVP не окупается;
  изоляция процессом даёт тот же защитный эффект при общем ядре кода.
- **Публикация по пути `/portal/` на общем имени** отвергнута: cookie скоупится
  по хосту, а не по пути — сессии портала были бы видны любому приложению на
  том же имени; плюс `*.nip.io` не в Public Suffix List, и HTTP-01 для него
  упирается в лимиты Let's Encrypt на весь nip.io.

## Consequences

- Два процесса на одном VPS: деплой и мониторинг слегка дороже, код ядра общий.
- Внутренний интерфейс «портал → операции устройств» — новая точка стыка; он
  должен быть узким и явно описанным, не «вторым админ-API».
- Отдельная БД учётных данных — отдельный объект миграций и бэкапа.

Связанные: ADR-0025 (публикация панели по домену), ADR-0021 (след панели на
хосте), ADR-0017 (резервное `<ip>.nip.io`).

## Реализация (MVP, 2026-10-23)

Приземлено: пакет `backend/src/vs_portal` (своя БД + миграции `alembic-portal`),
процесс на отдельном UDS (`packaging/vs-router-web-internal.service`,
`vs-router-portal.service`), внутренний стык `/internal/portal/*` на отдельном
UDS с секретом (админ-маршруты на нём физически отсутствуют), публикация в
Caddy: `portal_names()` = `portal.<ip>.nip.io` + производное
`portal.<custom>`, host-matched маршрут на сокет портала, ACME-субъекты
включают имена портала. Не приземлено: DNS-API автоматизация (после MVP).
