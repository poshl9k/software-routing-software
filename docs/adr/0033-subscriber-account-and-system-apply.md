# ADR-0033: Учётная запись абонента и системное применение его операций

**Status:** предложен

**Date:** 2026-10-23

**Deciders:** пользователь, Hermes

## Context

Для портала абонента (ADR-0032) нужно решить: чем является учётная запись
относительно существующей сущности «Абонент» в конфигурации, как абонент
получает доступ и как его операции над устройствами доезжают до применённой
конфигурации без участия администратора.

Ограничения существующего контура применения: черновик один, применяется
целиком, применение — тяжёлая операция через агента, «каждое применение
осознанное» — модель, рассчитанная на одного администратора. Абонент действует
без админа, в произвольный момент.

## Decision

**Учётная запись = Абонент из конфигурации.** Отдельной сущности учётной записи
нет: логин абонента — имя существующего `Subscriber` (уникально), пароль, email,
тариф, срок подписки и статус — в БД портала с ключом по имени абонента.
Конфигурация остаётся источником истины по устройствам; БД портала — по учётным
данным и подписке.

**Доступ — по приглашению.** По умолчанию администратор создаёт абонента и
отправляет одноразовую ссылку-приглашение; абонент активирует учётку, задав
пароль (email — опционально, для будущего самообслуживания). Срок действия и
отзыв непринятого приглашения — за админом. Явной галкой «активировать» админ
может сразу выдать ссылку с готовым паролем — это осознанный выбор и риск
администратора, перехват такого письма даёт постоянный доступ.

**Операции абонента применяет система.** Создание, удаление, активация и
деактивация устройства абонентом не требуют подтверждения админа: портал
формирует черновик с изменением и запускает применение сам. Если применение
невозможно (занято другим циклом применения), операция остаётся в очереди со
статусом «ожидает применения» — второго пути мутации конфигурации не появляется.
Админ видит результат постфактум в истории.

**Истечение подписки — авто-блокировка** тем же механизмом: пиры абонента
снимаются с применённой конфигурации; продление возвращает те же устройства
(ключи и адреса сохраняются), а не пересоздаёт их.

## Rationale

- **Отдельная учётная запись, связанная с абонентом** отвергнута: лишняя
  сущность и рассинхрон ради гибкости «одна учётка — несколько абонентов»,
  которая в MVP не нужна.
- **Применение руками админа (очередь заявок с одобрением)** отвергнуто:
  абонент, купивший подписку, ждёт админа, чтобы подключить телефон.
- **Узкий служебный RPC «добавить пир» мимо черновика** отвергнут: появился бы
  второй путь изменения конфигурации и рассинхрон с моделью «черновик
  применяется целиком».
- **Ссылка с готовым паролем как единственный путь** отвергнута: перехват
  приглашения в мессенджере даёт доступ навсегда; двухшаговая активация даёт
  окно отзыва. Осталась как осознанная опция админа.

## Consequences

- Автоматические применения — новая нагрузка на контур применения: очередь
  операций, отказ «черновик занят», наблюдаемость статуса для абонента.
- Приглашения и пароли — новые секреты БД портала; хранение паролей argon2id
  (как у панели), приглашение — одноразовый токен с сроком.
- Конфликт «админ редактирует черновик одновременно с операцией абонента»
  решается очередью, а не вытеснением черновика админа.

Связанные: ADR-0032 (портал как отдельный процесс), ADR-0031 (правила
маршрутизации с назначением-набором), ADR-0020 (DNS-политика абонента).

## Реализация (MVP, 2026-10-23)

Приземлено: учётка = имя `Subscriber`, БД портала (accounts/invites/tariffs/
subscriptions/devices/device_ops/audit), инвайт по одноразовому токену с опцией
готового пароля, argon2id + rate limit, системное применение операций через
штатный apply (очередь `portal_device_ops`, ретраи при `apply.busy`,
идемпотентность по `portal_<id>`), авто-блокировка истечения и возврат тех же
ключей при продлении. QR/Amnezia-экспорт — честная заглушка 501 в MVP.
