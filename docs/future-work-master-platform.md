# Черновой план будущих работ: master, ноды и границы продукта

**Статус:** проектный черновик для будущих агентов. Не заменяет ADR-0035, `docs/master-portal-plan.md` или принятые ADR. Ни один пункт не является разрешением менять production, подключать `rg3`, запускать платежи, переустанавливать ноды или коммитить/публиковать изменения. Существующие пользовательские diff сохранить.

## Приоритеты и порядок

1. **Правовой и продуктовый gate** — до запуска/продвижения доступа к заблокированным ресурсам и до идеи «выхода через сеть клиента».
2. **Внешняя доступность нод и уведомления администратору** — мониторинг без автоматического изменения конфигурации.
3. **Перенос устройства между нодами** — сначала исследование и ручной failover на одноразовых нодах; автоматизация только после доказательства безопасного контракта.
4. **Цена Telegram Stars** — separate accounting/pricing workstream; оставить платежи выключенными до утверждения модели.
5. **Установка slave-ноды из master UI** — отдельный безопасный provisioning-контур, не произвольный SSH из web-процесса.
6. **Граница `vs-router` / `vs-panel` / `vs_master`** — инвентаризация и решение об архивировании/разделении до удаления кода.
7. **`rg3` geo-routing** — только read-only инвентаризация и правовая оценка до любых изменений.

## Проверенные исходные факты репозитория

- `Node.state`/`last_seen` и master→node `/internal/master/state` существуют. Текущий worker проверяет управляющий bridge, но не публичный абонентский endpoint и не российские точки наблюдения (`backend/src/vs_master/models.py`, `backend/src/vs_master/worker.py`).
- Новые устройства выбирают ноду при создании по `Node.state == 'ok'`; существующее устройство привязано к одному `Device.node_id` (`backend/src/vs_master/device_service.py`, `backend/src/vs_master/models.py`).
- Экспортируемый клиентский профиль включает endpoint и публичный ключ серверного туннеля (`backend/src/vs_master/exports.py`). Простое изменение `Device.node_id` не переносит точку входа и не меняет уже установленный профиль.
- Текущие Telegram-уведомления — outbox событий подписки; отдельного outbox инцидентов нод нет (`backend/src/vs_master/notifications.py`).
- Текущая схема Stars ограничена тестовыми слотами и фиксированным `1 XTR`; это нельзя расширять на продажи простым изменением тарифа (`backend/src/vs_master/models.py`, `backend/src/vs_master/stars.py`).
- Существующий onboarding ноды рассчитан на браузерное подключение к bridge. Установка по SSH из master UI — новая привилегированная граница и требует отдельного ADR/угроз-модели.
- Оператор сообщает, что на `rg3.poshl9k.ru` уже есть российская нода с несколькими зарубежными туннелями и geo-routing. Считать это описанием владельца, а не независимо проверенным состоянием.

## 0. Правовой и продуктовый gate

Перед реализацией/эксплуатацией коммерческого сервиса, который обеспечивает доступ из РФ к ресурсам, ограниченным в РФ:

- получить заключение юриста по применимости ст. 15.8 149-ФЗ, ст. 13.52 КоАП и, если услуга будет платной, ст. 29 126-ФЗ; отдельно проверить действующие требования к продвижению, пользовательским условиям, обработке обращений и данным;
- описать фактическую услугу, географию пользователей, роль master/RU-node/foreign nodes, платежи и предполагаемую обработку трафика; не подменять анализ «технической схемой»;
- не проектировать передачу обычного трафика через домашнюю сеть абонента как способ скрыть источник, перенести атрибуцию или освободить владельца сервиса от ответственности. Такая схема не является правовой защитой и добавляет риск для самого абонента;
- до заключения не включать/не рекламировать поток, предназначенный для обхода блокировок, и не подключать новые реальные ноды для этой цели.

Результат gate: письменный scope «разрешено / запрещено / при каких мерах», назначенный ответственный за compliance и перечень допустимых сценариев. Техническая возможность не равна правовой допустимости.

## 1. Доступность нод

### Дизайн

Считать отдельно три независимых измерения:

1. **Control-plane:** доступность bridge мастеру.
2. **Public endpoint:** доступность точного публичного IPv4/IPv6 из внешних точек.
3. **Client service:** при отдельном согласовании — синтетическое реальное WG/AWG-подключение и обмен тестовым трафиком.

Первый MVP — интерфейс провайдера измерений (например, Check-Host API), с возможностью заменить/добавить собственные пробы. Две московские точки — начальная диагностика, не представительство всех российских мобильных/домашних операторов. Сравнивать российские точки с контрольными точками вне РФ.

Проверки хранить раздельно: ICMP, TCP 22, TCP 443, HTTPS с правильными Host/SNI, IPv4/IPv6 и при необходимости тест сервиса. Отказ ICMP не объявлять отказом IP. TCP connect на 22 не считать полноценной проверкой SSH, а HTTP(S) — проверкой VPN-туннеля.

### Данные и состояние

- Хранить наблюдения с node, IP/family, методом, probe/ASN, временем, RTT/классом ошибки и request ID внешнего API; не сохранять сырые произвольные ответы или секреты.
- Не переопределять одним флагом bridge-health и reachability. Добавить состояние публичной доступности/достоверности отдельно от текущего `Node.state`.
- Ввести состояния `unknown / healthy / degraded / suspected_down / down` с настраиваемыми порогами, несколькими циклами и независимыми точками; восстановление тоже подтверждать несколькими успешными циклами.
- На подтверждённом down исключать ноду из новых назначений. Не мигрировать уже существующие устройства автоматически в этой фазе.
- В интерфейсе показывать последнюю успешную проверку, последние ошибки по каждому методу, источники и давность данных.

### Приёмка

- Тесты: timeout, DNS/IP-family mismatch, ICMP-only fail, TCP-only fail, неверный SNI/cert, API rate/error, устаревший результат, flapping, один отказавший probe provider.
- На одноразовой среде проверить живой endpoint с нескольких российских ASN и внешнего контроля; unit-тесты не выдавать за российское сетевое подтверждение.

## 2. Telegram-уведомления администратору

- Завести отдельную проверенную привязку личного Telegram-чата администратора: админ инициирует её из своей авторизованной сессии, бот принимает короткоживущий одноразовый challenge в private chat. Не считать введённый числовой Telegram ID доказательством владения.
- Добавить отдельную модель incident/outbox для переходов состояния ноды; не переиспользовать outbox абонентских подписок и не смешивать его с настройкой Stars.
- Создавать одно событие на подтверждённый инцидент и одно на восстановление; хранить попытки, lease, next retry, delivered time/message ID. Учитывать неоднозначный timeout Bot API как доставку «возможно», чтобы не создавать бесконечные дубли.
- Сообщение: имя ноды, IP/family, провалившиеся проверки, независимые точки, время начала/последнего успеха; без bridge token, SSH данных, subscriber ID и секретов.
- Привязка/уведомления должны иметь явное состояние и тесты: нет администратора, неверный/истёкший challenge, повтор, смена чата, Telegram недоступен, retry, recovery, дедупликация.

## 3. Цена Telegram Stars

### Сначала определить бухгалтерский источник

Telegram Bot API выставляет цифровые услуги в `XTR` и даёт баланс/историю транзакций. Цена покупки Stars пользователем и сумма, которую владелец бота получит при выводе, — разные величины; публичные цены могут различаться из-за VAT и комиссий. До кода определить, что именно означает «стоимость Stars» для проекта: собственная фактическая стоимость пополнения, ожидаемая сумма вывода или утверждённый бухгалтерский курс.

### Реализация после решения

- Rate-provider с источником, валютой, временем снимка, периодом годности и происхождением; хранить историю, не перезаписывать прошлые цены.
- Разделить `XTR amount` тарифа, справочную стоимость XTR, комиссию/налоги и целевую маржу. Для денежных вычислений не использовать binary float; округление только по явному правилу.
- Сначала показывать рекомендованную цену администратору; автоматическое изменение действующих тарифов/подписок/счётов не включать без отдельного подтверждения и аудита.
- При устаревшем или недоступном курсе не повышать/не снижать цену автоматически: сохранить последнее утверждённое значение и уведомить администратора.
- Разделить immutable order snapshot (цена, тариф, срок, курс/источник) и редактируемый текущий тариф. Отдельно спроектировать миграцию от тестовых фиксированных слотов `1 XTR`; сохранить историю старых тестовых заказов.
- Тестировать изменения курса, недоступность источника, задержку/повтор платежа, refund, несовпадение snapshot и тарифа. Пока контракт не утверждён — Stars остаются выключены.

## 4. Slave-нода из веб-интерфейса мастера

Это не обычный web endpoint: он запускает привилегированную установку на удалённом хосте. Сначала отдельная ADR и threat model. Не запускать SSH-команды из unprivileged web-процесса и не добавлять произвольный shell RPC.

> **Частично закрыто (коммит `ad9ad68` «feat(master): add web-based node onboarding», чужой агент).** Уже есть: браузерный онбординг bridge — создание ноды в админке, одноразовый токен, настройка публикации из node UI (`/api/host/...`, `master_bridge_publication`), тесты `test_master_bridge_setup_api.py`. Нет (и остаётся этой задачей): установка пакета по SSH из веб-интерфейса, проверка host key, pinned release, откат. Перед началом перечитать `docs/master-node-onboarding.md` и не дублировать bridge-часть.

### Безопасный контур

- Отдельный ограниченный provisioning worker/job, typed steps и allowlist операций; связь web→worker — аутентифицированная очередь с idempotency key.
- Проверять адрес/результат DNS и запрещать loopback, link-local, metadata endpoints и непредусмотренные внутренние диапазоны; блокировать DNS rebinding. Требовать host key fingerprint, сверенный администратором с независимым источником (например, console провайдера); не доверять одному `ssh-keyscan`.
- Предпочтительно — короткоживущий одноразовый SSH-ключ/сертификат. Если парольная форма останется обязательной: передавать только по HTTPS в теле запроса, держать только в памяти job на короткое время, никогда не класть в БД, argv, env, логи, exception text или артефакты; после job уничтожить.
- Проверить ОС/архитектуру/профиль/диск/службы/состояние продукта до изменений; показать оператору host identity и планируемые последствия; требовать явное подтверждение установки.
- Ставить только проверенный pinned release с подписью/хешем; никаких плавающих branch/source downloads. Сначала backup и проверенный rollback на disposable VPS.
- Шаги и прогресс должны быть идемпотентны: connect → verify host → preflight → backup → install pinned artifact → health → bridge enrollment → verify → cleanup ephemeral credential. Ошибка — остановка/rollback, а не продолжение частичной установки.
- До автоматизации закрыть известные installer gaps из репозитория: unattended known password/NOPASSWD и плавающие bootstrap-загрузки. Обычная установка не должна получать эти лабораторные обходы.

### Приёмка

Неверный host key, DNS rebinding, частичная установка, lost ACK/retry, отмена job, ошибка скачивания/хеша, недостаток диска, существующая чужая панель и rollback тестируются на изолированных VPS. Логи не содержат пароль, ключ, bearer token или полный environment. Поведение service restart проверяется отдельно от установки.

## 5. Failover/перенос пира без переимпорта

> **Уточнено:** план `docs/mihomo-entry-plan.md` (решение D9) заменяет этот раздел для схемы «входная нода в РФ + выходы за рубежом»: там перенос на другую зарубежную ноду — это переключение маршрута на входной ноде, а не миграция пира, и клиентский конфиг не меняется вообще. Раздел ниже остаётся актуальным только для прямого подключения клиента к зарубежной ноде без входа.

### Архитектурный контракт до реализации

- Разделить **логический service endpoint** (то, что записано у клиента) и физическую ноду, где исполняется peer. Рассмотреть модель `EndpointGroup/ServicePool`: стабильное имя/порт, серверная идентичность и список совместимых backend-нод; `Device.node_id` хранит текущую ноду исполнения.
- Для нового профиля проверить постоянный FQDN + контролируемое переключение DNS на резервную ноду. Не считать DNS failover работающим, пока на реальных клиентских приложениях не подтверждено повторное разрешение имени при reconnect. Если у действующего профиля literal IP, заменить его серверной операцией невозможно без заранее предусмотренного альтернативного адреса/механизма обновления.
- Чтобы профиль не менялся, резервная нода/ingress должны совместимо принимать тот же client peer и тот же серверный публичный ключ; проверить AWG параметры, порт, адреса, DNS, AllowedIPs, MTU и egress policy. Общее распространение server private key — отдельный риск/решение; оценить выделенную точку входа/UDP ingress и её отказоустойчивость.
- Различать «не требуется переимпортировать профиль» и «сессия не прерывается»: при смене backend краткий reconnect вероятен; сохранение уже открытых TCP-сессий не обещать.

### Durable migration state machine

Не менять `Device.node_id` напрямую и не переиспользовать одиночный `DeviceOp` как весь перенос. Ввести отдельную durable migration/ticket с source, target, generation/fencing epoch, текущим шагом, ретраями, безопасным кодом ошибки и audit:

1. Проверить разрешённую причину (админ вручную или подтверждённый аварийный policy), подписку, target availability/capacity, протокол/ключи/адресный конфликт и отсутствие другой операции.
2. Заблокировать конфликтующие операции устройства; подготовить целевой peer идемпотентно с тем же ключевым материалом/адресом, не раскрывая его в журналах.
3. Проверить target bridge и публичную достижимость; переключить logical endpoint/DNS/ingress только если этот механизм уже проверен клиентским тестом.
4. Подтвердить синтетическим handshake и двусторонним тестовым трафиком; лишь затем зафиксировать новое назначение и отключать исходный peer.
5. Если target не прошёл проверку — вернуть endpoint к source, убрать новый peer и оставить старое назначение. Если source был недоступен, при его восстановлении выполнить reconciliation/fencing, чтобы старый peer не ожил независимо.

### Этапность и приёмка

- Сначала прототип на двух disposable нодах и одном тестовом устройстве; затем ручной admin-trigger с dry-run и подтверждением; автоматический failover — только после достаточной телеметрии и успешных циклов отказа/возврата.
- Проверять конфиг клиента до/после побайтно (секреты не печатать), отсутствие второго активного владельца peer, подтверждение target handshake, возврат source, повторы после lost ACK и отказ в середине каждого шага.
- Переносы существующих абонентов не включать до принятия ADR и успешной сквозной проверки. Это новое решение меняет текущее D4 ADR-0035 «автораспределение при создании, без автомиграций».

## 6. `rg3` и geo-routing

- Сначала только согласованная read-only инвентаризация фактических правил, таблиц геоданных, DNS/IPv4/IPv6, выбранных egress и тестовых destination-классов; не перезаписывать runtime config/Caddy и не трогать абонентов.
- Отдельно описать, какие направления считаются «обычным», «недоступным в РФ» и «недоступным из-за рубежа», кто поддерживает списки и как обрабатываются ошибки геоданных. Не делать вывод о правомерности из технического успеха теста.
- До юридического заключения не расширять сценарии доступа к заблокированным ресурсам и не добавлять выход через клиентские домашние соединения.

## 7. Судьба `vs-router` и рефакторинг

- Сначала принять продуктовый выбор: `vs-router` закрывается, замораживается/архивируется или остаётся отдельным поддерживаемым продуктом. Не выводить из «пока не нужен» разрешение удалить код.
- Сделать dependency/runtime inventory: профили `router`/`panel`, shared core, импорт-граф, UI, migrations, packaging/installers, systemd units, generated artifacts, golden/unit/native tests, документация, все установленные хосты и роль `rg3`.
- Сверить с уже существующим `docs/panel-router-split.md` (фазы B–H). Не переносить/удалять shared code до доказательства, что `vs-panel`/`vs_master` его не используют.
- Если продукт откладывается: сохранить точную воспроизводимую версию в отдельном archive repo/tag с инструкцией сборки и тестов; затем отделить живые `vs-panel`/master артефакты. Удалять только после CI обоих оставляемых профилей и явного решения владельца.

## Ограничения для будущих агентов

- Никаких коммитов, push, release, production deploy, live Telegram payments, peer migration, установки или изменения `rg3` без отдельного разрешения на конкретную операцию.
- Сохранять существующие незакоммиченные изменения; не редактировать `docs/master-portal-plan.md` без прямого поручения.
- Сначала синтетические БД/тесты, затем disposable Linux/VPS; Linux-host validation не подменять тестами Windows или mocks.
- Перед code change использовать TDD; schema/API/UI/config contracts менять согласованно; после внешнего side effect читать точное состояние обратно.
- Отдельно отчитываться по каждому acceptance gate: source/unit proof, external probe proof, реальные client tests, payment test, live installation — это разные уровни доказательства.
