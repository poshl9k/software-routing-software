# Пограничный роутер: порядок настройки и приёмка

Практический порядок действий для схемы «управление отдельно, клиентские VLAN
через транк, выход через вышестоящие роутеры или AWG». Общая модель сегментов —
`docs/admin-routing-segments.md`, решения — `docs/router-split-routing-plan.md`.

Пример ниже — рабочий стенд `192.168.10.10` (`wifi-router`, Debian 13, профиль
`router`). Адреса приведены как образец; логика применима к любому хосту с такой
ролью портов.

## 1. Схема и роли портов

```
  Управление (не для клиентского трафика)
  ens192  192.168.10.10/16   default via 192.168.10.9
     │
  Аплинки к вышестоящим роутерам (зона wan)
  ens224  192.168.107.2/24   gw 192.168.107.1, таблица 1000
          + дополнительные адреса /32 из нужных сетей
     │
  Транк к точкам доступа (ESXi: портгруппа 4095 / VGT)
  ens256  10.10.20.1/24      native
     └─ vlan1@ens256  VID 201  172.20.1.1/24   ( SSID → Kea → перехват )
     │
  Выход в интернет для «не РФ»
  tun0    10.66.126.2/32     AWG-клиент `prostor`
```

Правила схемы:

- `ens192` — только управление панелью, SSH и апстрим резолвера. Клиентский
  трафик туда **не пускать**.
- `ens224` — «LAN в сторону апстримов». Один физический линк, несколько адресов
  и несколько вышестоящих роутеров; выбор делается парой «адрес-источник + шлюз».
- VLAN создаётся на транк-родителе; VID в конфиге обязан совпадать с VID на
  ядре — иначе пакеты уходят в другой VLAN и ARP не разрешается.
- AWG-туннель — основной выход для не-RF-трафика и, заодно, транспорт для
  загрузки удалённых rule-set'ов.

## 2. Порядок настройки

Шаги идут по зависимостям: не переходите к перехвату, пока не заработали адрес,
DHCP и DNS без перехвата.

### 2.1. Интерфейсы и VLAN

1. «Подключения и адреса»: `ens192` — зона `lan`,статический адрес, шлюз по умолчанию.
2. `ens224` — зона `wan`, основной адрес с префиксом; каждый следующий адрес
   того же линка генерируется как `/32`. Указывайте **адрес хоста**, а не
   сетевой/широковещательный (`192.168.116.0/24` — не адрес интерфейса):
   валидатор отклоняет такой ввод кодом `interface.address_host_required`.
   Для каждого апстрима нужна своя пара «адрес + шлюз», иначе ядро выберет
   первый маршрут по умолчанию.
3. `ens256` — зона `lan`, адрес native-сети, DHCP выключен.
   Физический порт-транк можно добавить без адреса: в «Быстром подключении»
   выберите «Статический IP» и оставьте поле адреса пустым — затем на него
   навешиваются VLAN (помечать порт как DHCP-клиент нельзя). У существующего
   интерфейса основной адрес удаляется кнопкой или очисткой поля — после
   этого порт тоже становится транком.
4. Создайте `vlan` с `parent = ens256`, `vlan_id = 201`, зона `lan`, адрес
   `172.20.1.1/24`. На точках/контроллере SSID → VLAN 201, DHCP там выключен.
5. Примените и сверьте VID на хосте:

   ```sh
   ip -d link show vlan1 | grep 'vlan protocol'   # id 201
   ip -br addr show vlan1                         # 172.20.1.1/24
   ```

   Если VID отличается от конфига, а агент старой версии: удалите stale-линк
   (`ip link del vlan1`) и `networkctl reconfigure ens256`. В текущей версии
   агент делает это сам до reload'а networkd.

### 2.2. DHCP и DNS

1. DHCP-подсеть на `vlan1`: `172.20.1.0/24`, пул `172.20.1.20–.250`, шлюз и DNS
   `172.20.1.1`. Клиент обязан получить шлюз и DNS равными адресу панели в VLAN.
2. «DNS» → «Интерфейсы»: `vlan1` в списке слушателей.
3. «DNS» → «Кому отвечает резолвер»: `172.20.1.0/24` в `access_control`.
   **Не** добавляйте `0.0.0.0/0` без явной нужды — это открывает резолвер всем
   сетям. Проверка: `grep access-control /etc/vs-router/applied/unbound.conf`.
4. Проверка до перехвата:

   ```sh
   dig +short @172.20.1.1 ya.ru A
   ```

### 2.3. DNS-политика перехвата

Открывается **постоянно**: «Службы → DNS → Политика DNS для перехвата →
Настроить DNS-политику». Та же кнопка есть в предупреждении карточки сегмента.

- Укажите **доступный** сервер, например `192.168.10.9:53` (тип `udp`).
- Не указывайте `127.0.0.1:53`: в контуре перехвата обычный `unbound.service`
  остановлен, там нет слушателя. Генератор отклоняет такой адрес кодом
  `tproxy.dns_server_loopback_53` вместо того, чтобы пустить движок на fatal.
- Если вышестоящий резолвер сам ходит через DoT к внешнему серверу, это
  допустимо: проверьте, что RU-домены резолвятся в RU-адреса
  (`dig +short @192.168.10.9 ya.ru A`), иначе РФ-выход не сработает.
- Второй сервер не даёт failover: `final` у политики — первый. Остальные
  серверы подключаются только явными DNS-правилами (домены/наборы → сервер).

### 2.4. Разрешение транзита (частая причина «интернета нет»)

Перехват fail-closed: новый поток с сегмента сначала проходит `preauth`, и только
получив штамп допускается до TProxy. Для этого нужно **включённое** правило
файрвола:

- «Брандмауэр» → вкладка зоны сегмента (`lan`) → правило вида
  `pass`, ingress `lan`, `src = 172.20.1.0/24`, `dst = zone:wan`;
- состояние правила — «Включено». Правило с `enabled: false` в сгенерированную
  цепочку не попадает.

Проверка после apply:

```sh
nft list table inet vs_router_tproxy_preauth | grep -E 'any_to_any|drop'
```

Счётчик `return` должен расти, счётчик `drop` в `chain transit` — нет.

### 2.5. Выходы

«Маршрутизация» → «Сегменты» → «Изменить политику». Правила сверху вниз,
последнее — «Всё остальное» (`0.0.0.0/0`).

- РФ-выход: `Выход = Через интерфейс`, интерфейс `ens224`,
  `Адрес-источник = 192.168.107.2`, `Шлюз = 192.168.107.1`. Пара источник+шлюз
  обязательна, если на линке несколько апстримов.
- Остальное: `Выход = Через туннель`, клиентский AWG `prostor`.
- IP-наборы (`ru-ips` и т.п.) объявляются в «Источниках списков»; текстовые
  форматы генератор не принимает, используйте `srs`/`json`.

Для удалённых rule-set'ов генератор сам проставляет `download_detour` на
доступный клиентский туннель — без этого старт движка падает, если CDN
недоступен через management-аплинк. Проверка:

```sh
python3 -c 'import json;d=json.load(open("/etc/vs-router/applied/singbox.json"));rs=d["route"]["rule_set"];print(len(rs),sum("download_detour" in r for r in rs))'
```

### 2.6. Виртуальные IP-интерфейсы (IPVLAN L2)

Когда на одном физическом порту нужно несколько равноправных адресов или сетей,
а VLAN по тегу быть не должен, создайте интерфейс типа «Виртуальный IP (IPVLAN L2)»:

- родитель — существующий физический интерфейс с назначенной зоной;
- у виртуального интерфейса своя зона, свои адреса и своё имя;
- в `.netdev` это `Kind=ipvlan` + `[IPVLAN] Mode=L2`, а в `.network` родителя
  пишется `IPVLAN=<имя>` — именно с заглавной `V` (ключ регистрочувствителен;
  написание `IPvLAN=` networkd игнорирует как `Unknown key`);
- такой интерфейс выбирается везде, где и обычный: как источник/назначение
  в правилах маршрутизации (включая пару «адрес-источник + шлюз»), в зонах
  файрвола, в слушателях DNS;
- в таблице он стоит сразу под родителем с подписью «IPVLAN на …» и бейджем
  `IPVLAN L2`.

Реализованы оба варианта: `virtualip` (IPVLAN L2) и `virtualmac` (MACVLAN bridge).
Агент сообщает поддержку IPVLAN в `/api/host/profile` (`ipvlan: true/false`): панель скрывает
пункт IPVLAN, если хостовый networkd его не понимает, а apply с таким типом отклоняется
кодом `agent.ipvlan_unsupported` до изменения сети. Debian 13 с systemd 257 ключ
`IPVLAN=` понимает — проверено на живом хосте: `ip link add link ens224 name vip2
type ipvlan mode l2` с адресом `192.168.116.253/24` даёт ARP `REACHABLE`, ping
до `192.168.116.254` без потерь и HTTP 200.

Выбирайте IPVLAN L2, если апстрим не разрешает чужие MAC-адреса (например,
портгруппа ESXi с Forged Transmits = Reject): IPVLAN сохраняет MAC родителя.
MACVLAN даёт каждому интерфейсу свой MAC и требует разрешения подмены MAC на
апстриме. Ядро разрешает только один rx-handler на родителя, поэтому IPVLAN и
MACVLAN-дети **не могут сосуществовать на одном порту** (`Device is already in
use`); агент сам удаляет старых детей при смене типа через apply.

### 2.7. Перехват и применение

1. Включите тумблер «Перехватывать трафик сегмента» в карточке сегмента.
   Без него правила сохраняются, но не действуют.
2. Примените черновик. Успешный apply: `status = confirmed`, все фазы `applied`.
3. Дождитесь стабильного движка:

   ```sh
   systemctl is-active vs-router-singbox
   systemctl show vs-router-singbox -p NRestarts --value
   journalctl -u vs-router-singbox -n 30 | grep -i fatal
   ```

   `NRestarts` должен оставаться нулевым, `FATAL` — отсутствовать.

## 3. Приёмка

| Проверка | Команда | Ожидаемый результат |
|---|---|---|
| VID совпадает с конфигом | `ip -d link show vlan1` | `id 201` |
| Клиент на L2 | `ip neigh show dev vlan1`, `ping <client>` | `REACHABLE`, 0% потерь |
| DHCP | `cat /var/lib/kea/kea-leases4.csv` | аренда из пула .20–.250 |
| DNS клиента | `dig @172.20.1.1 ya.ru +short` | RU-адреса |
| Автоправила DNS/DHCP | `nft list ruleset \| grep -E 'dns_resolver_auto\|dhcp_server_'` | правила есть |
| Preauth пропускает | `nft list table inet vs_router_tproxy_preauth` | `return` растёт, `transit drop` — 0 |
| Перехват работает | `nft list table inet vs_router_tproxy_interception` | `tproxy_tcp/udp` растут после запроса клиента |
| Движок жив | `systemctl is-active vs-router-singbox`, `NRestarts` | `active`, `0` |
| Туннель жив | `awg show tun0` | свежий handshake, transfer растёт |
| Здоровье контура | `cat /run/vs-router/health.json` | findings пусто/исправлено |

Проверять «есть ли интернет через апстрим» ICMP-пингом ненадёжно: на части
апстримов ICMP заблокирован, а HTTPS работает. Используйте
`curl -I --max-time 8 https://example.com` с нужным `--interface`.

## 4. Что уже исправлено в коде, а что остаётся решением оператора

В коде (не требуют ручными действиями):

- свёрка VID/родителя существующего netdev и удаление stale-линка до reload networkd;
- автоматические `input`-правила для DHCP-подсетей и слушателей резолвера;
- отказ от `127.0.0.1:53` в DNS-политике перехвата на этапе генерации;
- статус DNS в панели учитывает split-резолверы, когда перехват включён;
- редактор DNS-политики доступен со страницы DNS, а не только из предупреждения;
- загрузка удалённых rule-set'ов через доступный клиентский туннель.

Остаётся настраивать вручную (это политика, а не дефект):

- адреса и шлюзы вышестоящих роутеров на `ens224`;
- подсеть и пул DHCP, список `dns.access_control`;
- включённое правило `pass` на транзит с сегмента;
- пары «выход + адрес-источник + шлюз» в правилах маршрутизации;
- сам факт включения перехвата сегмента.

## 5. Типичные поломки

| Симптом | Причина | Лечение |
|---|---|---|
| ARP `FAILED`, пинг клиента не идёт | VID в ядре отличается от конфига; порт не транк | сверить `ip -d link`, транк/VGT на ESXi; stale-линк удалить |
| Клиент получает `REFUSED` на DNS | подсети нет в `dns.access_control` | добавить сеть, убрать `0.0.0.0/0` |
| `tproxy_dns_direct` drop растёт | клиент шлёт DNS не на `172.20.1.1` | поправить DHCP-опции клиента |
| `preauth/transit` drop растёт, перехват пуст | правило файрвола выключено | включить `pass` для сегмента |
| `sing-box` FATAL `connection refused` на `127.0.0.1:53` | loopback в DNS-политике | поставить доступный DNS (`192.168.10.9`) |
| `sing-box` FATAL `i/o timeout` на rule-set URL | CDN недоступен через management-аплинк | проверить `download_detour` и здоровье туннеля |
| В панели «DNS остановлена» | обычный `unbound.service` выключен при перехвате | это нормально: active должны быть `vs-router-unbound-*` |
| Панель отдаёт `internal.error` / 500 на `/api/versions` | в базе остался черновик, который стал невалидным после ужесточения правил | читать такие версии теперь можно (доменная проверка пропускается только при чтении), но apply всё равно отклоняет их; поправьте или удалите черновик |
| Ответы RU-сайтов не-RU | апстрим-резолвер гео-некорректен | использовать другой резолвер или DNS-правила по доменам |
