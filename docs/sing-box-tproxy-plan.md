# План: выборочная маршрутизация через sing-box TProxy

**Статус:** проект, сетевой тракт не реализован. Частичный UI позволяет сохранять выключенную политику (источники, IPv4/доменные правила direct/block, расписание) в черновике; администратор может запросить синтаксический предпросмотр **сохранённого черновика** (`GET /api/draft/tproxy/preview`, без побочных эффектов и сетевого перехвата). Генератор проверен через `sing-box check`, но сам запрос предпросмотра не запускает бинарник и не подтверждает готовность. Пакетная проба на одноразовой VM (`docs/lab-05-singbox-tproxy.md`) подтвердила TCP/UDP TProxy с loopback bind, off и ограниченные сценарии отказа; одновременно доказала **обход default-deny FORWARD при перехвате**. Это блокер включения до предварительной авторизации по правилам firewall. Расписание не исполняется, доменные признаки требуют sniff и не покрывают все протоколы без DNS-интеграции. Включение отвергается `tproxy.not_available` до реализации безопасного перехвата и crash guard. Основано на обсуждении с владельцем продукта и анализе `hoaxisr/awg-manager` (`develop`, `0e5f4952d34e5b75767a6da84a8f1771d9b79839`). Живая страница роутера ответила на GET, но вернула лишь оболочку SPA; действующие настройки и работающий сетевой тракт не исследованы. На роутере ничего не менялось.

## Результат и границы

В панели появляется раздел «Маршрутизация → sing-box TProxy»: выбор источников, правила, пресеты сервисов, rule-set'ы, выходы WG/AWG и исходящие прокси/подписки, DNS-политики, исключения, диагностика и простой/экспертный интерфейс. Это функциональная адаптация под Debian 13, а не перенос Keenetic NDMS, iptables или Svelte-компонентов. Действующие Caddy/Unbound/firewall/WG/AWG продолжают работать.

Не входят: FakeIP/policy-TUN, перехват исходящего трафика самого роутера, полноценный IPv6 TProxy, внешние оповещения, DNS-заглушка и произвольное исполнение конфигурации/команд через агент. Совместимость каждого протокола прокси/формата подписки определяется тестовой матрицей из upstream и закреплённой версии sing-box до обещания паритета. Резерв через **другую** службу маршрутизации — точка расширения: пока второй службы нет, переключать некуда. Существующие выходы и группы sing-box могут иметь отдельный резерв, но только при проверенной готовности и явном выборе администратора.

## Согласованная семантика

1. Исходно TProxy выключен. Администратор явно выбирает LAN/VLAN/VPN-интерфейсы или устройства; «весь транзит» — отдельный выбор только для назначенных входящих интерфейсов. Неназначенные порты, WAN-вход, локальные сервисы роутера и его собственный OUTPUT не перехватываются. За устройством нельзя полагаться только на изменяемый IP: отдельно проверить MAC/DHCP/ARP и поведение для VPN без MAC.
2. Правила упорядочены, первое совпадение выбирает `direct`, `block` либо выход. Матчеры: домен/суффикс, IP/CIDR, адрес/устройство источника, TCP/UDP и порт, наборы и их логическая комбинация; импорт и редактирование сложных правил не должны терять скрытые поля. Конечное действие для не совпавшего трафика — `direct` по умолчанию, изменяемое. `direct` означает обычную маршрутизацию и всё ещё подчиняется firewall, а не обход его.
3. Явное выключение снимает перехват и защитные правила, возвращает обычную маршрутизацию. Неожиданный отказ при включённой политике блокирует **весь не исключённый трафик выбранных источников**: без работающего движка нельзя отличить совпавшие правила от конечного `direct`. Явные bypass, доступ к панели и служебный трафик роутера сохраняются. Резервный выход используется только если он явно настроен и подтверждён живой проверкой; иначе блокировка. Не утверждать, что уже установленные соединения переживут переключение.
4. DNS выбранных источников обрабатывается с приоритетом локальных записей и явных forwards Unbound; оставшиеся запросы идут через DNS-политику sing-box, без прямой утечки во внешний WAN-DNS при отказе. DNS самого роутера не перехватывается. В UI честно указать ограничения при стороннем DoH/DoT, зашифрованном DNS, CDN/shared IP и отсутствии доступного доменного имени; SNI/sniffing не объявлять доказательством имени для любого соединения.
5. В первой поставке TProxy маршрутизирует IPv4; для выбранных источников IPv6-выход в WAN блокируется, пока нет эквивалентного IPv6-перехвата. Не блокировать локальный IPv6/панель без необходимости. Показывать ограничение до включения, тестировать IPv4/IPv6 отдельно.
6. Пересечение с firewall: политика доступа и default deny остаются обязательными; port forward/DNAT и локальные сервисы имеют существующие приоритеты. Перехват не должен превратить отклонённый firewall-пакет в разрешённое соединение или перехватить входящий port forward.

## Источники списков и обновления

- Перенести **каталог как данные/адаптер** из `awg-manager/internal/presets/defaults.json`, не его Keenetic-логику. Он включает ссылки на SagerNet и `https://repo.hoaxisr.ru/rulesets/` (`json/`, `raw/`, `srs/`). Дополнить адаптерами для `v2fly/domain-list-community` (домены), `RockBlack-VPN/ip-address` (CIDR), `123jjck/cdn-ip-ranges` (CDN IP), geoip и geosite. Реестр источников с именем, форматом, URL, лицензией, временем/хешем версии и предупреждением о происхождении. Права на переупаковку сторонних данных проверить до включения их в дистрибутив: у `123jjck/cdn-ip-ranges` файл лицензии при проверке через GitHub API не найден.
- Профиль источника определяет строго проверяемый формат: текст доменов/IP, бинарный `.srs`, исходный geosite/geoip и т. д. Не считать CIDR-набор доменным, не путать DNS-совпадение и IP-совпадение. Материализация/компиляция — агентом с фиксированной версией инструментов и ограниченными ресурсами; внешние URL нельзя использовать для SSRF во внутреннюю сеть (allowlist для встроенных источников, отдельное разрешение и защита от перенаправления/DNS rebinding для пользовательских). Лимит размера, таймаут, синтаксическая проверка, предел записей, контроль TLS, статус stale.
- Два взаимоисключающих режима расписания: «Периодически» (по умолчанию 6 часов, период настраивается) или «В суточном окне» (один запуск за сутки, исходно 00:00–05:00 по таймзоне сервера; окно и время меняются). Ручное обновление — в любое время. Сохранять последнюю попытку/успех и не делать массовую догоняющую серию после долгого простоя; условные HTTP-запросы, backoff/джиттер и лимиты. Показать фактическое следующее время с учётом смены времени/DST.
- Обновление **используемых** наборов: скачать во временное ограниченное хранилище → проверить формат/размер/ссылки → проверить собранный sing-box-конфиг с новым набором → атомарно активировать → проверить готовность/тестовый маршрут. При неудаче вернуть прежний рабочий файл и статус, не трогать целую конфигурацию роутера; оставить историю и ручной откат версии набора. Обновление каталога пресетов отдельно от содержимого уже выбранных наборов; удалённые каталоги не должны молча переписывать решения администратора.

## Реализация по этапам и критерии готовности

### Текущий промежуточный результат: изолированное containment и preauth

- `generators/nftables.py:generate_tproxy_containment` — чистый **экспериментальный** генератор отдельной `inet vs_router_tproxy_guard`, не подключённый к bundle, apply, API или boot restore. При включённом намерении блокирует весь FORWARD от выбранных назначенных non-WAN интерфейсов с priority `-10`, до существующего `established,related`; без ограничений по семейству/протоколу. При выключенном намерении выдаёт только удаление своей таблицы. Неверный или пустой ingress отвергается. Это не разрешает включение TProxy через публичный контракт.
- Намеренное ограничение прототипа: нет bypass/DNAT-исключений и готового состояния. Блокируется также локальный транзит и потенциально ответы на port forward. INPUT/OUTPUT не меняются; **уже перехваченные соединения и OUTPUT sing-box этой таблицей не защищены**, обратное направление с другого ingress тоже не охвачено. Flow offload/bridge требуют отдельных проверок. Это заготовка containment для потери перехвата, не полный fail-closed.
- Проверено: unit-тесты порядка/семейств/недопустимых ingress/off; сгенерированный файл прошёл `nft -c -f` внутри разрешённой Debian VM (exit 0), без live-применения. Пакетная матрица этого генератора ещё не выполнялась. VM возвращена к `pre-singbox-20261002`, выключена.
- Дизайн предварительной авторизации: общая компиляция first-match с FORWARD, после DNAT, до TProxy и его mark. `zone:<dst>` означает маршрутизируемый выходной интерфейс, **не** подсеть: нельзя механически скопировать `oifname` в PREROUTING или заменить его CIDR. Требуется доказать обычный post-DNAT lookup до interception mark, затем отдельно разрешённость фактического proxy-outbound. DNAT обходится без перехвата, но не получает blanket-accept. Неопределённый маршрут/неподдерживаемая семантика должны закрываться, а не давать доступ.
- Добавлен отдельный offline `generate_tproxy_preauthorization`: общие с действующим firewall матчеры/алиасы/порядок, post-DNAT hook `-90`, положительный assigned-egress gate, local/DNAT возврат без marker, default deny. Нет live-интеграции; prototype re-evaluates каждый пакет и заменяет reject на drop. UDP-проба с синхронными ingress/origin AF_PACKET и echo receiver проверила first-match/default-deny/off и маршрутизируемую зону (`docs/lab-06-tproxy-preauthorization.md`). С настоящим TProxy эта авторизация ещё не проверена.
- Пакеты выявили непригодность `fib daddr . mark . iif oifname`: `.iif` ограничивает результат входящим устройством и блокировал разрешённый маршрут. Исправленный `fib daddr . mark oifname` прошёл простой маршрутизируемый UDP-сценарий, но не воспроизводит iif-/L4-зависимые policy rules и все ECMP-случаи. До включения обязателен runtime gate неподдерживаемого routing либо другая точка проверки. Обычные nft golden-файлы не изменились.

- Дополнительная UDP-проба с настоящим обычным firewall и preauth: локальный INPUT подчиняется явному pass/default deny; связанный port-forward работает через сгенерированный auto-accept и сохраняет NAT tuple; несвязанные WAN/LAN DNAT доходят до post-preauth observer, но блокируются обычным FORWARD. Контрольные запросы после отказов проходят. Это не проверка вместе с sing-box/containment; ограничения и результаты — `docs/lab-06-tproxy-preauthorization.md`.

- **TCP-верификация preauth (новое, 7 окт 2026):** VM-проба `docs/lab-24-tproxy-tcp-preauth-combined.md` с настоящим ordinary firewall + preauth + containment + sing-box показала, что при **активном** перехвате deny/default-deny (fresh и established) не достигают origin — обход default-deny FORWARD для TCP при включённом preauth не воспроизводится. Proxy OUTPUT авторизуется независимо по UID сокета; отзыв удерживает активное окно, но уже буферизованные в сокете байты флашатся при teardown и не атрибутируются `meta skuid`. - **INPUT-авторизация через conntrack (новое, 7 окт 2026):** LAB-проба `docs/lab-26-tproxy-input-authorization.md` (`backend/tests/lab/tproxy_tcp_ct_proof_probe.py`, режим `--tcp-ct-proof`) переносит владение INPUT из подделываемого packet `meta mark` в `ct mark`: reset очищает conntrack-бит, перехват ставит `ct mark | 0x200` после успешного TProxy, независимый INPUT guard допускает только по `ct mark & 0x200`. На одноразовой VM точная инъекция lab-09 (packet-mark forge) больше НЕ доставляет established TCP (`delivered=false`, drop+6); здоровый поток/recovery/off/fresh-deny прошли, EXIT=0. **Остаточная граница:** привилегированное правило, пишущее сам `ct mark`, по-прежнему доставляет токен (`delivered=true`) — неподделываемость против конкурирующего root-nft-writer'а недостижима в принципе; реальное требование — единственный владелец mark/table/hook-пространства (root), а резервирование marks в `marks.py` остаётся контрактом владельца, не security-гарантией. Packet-path для ct-варианта на позиции `-86`, buffered-байты, proxy OUTPUT, DNS, IPv6, ECMP и lifecycle не проверялись.

### 0. Совместимость и угрозы (до изменений сетевого тракта)
- **Кэш selected resolver при отказе:** offline selected Unbound теперь выставляет `cache-max-ttl: 0`, `cache-max-negative-ttl: 0`, `serve-expired: no`, ordinary/live конфиг не затронут. В одноразовой VM последовательные повторные selected UDP/TCP запросы каждый раз доходили до fake stub; после его остановки ранее успешное имя перестало отвечать прежним A, новые имена не ушли в WAN, локальная запись и explicit forward остались доступны, после рестарта stub новые UDP/TCP имена восстановились. Это не гарантия для параллельных запросов, буферов или реального sing-box и не host-owned detector; кэш explicit forwards selected тоже отключён. См. `docs/lab-23-tproxy-dns-selected-cache-off.md`.
- **DNS при потере fake stub (VM-only):** после остановки тестового loopback DNS-stub оба Unbound и UID-guard остались работать. Новые unmatched QNAME выбранного клиента по UDP/TCP дали timeout, не появились у ordinary/explicit WAN origin; обычный клиент продолжил получать ответы, локальные записи и новые explicit forwards выбранного клиента тоже работали. После запуска stub новые UDP/TCP имена снова дошли до него без рестарта Unbound. **Но** старое unmatched имя продолжило отвечать из кэша selected Unbound при остановленном stub: один OUTPUT guard не обеспечивает строгий отзыв DNS-ответов и не является host-owned detector. Нет доказательства поведения настоящего sing-box или lifecycle. См. `docs/lab-22-tproxy-dns-stub-failure.md`.
- **UID OUTPUT-контур для двух временных Unbound:** отдельный offline-генератор разрешает выбранному numeric UID только ответы своего listener клиентам, loopback DNS-stub и явные forward IPv4 адреса/`:53`; остальной OUTPUT UID отбрасывает. На одноразовой VM два Unbound с UID 29092/29093 и нулевыми capabilities прошли UDP/TCP локальные записи, раздельный кэш, stub и explicit forward; при попытке к одному ordinary upstream выбранный UID остановлен с ростом OUTPUT-drop, обычный UID прошёл к тому же IP/порту. UID и destination не доказывают QNAME/client attribution, привилегированный обход, fail-closed при отказе или release readiness. См. `docs/lab-21-tproxy-unbound-output-uid.md`.
- **Два реальных Unbound в namespace (только VM):** test-only probe запускает выбранный и обычный resolver из двух offline-конфигов, fake loopback DNS-stub и внешний тестовый origin; generated ordinary nft + DNS INPUT/PREROUTING guards применяются только в router namespace. UDP/TCP-запросы одного имени дали разные ответы через stub/origin и независимое кэширование; локальная запись и explicit forward сохранили приоритет у обоих. Cross-listener и прямой selected DNS блокировались с ростом нужных счётчиков. Это не реальный sing-box и не продуктовая изоляция OUTPUT/UID или fail-closed при отказе; см. `docs/lab-20-tproxy-two-unbound-dns-cache.md`.
- **Offline INPUT-разделение DNS listener:** `generate_tproxy_dns_listener_guard` выводит отдельную nft-таблицу с hook INPUT -10. Выбранный ingress на локальном IPv4 `:53` допускает только selected listener IP, другой ingress не может обратиться к selected IP; модель адресов общая с offline Unbound split. VM с отдельными UDP echo на двух IP показала, что без guard запросы к чужому listener проходят, с guard тот же установленный UDP tuple блокируется с положительными INPUT/`ct state established` счётчиками, после удаления снова проходит; own-listener пути сохранились. Отдельный запрет входа не с `lo` к будущему `127.0.0.1:15353` прошёл лишь `nft -c`, не packet test. Это не два работающих Unbound и не контроль OUTPUT, TCP, DNAT или apply. См. `docs/lab-19-tproxy-dns-listener-boundary.md`.
- **Два изолированных DNS-конфига (пока только текст):** offline `generate_tproxy_unbound_split` создаёт selected Unbound с собственными IPv4 listener, локальными записями/явными forwards и default forward на предполагаемый loopback DNS-stub `127.0.0.1@15353`; обычный Unbound остаётся с прежними upstream. Неизвестные/общие адреса, IPv6 listener, explicit root forward и recursive mode отвергаются. Оба файла прошли `unbound-checkconf` на одноразовой VM; `do-not-query-localhost: no` необходим — без него checkconf выдаёт предупреждение и stub не используется. Это не два запущенных resolver, не source-isolation или защита OUTPUT; продуктовые генераторы/apply не меняются. См. `docs/lab-18-tproxy-unbound-split-config.md`.
- **Экспериментальный DNS ingress guard:** отдельный offline-генератор `generate_tproxy_dns_ingress_guard` строит PREROUTING -110 drop только для IPv4 TCP/UDP `:53` выбранных источников к нелокальным адресам, local возвращает; выключение удаляет лишь свою таблицу. Не подключён к bundle/apply/boot. На одноразовой VM с тестовым UDP echo (не DNS) тот же выбранный socket дошёл до origin до guard, блокировался после установки с ростом счётчика, после явного off снова прошёл. Локальный `:53`, невыбранный `lan1` и другой порт не блокировались. TCP, DNAT-исключения, общий кэш/OUTPUT Unbound и аварийный lifecycle остаются открытыми; см. `docs/lab-17-tproxy-dns-prerouting-guard.md`.
- **Unbound OUTPUT вне FORWARD guard:** на одноразовой VM после отдельной установки Unbound действующий TProxy-off DNS baseline прошёл 8 UDP/TCP этапов. Дополнительная VM-проба добавила lab-only FORWARD drop для выбранного `lan0` и узкий последующий allow UDP/53. Запрос клиента к локальному Unbound с новым именем дошёл от WAN-адреса роутера до тестового origin, не увеличив счётчик guard; прямой запрос того же клиента на origin был остановлен guard до последующего allow. Это пакетное доказательство границы INPUT→Unbound OUTPUT **при TProxy off**, не доказательство нарушения разрешённых explicit forwards или утечки при TProxy on. Нужны источник-ориентированное разделение DNS до кэша и отдельная OUTPUT-авторизация с сохранением разрешённых forwards. См. `docs/lab-16-tproxy-unbound-output-boundary.md`.
- **UDP/53 boundary на VM без Unbound:** сгенерированные ordinary firewall + lab preauth оставили локальный UDP-сервис доступным выбранному `lan0`; без guard выбранный источник дошёл напрямую к внешнему `:53` (небезопасный контроль). Заранее установленный FORWARD containment заблокировал повтор на том же established UDP tuple, не задев локальный сервис и невыбранный `lan1` к тому же внешнему `:53`; explicit off вернул ordinary forwarding. Использованы только ASCII-токены и fake UDP echo на порту 53 — **не** настоящий DNS/Unbound/sing-box, не защита OUTPUT, не автоматический crash guard. См. `docs/lab-15-tproxy-dns-source-guard.md`.
- **DNS source-boundary блокер:** действующий Unbound компилирует общий listener/forward/cache без признака TProxy-источника. Offline контрпример с общим `dns.upstreams` дал одинаковые Unbound и ordinary firewall конфиги при изменении TProxy intent (через test-only `model_copy`); публичный `tproxy.not_available` остаётся. Выход Unbound имеет идентичность процесса роутера, не исходного клиента; одного `meta skuid` sing-box недостаточно для DNS split/fail-closed. Нужны источник-ориентированная развилка до общего кэша и независимый контроль внешнего DNS с сохранением явных forwards. Это анализ, не VM-on proof; см. `docs/tproxy-dns-source-boundary.md`.
- **DNS baseline при explicit off:** отдельная VM-only проба действующих Unbound/nftables без sing-box подтвердила локальную A-запись, явный upstream forward, `NXDOMAIN` для неизвестного имени и FORWARD-блокировку прямого UDP/TCP DNS к синтетическому origin. Клиентские UDP/TCP запросы проверены захватом входа/выхода и приложением; Unbound меняет upstream ID и может отвечать из cache, поэтому тест использует разные QNAME. Это **не** проверка DNS при включённом TProxy или fail-closed; см. `docs/lab-14-tproxy-dns-off-baseline.md`.
- **UDP UID-scoped OUTPUT в VM:** постоянный клиентский UDP tuple после `ct state established` прошёл через INPUT и был остановлен заранее установленным OUTPUT drop для socket UID sing-box (drop +1, origin wire/receiver 0); другой UID дошёл до того же destination, recovery/off подтвердили разделение. Это только IPv4 UDP direct-эхо, не DNS, не атрибуция исходному клиенту и не автоматический отзыв при отказе. Лабораторные правила не подключены к продукту. См. `docs/lab-13-tproxy-udp-output-uid.md`.
- **Совмещённая TCP VM-проба:** после удаления interception привилегированное правило выставило proof bit за reset и вновь доставило established TCP token при отсутствующем OUTPUT-отзыве. На отдельном healthy established socket та же коллизия прошла INPUT, но заранее установленный UID-scoped OUTPUT drop не пропустил новый token к origin (UID drop +5); другой UID на том же destination tuple прошёл. Это показывает разделение защитных точек, **не** автоматическое обнаружение отказа или гарантию закрытия до него. См. `docs/lab-12-tproxy-combined-tcp-fault.md`; INPUT proof не исправлен, продуктовый gate закрыт.
- **UID-scoped OUTPUT-проба на VM:** sing-box с тестовым UID `29090` и `CAP_NET_RAW` сохранил transparent TCP listener и реальный proxy-тракт. `meta skuid 29090` в OUTPUT `-20` заблокировал новый токен установленного proxy TCP, в то время как другой процесс с UID `29091` дошёл до **того же** origin адресу/порту; отдельные счётчики, ingress и origin подтвердили оба пути. Это более узкая изоляция, чем destination-only guard, но UID не выражает исходную клиентскую политику и не защищает от root/socket passing; UDP/DNS и жизненный цикл процесса не доказаны. Только лабораторная проверка, не подключено к apply. См. `docs/lab-11-tproxy-output-socket-uid.md`.
- **Отдельная VM-only OUTPUT-проба:** лабораторный destination-scoped OUTPUT hook `-20` заблокировал новый токен установленного TCP-потока при работающем proxy (ingress и INPUT observer положительны, OUTPUT drop +5, origin не получил токен). Соседний router-originated порт прошёл, после отзыва ограничения новый proxy-поток восстановился, explicit off вернул ordinary forwarding. Это **не** авторизация по владельцу sing-box и не привязка исходного клиента к proxy outbound: любое другое локальное приложение к тому же tuple попало бы под тот же drop. Реализация отдельно от bundle/apply; подробности `docs/lab-10-tproxy-output-revocation.md`.
- **Дополнительный TCP-блокер:** VM-only проба с инъекцией только proof-бита `0x200` после его reset (`PREROUTING -84`) доставила новый post-fault токен по established proxy TCP после удаления interception: INPUT proof drop 0, proxy OUTPUT +2, origin получил payload. Та же инъекция до reset (`-86`) блокировалась (drop +6). `meta mark` нельзя считать неподделываемым proof при конкурирующем привилегированном nft writer; нужен дизайн владения marks/hooks либо другая независимая INPUT-авторизация. См. `docs/lab-09-tproxy-mark-collision.md`. Экспериментальные правила не входят в продукт; публичный gate не открыт.
- **TCP-блокер подтверждён:** established proxy TCP продолжил передавать новые данные после удаления interception через unmarked INPUT и отдельный proxy OUTPUT; FORWARD guard не сработал. Baseline TCP-проба остаётся red. Отдельная lab-only INPUT proof-проба (reset proof на каждом packet, выставление после успешного TProxy, независимый INPUT drop до established accept) прошла, включая fault/recovery и fresh explicit-off controls. Это не продуктовая интеграция и не OUTPUT/buffered-byte containment; результаты и ограничения — `docs/lab-08-tproxy-tcp-input-proof.md`.
- Расширение UDP combined-пробы удерживает один socket/source port через deny/default deny, crash, удаление interception/local route/policy rule и recovery. Observer ядра подтвердил `ct state established` перед preauth для каждого повторного запроса; запрещённые токены не достигли origin, включая поздние контрольные окна. Explicit off вернул тот же tuple к обычному forwarding. Это ограниченная established UDP-проба, не TCP/lifecycle/OUTPUT authorization; см. дополнение `docs/lab-07-tproxy-combined-udp.md`.
- Совместная VM-only UDP-проба preauth + настоящий sing-box + containment прошла: firewall deny/default deny не обходит перехват; SIGKILL, потеря interception, local route или policy rule не доставили новые токены origin; explicit off вернул ordinary forwarding с сохранением default deny. Proxy OUTPUT подтверждён отдельно от FORWARD, guard drop подтверждён при потере interception. Лабораторные interception/INPUT/mark не подключены к продукту; established flows, TCP, OUTPUT authorization, исключения с containment и lifecycle ещё не доказаны. См. `docs/lab-07-tproxy-combined-udp.md`.
- **Обнаруженный блокер:** upstream закрепляет форк `hoaxisr/amnezia-box` `1.15.0-alpha.9-awgm.30`, но его карта бинарников содержит только mipsel/mips/aarch64, без amd64; адреса загрузки — HTTP с проверкой встроенного SHA256 (`internal/singbox/installer/embedded.go:4–16`). Нельзя утверждать, что есть готовый проверенный Debian amd64-бинарник или переносить hash другого CPU. До сетевого этапа выбрать/собрать совместимый релиз для целевой архитектуры и зафиксировать его собственный hash и происхождение.
- **Проверенная альтернатива для пробы (не выбор для установки):** официальный `SagerNet/sing-box` v1.14.2, `sing-box-1.14.2-linux-amd64.tar.gz`, SHA256 `a684484d7477d1437282ee411f4d131d0340aaad60a7868841ebd5d87dd8a0c6` совпал с `digest` GitHub release asset; локально исполняется как `linux/amd64`, теги `with_wireguard` (нет `with_awg`). Сгенерированный из `backend/src/vs_router/generators/singbox.py` конфиг с IPv4 TCP/UDP TProxy (оба listen `127.0.0.1`), логическим OR домена и IP и reject/direct прошёл `sing-box check -c` и ограниченную пакетную пробу на Debian 13 VM (`docs/lab-05-singbox-tproxy.md`). Изначальный вариант TCP REDIRECT с listen `127.0.0.1` прошёл синтаксическую проверку, но **не принимал реальные соединения**; заменён на TCP TProxy. Проверка не доказывает безопасность firewall/DNS/релиза или поддержку форкового AWG-outbound. Перед закреплением по ADR-0005 нужны проверка доверия к релизу и матрица протоколов.
- Не переносить `type: awg` и форковые поля из upstream в официальный sing-box: нужен отдельный проверенный вариант выхода через существующий WG/AWG-интерфейс или подходящий бинарник. На отдельной Debian 13 VM подтвердить поддержку TCP/UDP transparent proxy, конфигурационного теста, локальных/remote rule-set, DNS, выбранных proxy-протоколов, WG/AWG-выходов через интерфейс и диагностического API. Проверить права и форматы перечисленных репозиториев, доступность зеркал и режим без сети.
- Спроектировать отдельную предварительную авторизацию пакетов до TProxy: `prerouting`-перехват после DNAT не должен обходить текущую default-deny политику FORWARD; `ct status dnat`/port-forward сохранить, запрещённые и нераспознанные источники блокировать. Guard требуется до `established,related`, с независимым от службы sing-box lifetime, покрытием reboot/неудачного apply и запретом ухода через WAN при потере policy route/туннеля. IPv6 WAN-эскейп закрыть отдельно. Выделить mark/table/ports и сверить конфликты. Не переписывать nft, пока нет проверяемой матрицы отказов.
- **Gate:** прототип на disposable VM доказывает TCP/UDP, DNS, обход петли, сохранение панели, port forward, firewall deny, отключение и падение sing-box без утечки. Без этого не открывать функцию в UI.

### 1. Контракт и контролируемый процесс
- В `backend/src/vs_router/schema.py` и `validators.py` добавить отключённую по умолчанию секцию: ingress, политики/упорядоченные правила, выходы/группы и ссылки, DNS, bypass, расписание и пределы. Типы в `frontend/src/types.ts`, тестовые фикстуры, JSON snapshot и миграции согласовать; старые версии должны загружаться выключенными. Секреты прокси/подписок шифровать как существующие, возвращать redacted; различать сохраняемый намеренный статус и наблюдаемый runtime-статус.
- Чистый детерминированный генератор sing-box-конфига + интеграция с nftables-генератором (`generators/nftables.py`), независимым управляемым policy route. Не добавлять правила вручную поверх таблицы `inet vs_router`: она полностью пересоздаётся. Инициализация/остановка маршрутов и процесса — только через типизированные методы агента; без произвольного shell/API исполнения.
- Extend `agent/apply.py`: `FILES`, validators, подготовка, атомарная активация/компенсация, readiness перед включением перехвата и проверка доступности после. Существующий порядок применяет nft первым: для TProxy его менять осознанно, чтобы не открыть трафик до готовности защитного состояния. Учесть rollback, первый apply и старые snapshots без sing-box-файла. В `agent/boot_restore.py` восстановить защиту **до** открытия сетевого тракта и не подтверждать pending-версию при reboot. systemd-зависимости/ограничения прав: ровно нужные capabilities и запрет вывода секретов/конфига в журналы/preview.

### 2. Правила, DNS и источники
- Правила: first-match, порядок, логическая OR для «пресет **или** введённые адреса» при сохранении общих ограничителей; ссылки на rule-set и outbound валидировать. Пресеты из перечисленных источников; версия/обновление/rollback используемого набора отдельно от snapshot. Планировщик и downloader в agent, read-only runtime API в web; ручной запуск — типизированный whitelist RPC с авторизацией. Автоматическое обновление не должно обходить один активный цикл применения: сериализовать activation с apply/rollback.
- DNS: объединить локальные overrides/forwards Unbound и DNS-политику sing-box без циклов и перехвата DNS роутера; локальная зона и управление работают при падении движка, внешние запросы выбранных источников не утекают. Системные исключения для управления, proxy endpoint, DHCP и туннелей.
- **Gate:** по отдельности DNS localhost/local override/forward/remote, explicit DNS:53, DoH как документированное ограничение, истёкшие/битые/недоступные списки, регулярный и ручной запуск, откат списка во время общего apply.

### 3. Прокси/подписки и интерфейс
- Добавить исходящие sing-box-прокси и подписки: импорт ссылок/файлов и ревизию форматов из AWG Manager; секреты, проверки TLS, запрет открытых административных inbound по умолчанию. `direct`, `block`, WG/AWG-клиенты, selector/urltest/резервные группы; не выдавать исходящий Caddy за VPN-прокси. Серверные WG/AWG-пиры не становиться outbound. Контроль выбора WAN/детура при недоступном туннеле, защита от рекурсивного outbound и DNS loop.
- React/MUI: пункт меню «Маршрутизация», мастер включения с предупреждением об IPv6/потере связи, простой визард (источник → признаки/пресет → выход → предпросмотр), экспертные редакторы правил/rule-set/outbound/DNS/bypass, drag/move порядка, diff перед общим apply, статусы enabled/ready/intercepting, списки соединений/логи/инспектор/предпросмотр **без секретов**. Сохранять только черновик до общего применения; не копировать upstream's немедленное применение отдельных настроек. Ошибки видимы (`ErrorNotice`), асинхронные действия обработаны.
- **Gate:** фронтенд-сценарии CRUD/invalid/empty/error, typecheck/build, доступность редактирования для администратора и read-only для оператора, отсутствие секретов в API, UI, logs и inspector.

### 4. Пилот и выпуск
- На разрешённой disposable Debian VM: обычная сеть + VLAN/VPN, firewall deny, DNAT, WG/AWG и несколько proxy-протоколов; трасса HTTP/TLS/QUIC/DNS, IPv6, unassigned/WAN ingress, reboot/rollback, смена WAN-IP, потеря rule-set, отсутствие интернета и переполнение диска. После — отдельный пилот на выделенном сегменте, не на Keenetic пользователя.
- Документировать производительность/userspace, влияние правил на задержку и память (минимум продукта 2 vCPU/2 GiB), лимиты хранилища/трафика, аварийное выключение из локальной консоли и восстановление управления. Release gate: никакого выставления пункта как «готово» до прохождения VM-сценариев.
