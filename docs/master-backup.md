# Резервная копия мастер-портала

`vs-master-backup.timer` ежедневно запускает `vs_master.backup` от пользователя `vs-master-web`. Копирование SQLite через online backup API согласовано с WAL; перед публикацией проверяется `PRAGMA integrity_check`, затем временный файл атомарно переименовывается. Каталог `/var/lib/vs-router/master/backups` имеет режим `0700`, файлы — `0600`; сохраняются семь последних копий. При ошибке существующие копии не удаляются. Отсутствующая или неинициализированная база не заменяется пустым файлом.

**Граница защиты:** это только локальные копии на том же VPS. Нет зашифрованной передачи на ноды, станцию либо в Telegram и нет гарантии восстановления после потери VPS. База содержит персональные данные; не публиковать и не прикладывать к тикетам. Ключ `VS_ROUTER_SECRET_KEY` хранится отдельно в `/etc/vs-router/master.env` и **не входит** в SQLite-копию; без него сохранённые токены нельзя расшифровать. Его резервирование и проверка восстановления требуют отдельного защищённого канала и явного операционного решения.

Для проверки восстановления используйте отдельную изолированную машину/каталог, скопируйте туда один backup и отдельно восстановите ключ; выполните `PRAGMA integrity_check`, миграции и вход в тестовый мастер без доступа к рабочим нодам. Не заменяйте действующую базу на работающем сервере и не запускайте два мастера с одним bridge-токеном.

## Внехостовой backup и проверка ключа (практика 19.11.2026)

Порядок, применённый к `.130` после независимого подтверждения host key из VNC-консоли провайдера:

1. SSH только fleet-ключом с `BatchMode=yes`, `StrictHostKeyChecking=yes` и отдельным `UserKnownHostsFile`; живой ED25519-key сверяется с записанным до любой передачи данных.
2. Свежая согласованная копия прямо из работающего мастера: `sqlite3.connect('file:/var/lib/vs-router/master/vs-master.db?mode=ro', uri=True)` → `connection.backup(dst)` в `/var/lib/vs-router/master/backups/offhost-<UTC>.db`, режим `0600`. Так же копируется `/var/lib/vs-router/vs-router.db` локального портала — после переноса только master DB его живые пиры потерялись бы.
3. На копии: `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, revision из `alembic_version`, SHA-256; затем `scp` в защищённую папку оператора и повторная сверка хэша и ACL.
4. `/etc/vs-router/master.env` копируется отдельно и никогда не печатается в чат/логи. Проверка ключа: `get_secret_key()` + `Fernet.decrypt()` значения `ciphertext` из JSON-колонок `SecretJSON` (`master_nodes.bridge_token`, `master_devices.private_key`, `master_device_subscriptions.token_secret`). Успешная расшифровка доказывает, что ключ подходит к этой БД.
5. Restore-драйл: isolated scratch-каталог, `VS_MASTER_DATABASE_URL=sqlite:///<copy>` + `alembic-master upgrade head` (на копии), без запуска worker/bot и без доступа к живым нодам. Открытие SQLite для проверки может создать `-wal`/`-shm`; после проверки удалите их.

`master.env` и `secrets.env` на хосте содержат переменную с одним и тем же именем `VS_ROUTER_SECRET_KEY`; само наличие переменной ещё не доказывает, что ключ подходит к конкретной БД. Проверка п. 4 обязательна: она ловит рассинхрон ключа до cutover, а не после.
