# Экспериментальный PREROUTING guard для прямого DNS

## Объём

Новый **offline-only** генератор `generate_tproxy_dns_ingress_guard()` строит отдельную nft-таблицу `inet vs_router_tproxy_dns_ingress`. Входящий IPv4 TCP/UDP с выбранных интерфейсов к **нелокальному** `:53` отбрасывается до обычного DNAT, preauth и маршрутизации; локальный адрес роутера возвращается без блокировки. При выключенном намерении генератор выдаёт удаление только своей таблицы. Генератор **не подключён** к bundle, apply, boot restore, агенту или UI. Публичное `enabled=True` по-прежнему отвергается `tproxy.not_available`; только offline fixture использует `model_copy` после валидации выключенной версии.

Это узкая защита от прямого DNS по стандартному порту, а не DNS split: общий Unbound по-прежнему теряет источник до кэша, а его OUTPUT может идти к WAN (`docs/lab-16-tproxy-unbound-output-boundary.md`). Правило не покрывает нестандартные порты, DoH/DoT или IPv6; DNAT на внешний DNS `:53` выбранного клиента консервативно блокируется до преобразования, а значит исключения port forward ещё нужно спроектировать.

## Пакетная проверка

Разрешённая одноразовая Debian VM `vsr-verify-20261002`, четыре изолированных network namespace: router (`lan0`, `lan1`, `wan0`), выбранный и невыбранный клиенты, origin. В root namespace VM не применялись nft/сетевые правила. Реальные конфиги ordinary firewall, preauth, containment и новый guard получены генераторами из test-only snapshot; каждый этап перед применением прошёл `nft -c` **в router namespace**. Локальный и внешний `:53` — тестовые UDP echo, **не DNS/Unbound**. Один UDP socket выбранного клиента сохранялся через включение и выключение guard. AF_PACKET ingress/origin, receiver и счётчики проверялись отдельно.

| Этап | Наблюдение |
| --- | --- |
| До guard, выбранный → внешний `:53` | Origin получил токен: небезопасный контроль с обычным разрешающим firewall. |
| Guard включён, выбранный → локальный `:53` | Локальный receiver и ответ подтвердили доступность. |
| Тот же выбранный UDP socket → внешний `:53` | Ingress увидел токен; ответ timeout, origin wire и receiver пусты; `tproxy_dns_direct` counter вырос. |
| Невыбранный `lan1` → тот же origin `:53`, выбранный → origin `:19090` | Оба доставили токены; узкая область правила подтверждена. |
| Удаление DNS guard при сохранении обычных правил | Выбранный клиент снова достиг origin `:53`; затем обычный FORWARD containment показал прежние local/direct и explicit-off сценарии. |

VM probe завершился `guest exit: 0`, все именованные этапы `PASS`. В отдельной проверке сгенерированный файл прошёл `nft -c -f` на VM. Backend-тесты проверяют детерминизм, порядок local-before-drop, недопустимые источники, отсутствие live activation и явное off.

## Нерешённое

UDP-эхо не доказывает TCP DNS, обработку фрагментов IPv4, настоящий Unbound, разделение выбранных/невыбранных запросов до общего кэша, сохранение explicit forwards при отказе, защиту Unbound OUTPUT, полный fail-closed TProxy, конфликт nft hook либо безопасность apply/reboot. Даже если прямой `:53` заблокирован, локальный resolver остаётся отдельным выходным путём. Не открывать `tproxy.not_available` на основании этого опыта.
