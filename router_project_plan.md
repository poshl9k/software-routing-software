## Цель и границы MVP

Создать устанавливаемый на выделенную Linux-машину или VM роутер с современной веб-панелью. В MVP администратор может настроить сеть, DHCP/DNS, firewall, два типа VPN-туннелей, входящие сайты и DDNS без ручного редактирования конфигурационных файлов. Ошибочное изменение сетевых параметров можно откатить из панели или автоматически по таймеру.

За визуальный референс принят концепт главного экрана из обсуждения: тёмное левое меню, светлая рабочая область, компактные таблицы, явные состояния сервисов, умеренные синие и зелёные акценты. Рабочее имя продукта — **vs-router**; финальное имя/бренд — отдельное решение перед пилотом.

**Не входит в MVP:** маршрутизация по доменам/IP/CIDR как пользовательский конструктор политик, полноценный магазин модулей, динамические протоколы маршрутизации, HA-кластер, собственный установочный образ ОС, второй WAN и переключение, 2FA, роль оператора в UI. Архитектурные точки расширения для них закладываются заранее. Псевдонимы firewall и их импорт/экспорт, напротив, входят в MVP.

## Принятые решения (сводка сессии проектирования)

| Область | Решение |
| --- | --- |
| Пользователь | Продвинутый домашний/prosumer-админ или админ малого офиса; один администратор. Панель — только из LAN/VPN, HTTPS всегда, 2FA после MVP |
| Применение конфигурации | Черновик (persisted-версия) применяется целиком; подтверждение — явное действие; перезагрузка не подтверждает конфиг; один активный цикл применения |
| «Безопасная настройка» | Параметр панели, по умолчанию выключен; включает окно подтверждения (60–600 с, дефолт 180), маркер с дедлайном на диске, автооткат по таймеру через механизм на хосте и пробу доступности панели; предлагается включить в onboarding-мастере |
| Архитектура | Непривилегированный FastAPI-бэкенд + привилегированный агент; канал — unix socket с проверкой peer-credentials; whitelist RPC-методов; агент — источник истины аудита |
| Платформа | Debian 13 stable (Ubuntu — следующий поддерживаемый дистрибутив; ADR-0001); AmneziaWG userspace в MVP, kernel-модуль — целевая форма после MVP |
| DNS | Unbound: forwarding по умолчанию, рекурсия опцией; per-domain forwards, host overrides, привязка к интерфейсам, журнал запросов с ротацией |
| DHCP | Kea DHCPv4: конфиг-файл — источник истины (`kea-dhcp4 -t` + config-reload); ctrl-agent (unix socket) — чтение аренд/статистики; резервации внутри и вне пула |
| Firewall | Модель pfSense: правила на зоне входа (вкладки зон), first match wins, pass/block/reject, неявный default deny, anti-lockout, счётчики правил; зоны wan/lan/router, неназначенный интерфейс fail-closed |
| NAT | Port forward — отдельный список с автогенерируемыми filter-правилами; outbound NAT в режимах pfSense (авто/гибрид/ручные/выкл) с выбором translation address и флагом «Do not NAT» |
| WAN-адреса | Упорядоченный список реальных адресов на WAN-интерфейсе: основной + дополнительные (/32), равноценны в правилах; без типов VIP |
| Псевдонимы | Типы «Адреса» и «Порты»; вложенность только совместимых типов, циклы запрещены; пересечения — предупреждение; лимиты 10 000 (warn) / 100 000 (error) |
| Туннели | Туннель = интерфейс + роль (сервер/клиент, не меняется после создания) + протокол (wg/awg); AllowedIPs ≠ маршрут; импорт сторонних .conf; экспорт сервера — пакет клиентских конфигов/QR |
| Caddy | Режимы сертификата: Auto HTTP-01 (привязка к WAN-адресу), Auto DNS-01 (если провайдер поддерживает), ручной, TLS passthrough (по результату проверки L4); `caddy validate` + graceful reload |
| DDNS | Cloudflare + RFC 2136; адаптерная архитектура; журнал обновлений и ошибок |
| Бэкап | Экспорт — зашифрованный архив (пароль админа; без него секреты не восстанавливаются); локальный автобэкап по расписанию с секретами |
| Безопасность панели | Собственный CA роутера + серверный сертификат при первом старте; argon2id; локальные учётки; rate limit на login; CSRF/origin-защита |
| Масштаб MVP | До 20 интерфейсов / 10 зон; 10 подсетей / 500 аренд; 500 правил; 100 алиасов (10 000 элементов); 10 туннелей / 50 пиров; 20 сайтов; 1 Гбит/с NAT; min 2 vCPU / 2 ГБ RAM / 16 ГБ |
| Обновления | Ядро Linux — только при уязвимостях; компоненты — фиксированные версии, обновления по безопасности/блокирующим дефектам; после обновления ядра обязательная проверка туннелей и сетевого стека |
| Локализация | i18n с первого дня; русский по умолчанию; общепризнанные термины на латинице; системные идентификаторы фиксированы на латинице |

## Предлагаемая техническая основа

| Область | Базовый выбор | Особенность интеграции |
| --- | --- | --- |
| Платформа | Debian 13 stable; Ubuntu — следующий поддерживаемый дистрибутив (ADR-0001) | Фиксируемые версии пакетов; установщик проектируется с учётом добавления второго дистрибутива без смены архитектуры |

| DNS | Unbound | Forwarding по умолчанию; per-domain forwards, host overrides, привязка к интерфейсам; `unbound-checkconf` перед применением |
| Туннели | WireGuard и AmneziaWG (userspace `amneziawg-go`) | Единая модель маршрутов/состояний; явная роль сервер/клиент; kernel-модуль AmneziaWG — после MVP |

| Backend и UI | FastAPI + React/TypeScript + MUI | Backend хранит желаемое состояние; привилегированный агент применяет его через unix socket RPC |
| Хранилище панели | SQLite на одной машине для MVP | Шифрованный бэкап и миграции схемы; ротация журналов; секреты не возвращаются API открытым текстом |

### Поведение псевдонимов в MVP

Псевдоним — именованный типизированный объект, а не текстовая подстановка. Начальные типы: `Адреса` (IPv4/IPv6 хосты, CIDR, диапазоны) и `Порты` (отдельные порты и диапазоны TCP/UDP). Группы могут содержать элементы и другие псевдонимы совместимого типа. UI показывает раскрытое содержимое, количество итоговых элементов, места использования и ошибки компиляции. Вложение с циклом запрещено; пересечения содержимого алиасов допустимы и показываются как предупреждение.

Импорт JSON переносит имена, описания, типы, элементы и связи между группами; версия схемы формата фиксируется. CSV/TXT предназначены для обмена простыми списками адресов или портов; экспорт выдаёт файл того же уровня сложности. Импорт не применяет изменения сразу: сначала проверка и предпросмотр, затем подтверждение с обычным механизмом отката конфигурации.

Возможное расширение после MVP: FQDN-псевдонимы, списки по URL с расписанием обновления, готовые наборы RFC-сетей, географические и ASN-группы. FQDN означает динамический набор полученных DNS-адресов и не гарантирует соответствия каждому соединению по доменному имени; его следует вводить вместе с диагностикой DNS-обновлений. Для внешних URL-источников нужны ограничения размера, частоты и доступных адресов загрузки.

    невидимой системной зоной (правила «этот роутер»), либо явно исключить из пользовательского
    списка. Согласовать с `CONTEXT.md`/ADR перед реализацией.
- **Ссылки:** макет `mockups/firewall.html`; текущий код `frontend/src/pages/Firewall.tsx`,
  `frontend/src/types.ts:35` (`FirewallRule.ingress_zone`), `frontend/src/editor.tsx` (`nameValid`).
- **Статус:** в плане, не начато.

### Firewall: встроенные псевдонимы (system aliases) + автодополнение в полях правил

- **Зачем:** В pfSense/OPNsense есть системные псевдонимы, которые создаются автоматически и
  динамически обновляются при смене настроек интерфейсов: *This firewall (Self)* — все IP роутера
  (WAN/LAN/loopback/VPN); *[iface] address* — IP конкретного интерфейса; *[iface] net* — подсеть
  интерфейса. Сейчас в vs-router алиасы только пользовательские (`schema.py:30-34`, `types.ts:126`),
  а поля src/dst — обычные `TextField` без подсказок (`Firewall.tsx:241-254`), alias-ы ссылаются
  через `@` (`endpointValid`, `editor.tsx:36-42`), но системных имён нет и вводить их вслепую
  неудобно.
- **Объём (2 части по требованию):**
  1. **Встроенные псевдонимы (system aliases):**
     - Набор: `This firewall` (Self — все адреса роутера: WAN, LAN и прочих iface/VLAN, loopback
       127.0.0.1, терминируемые VPN), `<iface> address` (IP интерфейса), `<iface> net` (подсеть
       интерфейса с маской). По аналогии с pfSense для каждого интерфейса из `interfaces[]`
       (`schema.py:22-26`, поля `addresses`).
     - **Генерация:** вычисляются (не хранятся в пользовательском списке `aliases`), либо помечаются
       `system: true` — чтобы автоматически отражали текущие настройки интерфейсов (динамическое
       обновление «бесплатно» при любой правке интерфейса). Исключить из импорта/экспорта
       (`api/aliases_io.py`) и из редактирования/удаления пользователем.
     - **Разрешение:** при применении nftables-генератор (`generators/nftables.py`) раскрывает
       ссылки на системные псевдонимы в реальные IP/подсети (как сейчас раскрывает `@useralias`).
  2. **Автодополнение (typeahead) в полях правил:**
     - В полях Источник/Назначение (endpoint), Порт (`destination_ports`), и аналогичных — при вводе
       показывать выпадающий список всех алиасов (пользовательских + системных), отфильтрованный по
       набранному тексту (как MUI `Autocomplete`/`TextField` с `Listbox`, либо расширить
       `Field`/`editor.tsx`).
     - Источник подсказок = объединение: пользовательские `aliases` (`c.aliases`), системные
       псевдонимы (из пп. 1), зарезервированные токены (`any`, `zone:<зона>` — уже поддержаны
       `endpointValid`/`Firewall.tsx:245,252`), возможно `self`.
     - Синтаксис ссылки: у пользовательских — `@имя` (как сейчас). Для системных решить именование
       (см. Ограничения) — единый путь разрешения с `@`.
- **Ограничения:**
  - **Открытое решение (именование системных алиасов):** `nameValid` (`editor.tsx:3`) запрещает
    пробелы, а pfSense-имена вроде «LAN net»/«LAN address» их содержат. Либо перевести на
    `snake_case`/`@self`, `@lan_net`, `@lan_address` (совместимо с `@`-грамматикой), либо расширить
    грамматику `endpointValid`/`addressElementValid` отдельным видом токенов (например,
    `zone:lan:net`). Решить до реализации; не ломать `endpointValid`.
  - Системные алиасы не должны попадать в `aliasValid`/`allValid` как пользовательские
    (`Firewall.tsx:38-43,101-125`) и не должны быть удаляемы (`remove`, `Firewall.tsx:148`).
  - Сохранить семантику fail-closed и `saveDraft`; подсказки — только UX, не меняют контракт
    (валидный ввод остаётся валидным без автодополнения).
  - Учесть IPv4+IPv6 (подсказки/разрешение для обоих семейств, как `ipValid`/`addressValid` в
    `editor.tsx:12-35`).
  - **Ссылки:** `schema.py:30-34`, `types.ts:126`, `api/aliases_io.py` (экспорт/импорт),
    `generators/nftables.py` (разрешение `@`), `Firewall.tsx:241-254` (поля src/dst),
    `editor.tsx:36-52` (`endpointValid`/`addressElementValid`/`portElementValid`).
- **Статус:** в плане, не начато.

## Аудит первичной установки: открытые работы

Принятые границы и компромиссы: `CONTEXT.md`, ADR-0002 — ADR-0005.
Чекбоксы ниже остаются открытыми **до проверки на чистой Debian VM**;
формулировки и номера строк в них описывают исходный аудит, а не текущее
состояние кода. Часть защит уже видна в исходниках и host-free тестах:

| Область | Что подтверждено исходниками | Что ещё не доказано |
| --- | --- | --- |
| Этапы bootstrap | `run_stage` вызывает этап вне `if`; `stage_build` проверяет UI, `stage_install` — обязательные службы и `/health` через Unix-сокет (`backend/packaging/bootstrap.sh`). | Отказы этапов, перезапуск и доступность с отдельного LAN-клиента на чистой VM. |
| Первый доступ/ISO | Нормальный ISO выбирает интерактивную запись без предзаданного пароля и NOPASSWD; unattended-пароль допускается только явным lab-режимом (`installer/make-iso.sh`, `preseed-semiauto.cfg`). До назначения LAN входящий трафик ограничен `bootstrap.nft`; SSH замаскирован в `installer-prepare.sh`. | Полный цикл d-i → первый вход с LAN; отсутствие WAN-доступа к HTTPS/SSH и политика при одном порте. |
| Management/SSH | Console LAN, локальный HTTPS-probe до первого apply, запрет смены endpoint и интерфейсные настройки SSH с подтверждением WAN есть в агенте и UI. Kea-пароль загружается из ограниченного файла через systemd credential (`bootstrap.sh`). | Реальный apply/rollback/reboot, LAN/WAN reachability, Fail2Ban и Kea на VM. |
| Воспроизводимость/восстановление | ISO требует SHA-256 и фиксированный commit; bootstrap использует signed APT snapshot и временный root-owned каталог; `firstboot-bootstrap.sh` оставляет ручной `--retry`, install мигрирует БД (`make-iso.sh`, `bootstrap.sh`, `install.sh`). | Совместимость всего набора release inputs, воспроизводимость установки и восстановление после обрыва на VM. |

Успешный unit-тест или `bash -n` не подтверждает пакетную безопасность.

### P0 — доступ и безопасность

- [ ] Убрать скрытые ошибки этапов: `run_stage` вызывает функции в `if`, поэтому `set -e` внутри них не останавливает работу. Явно проверять критические команды; проверять сборку UI/wheel и запущенные обязательные сервисы до статуса успеха (`backend/packaging/bootstrap.sh:20-30,168-181,216-228`).
- [ ] Разделить «ПО установлено» и «готово к первому входу»: выбрать LAN и адрес с консоли, проверить доступность HTTPS с LAN, не публиковать панель на WAN. Создать первичный CA/сертификат, показывать отпечаток на консоли; сохранить системный HTTPS-маршрут панели после первого и всех следующих применений, зарезервировать адрес:порт (`bootstrap.sh`, `install.sh`, `generators/caddy.py`).
- [ ] Сделать обычный ISO интерактивным по умолчанию: пароль системной учётки задаётся в установщике, без `sudo NOPASSWD`; старый unattended-режим только явно выбранный лабораторный (`installer/make-iso.sh`, `preseed.cfg`, `preseed-semiauto.cfg`).
- [ ] До первого применения закрыть новые входящие соединения на интерфейсе установки, не ломая DHCP/исходящий трафик. SSH по умолчанию не доступен на нём; после настройки — интерфейсный список SSH в модели/UI/агенте, единое применение и откат. Для парольного SSH на WAN требовать защиту от перебора и отдельное подтверждение (`schema.py`, `generators/nftables.py`, UI, installer).
- [ ] Защитить первое применение: без автоотката, но запретить конфигурацию, удаляющую текущий LAN-порт, адрес или HTTPS-панель; предупредить о консоли. После первой подтверждённой версии смена пути к панели обязана использовать безопасную настройку (`agent/apply.py`, UI).
- [x] Дополнительная граница первого apply: при отсутствии host-owned записи о назначенном LAN агент отвергает применение до изменения файлов; локальный Unix-socket больше не считается успешной проверкой panel HTTPS. Host-free тесты покрывают отказ и подтверждённый HTTPS-путь; доступность с реального LAN/WAN остаётся в VM-критерии ниже.
- [x] При наличии management-записи, но недоступном локальном HTTPS, первое применение отвергается до любых файлов/маркера; без confirmed-снимка автоматический откат невозможен. Пакетная проверка доступа с отдельного LAN/WAN клиента остаётся обязательной.
- [ ] Не печатать пароль Kea в лог/трассировку; убрать секрет из открытого systemd drop-in, использовать ограниченный файл и проверить доступ web-сервиса (`bootstrap.sh:191-227`, `firstboot-bootstrap.sh:30`).

### P1 — воспроизводимость и восстановление

- [ ] Привязать ISO, репозиторий, Go/npm/Python-зависимости и пакеты к проверенному выпуску; проверять целостность загрузок. Не ставить непроверенные обновления даже ради security без теста совместимости (`installer/preseed*.cfg`, `bootstrap.sh:114-165,173-181`).
- [ ] Не отключать firstboot-service при ошибке; показать причину на консоли и дать явно повторить установку после исправления, без бесконечных авто-повторов (`firstboot-bootstrap.sh:30-40`).
- [ ] Мигрировать сеть без потери WAN: DHCP-fallback только для интерфейса установки, статический адрес на выбранном LAN, остальные без адреса; регистрировать временные файлы для удаления при первом apply; проверять успешность запуска networkd перед отключением прежнего менеджера. При смене MAC первичного LAN — блокировать публикацию панели до проверки с консоли (`bootstrap.sh:69-100`, `agent/services.py:94-121`).
- [ ] Повторный bootstrap на установленной машине не должен оставлять старые процессы или старую схему БД: переустановка wheel, миграция существующей БД и управляемый перезапуск сервисов; не менять CA, ключ шифрования и пользовательские настройки (`bootstrap.sh:177-217`, `install.sh:59-68`, `update.sh`).
- [ ] Не использовать общий `/tmp/vs-router-bootstrap` как доверенный каталог для root-сборки; ограничить доступ и проверять происхождение исходников (`bootstrap.sh:134-165`).
- [ ] Ограничить проверку платформы поддерживаемым Debian 13 или отдельно подтвердить совместимость Debian 12 (`bootstrap.sh:63-65`, `docs/install.md:3`).

### Проверка

- [ ] Покрыть повторный запуск, отказ каждого этапа, сбой сети/reboot, первый apply с пустой и безопасной конфигурацией, смену MAC/интерфейса, один физический порт и SSH WAN тестами на чистой Debian VM. Проверить доступность панели *с LAN* и отсутствие доступа *с WAN*, а не только `systemctl is-active` или локальный HTTP 200.
