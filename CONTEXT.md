# CONTEXT.md — Глоссарий домена «программный роутер»

Только термины и их значения. Без деталей реализации, без спеки.

## Пользователи и доступ

- **Администратор** — основной пользователь панели; полный доступ ко всем настройкам. В MVP — единственная реальная роль.
- **Оператор** — роль с ограниченными правами; заложена в модель данных, но в UI MVP не отображается.
- **Панель** — веб-интерфейс управления роутером. В MVP доступна только из LAN/VPN, не из WAN.
- **Целевой пользователь MVP** — продвинутый домашний/prosumer-админ или админ малого офиса; один администратор.

## Продукт и локализация

- **Рабочее имя продукта** — `vs-router` (virtual software router); финальное имя/бренд — отдельное решение перед пилотом.
- **Локализация** — i18n с первого дня; русский — язык по умолчанию, другие языки после MVP. Хардкод строк UI запрещён.
- **Технические термины** — общепризнанные термины на латинице (firewall, port forward, passthrough и т.п.), не переводятся во избежание недопонимания.
- **Системные идентификаторы** — имена интерфейсов и стандартных зон (`wan`, `lan`, `router`) — фиксированные латинские; локализуется только отображаемое имя.

## Конфигурация и применение

- **Черновик** — persisted-версия конфигурации со статусом `draft`; сохраняется в БД, переживает закрытие вкладки и перезагрузку. Один черновик за раз.
- **Версия конфигурации** — атомарная единица изменения; черновик применяется целиком, а не по блокам.
- **Подтверждение** — единственное явное действие в панели, фиксирующее применённую версию как `confirmed` (последнюю стабильную). Истечение таймера без действий — не подтверждение.
- **Откат** — восстановление конфигурации сервисов из последней `confirmed`-версии тем же механизмом, что и обычное применение (без отдельного «undo»-кода). Решение об откате принимает механизм на самой машине, а не веб-процесс.
- **Маркер** — файл на хосте вне БД, хранящий факт применения неподтверждённой версии и дедлайн отката. Перезагрузка не подтверждает конфигурацию: после загрузки маркер обрабатывается тем же таймером.
- **Окно подтверждения** — интервал после применения, в течение которого нужно подтвердить; по умолчанию 180 с, настраивается (60–600 с).
- **Пока предыдущий цикл не завершён (подтверждён или откачен), новый черновик применить нельзя.**
- **Проба доступности панели** — активная проверка самопрослушивания API после применения; при потере доступа — немедленный откат, не дожидаясь таймера.

## Безопасная настройка

- **Безопасная настройка** — параметр панели, включающий весь контур безопасного применения: окно подтверждения, маркер с дедлайном, автооткат по таймеру и пробу доступности панели.
- **По умолчанию выключена**: применение сразу фиксируется как `confirmed`, без окна подтверждения.
- **Первый старт (onboarding)** — мастер начальной настройки; один из шагов предлагает включить безопасную настройку с выбором длительности таймера.
- **Переключение** — в разделе «Настройки» в любой момент.

## DNS

- **DNS-сервис** — Unbound; режим forwarding по умолчанию, полная рекурсия — опция.
- **Локальная запись (host override)** — имя + тип + значение через `local-data`; переопределяет внешние ответы.
- **DNS-переадресация (per-domain forward)** — домен + upstream-адрес через `forward-zone`; домен уходит на указанный сервер (аналог DNS Forwards в dnsmasq).
- **Привязка resolver'а** — resolver слушает только выбранные интерфейсы (`interface:` + `access-control:`), не «все».
- **Журнал запросов DNS** — включаемое логирование с ротацией; в MVP — для диагностики.
- **Точка расширения доменных политик** — модель данных оставляет место для связки «DNS-ответ → адресный набор nftables» (после MVP).

## DHCP (Kea)

- **Конфигурация Kea** — генерируемый конфиг-файл, единственный источник истины; проверка `kea-dhcp4 -t` перед применением, затем `config-reload` без рестарта демона.
- **Control-channel** — ctrl-agent (REST по unix socket) только для чтения аренд/статистики и деликатных runtime-операций; конфиг через API не меняется.
- **Резервация** — конфигурационный объект (переживает ребут); возможна внутри динамического пула и вне его; Kea-оптимизация out-of-pool не включается.
- **Аренды** — читаются через ctrl-agent (`lease4-get-all`, `lease4-get-by-*`), поиск клиента по MAC/IP/hostname.

## Firewall

- **Зона** — группировка интерфейсов для firewall-политики; интерфейс ∈ ровно одна зона; неназначенный интерфейс не пропускает транзит (fail-closed). Стандартные зоны: `wan`, `lan`; встроенная зона `router` — трафик на сам роутер, вручную не назначается.
- **Правило firewall** — модель pfSense: привязано к зоне входа (вкладка на зону), направление «входящий на зону» трафик; поля: протокол, src-алиас, dst (зона/алиас/адрес), порт-алиас, действие `pass`/`block`/`reject`, лог-флаг, вкл/выкл.
- **First match wins**; порядок редактируемый внутри вкладки зоны; в конце — неявный default deny.
- **Anti-lockout** — авто-правило доступа к панели с LAN, отключаемое.
- **Счётчики правила** — states, packets, bytes на каждом правиле (nftables counter).
- **Port forward** — отдельный список правил NAT (как Firewall > NAT > Port Forward): интерфейс входа, протокол, внешний порт, цель + порт. К каждому — автоматически сгенерированное filter-правило (ассоциация, как в pfSense), отображается с пометкой «авто».
- **Port forward приоритетнее локальных сервисов роутера** на том же порту.
- **Outbound NAT (masquerade)** — режимы как в pfSense: `Автоматический`, `Гибридный` (дефолт при наличии доп. адресов: ручные правила + автоправила для остального), `Только ручные`, `Отключён`. Ручное правило: egress-зона, src/dst-алиас, протокол, translation address (основной адрес WAN | конкретный WAN-адрес | вручную), флаг «Do not NAT». First match wins. Пулы и EIM-NAT — после MVP. Outbound NAT не выбирает путь (это делает таблица маршрутизации).
- **Алиасы (псевдонимы)** используются как src/dst/порт в правилах filter и NAT — семантика совпадает с pfSense Aliases.

## WAN-адреса

- **WAN-адреса интерфейса** — упорядоченный список реальных адресов на WAN-интерфейсе: первый — **основной** (default для исходящего трафика и masquerade), остальные — **дополнительные** (например, диапазон реальных адресов от провайдера, /32 + обычный шлюз).
- **Равноценность** — все WAN-адреса доступны в правилах firewall, port forward и outbound NAT (как destination/translation address) без ограничений pfSense-VIP; различие только в том, какой адрес основной.
- **Дополнительный адрес — обычный вторичный адрес интерфейса** (networkd), без типов VIP.
- **Привязка сервисов** — сервисы (Caddy, DDNS) могут привязываться к конкретному WAN-адресу из списка.

## Псевдонимы (алиасы)

- **Типы** — `Адреса` (IPv4/IPv6, CIDR, диапазоны) и `Порты` (TCP/UDP, порты и диапазоны). Вложение только совместимого типа, циклы запрещены — ошибка.
- **Пересечения алиасов** — допустимы, показываются как предупреждение (не ошибка); несовместимое вложение, циклы и невалидные значения — ошибки.
- **Лимиты размера** — рекомендуемый предел (~10 000 итоговых элементов, предупреждение), жёсткий предел (~100 000, ошибка).
- **Импорт TXT адресов** — строка = IPv4/IPv6/CIDR/диапазон `a-b`; `#` — комментарий.
- **Импорт TXT портов** — только с протоколом: `tcp/80`, `udp/53`, диапазоны `tcp/1000-2000`.
- **Импорт CSV** — `value,description`, опциональный заголовок; описание → комментарий элемента.
- **Экспорт** — алиас в своём формате; полный JSON со связями (зафиксировано в плане).
- **nftables-sets** — адресные алиасы → наборы nftables; обновление содержимого без пересоздания правил.

## Туннели

- **Туннель** = интерфейс + явная роль (`сервер` | `клиент`) + протокол (`WireGuard` | `AmneziaWG`). Роль выбирается при создании и **не меняется после**; чтобы сменить роль — создаётся новый туннель.
- **Туннель-сервер** — слушает порт; пиры (клиенты) подключаются к нам; endpoint у пиров не задаётся.
- **Пир** — только у туннеля-сервера: ключ клиента + экспорт клиентского конфига (`.conf`/QR).
- **Туннель-клиент** — мы инициатор: endpoint сервера, AllowedIPs, keepalive; удалённый сервер не отображается как «пир».
- **Сервер и клиент одновременно** — отдельные туннели (каждый со своим интерфейсом), не один.
- **Протокол `AmneziaWG`** — добавляет обязательные параметры обфускации (Jc, S1, S2, H1–H4); совместимость профилей с клиентскими приложениями Amnezia подтверждается лабораторной проверкой.
- **Импорт `.conf`** — сторонний (в т.ч. от VPN-провайдера) или наш профиль создаёт туннель-клиент; экспорт сервера — пакет клиентских конфигов/QR.
- **AllowedIPs ≠ маршрут** — AllowedIPs — криптографический фильтр WireGuard; **маршрут туннеля** — запись в таблице маршрутизации. Панель выводит маршруты из AllowedIPs (например, `0.0.0.0/0` → default-маршрут с метрикой), но допускает переопределение.

## Прокси (Caddy)

- **Режимы сертификата сайта:** `Авто (HTTP-01)` — сайт привязан к конкретному WAN-адресу, Caddy держит 80/443 на нём; `Авто (DNS-01)` — через API DNS-провайдера, без открытых портов, wildcard (в MVP только при поддержке выбранным DDNS-провайдером); `Ручной` — загрузка сертификата и ключа; `TLS passthrough (SNI)` — без завершения TLS, судьба по лабораторной проверке L4-модуля.
- **Конфликт портов** — если port forward занял 80/443 на том же WAN-адресе — предупреждение в UI (или port forward на другой адрес).
- **Сертификаты и ключи** — секреты: не возвращаются API открытым текстом.
- **Применение** — генерация Caddyfile + `caddy validate` + graceful reload (без разрыва соединений).

## DDNS

- **Провайдеры MVP** — Cloudflare (API, поддерживает DNS-01) + универсальный RFC 2136 (обновление через собственный/сторонний DNS-сервер). Добавление провайдера = новый адаптер (плагинная архитектура).
- **История обновлений** — журнал обновлений и ошибок DDNS.

## Бэкап

- **Экспорт бэкапа** — зашифрованный архив; пароль задаёт администратор при выгрузке, секреты шифруются им же. Без пароля бэкап восстанавливается без секретов (конфигурация есть, токены/ключи вводятся заново).
- **Локальный автобэкап** — по расписанию внутри машины, с секретами; для восстановления после аварии.

## Безопасность панели

- **HTTPS всегда** — при первом старте генерируется корневой CA роутера + серверный сертификат панели, подписанный им; админ один раз принимает CA в браузере.
- **Учётные записи** — локальные, в БД панели; пароли — argon2id; первичная учётка создаётся в onboarding-мастере. Роль «оператор» — в модели данных, 2FA-поле (TOTP) у пользователя закладывается сразу.
- **Сессии** — httpOnly cookie, TTL ~8 ч, опция Remember-me, выход = инвалидация.
- **Защита от перебора** — rate limit на login, попытки в аудит-лог.
- **CSRF/origin-защита** — state-changing запросы только со своих origin.
- **2FA (TOTP)** — после MVP.

## Масштаб и ресурсы

- **Целевая нагрузка MVP:** до 20 интерфейсов / 10 зон; до 10 подсетей DHCP и 500 аренд; до 500 firewall-правил; до 100 алиасов (10 000 элементов); до 10 туннелей (до 50 пиров); до 20 сайтов Caddy.
- **Пропускная способность:** 1 Гбит/с NAT; userspace-туннели медленнее (сотни Мбит/с) — известное ограничение MVP, документируется.
- **Минимальные ресурсы:** 2 vCPU / 2 ГБ RAM / 16 ГБ диск (рекомендуемые 4/4).
- **Журналы** — ротация и лимит размера (SQLite не должен расти бесконтрольно).

## Политика обновлений

- **Обновление ядра Linux — только при острой необходимости** (уязвимости/эксплойты); функциональные обновления ядра не проводятся.
- **AmneziaWG как модуль ядра** — целевая форма после MVP (см. ADR-0001); userspace-порт — для MVP.
- **Обновления ОС и компонентов жёстко регулируются:** фиксированные версии пакетов, обновление только по безопасности/блокирующим дефектам, проверка после обновления ядра (AmneziaWG и сетевой стек) обязательна — см. лабораторную проверку этапа 0.

## Архитектура применения

- **Веб-процесс** — FastAPI-бэкенд панели; непривилегированный, не имеет capabilities, хранит желаемое состояние.
- **Агент** — отдельный системный демон с минимальными capabilities (NET_ADMIN и т.п.); единственный исполнитель системных действий.
- **Канал веб ↔ агент** — unix socket; агент проверяет peer-credentials (UID веб-процесса), TCP не слушает.
- **Набор операций агента** — явно заданный whitelist RPC-методов (применить, подтвердить, откатить, диагностика, статус сервисов); произвольный shell исключён.
- **Аудит системных действий** — агент логирует каждую RPC-команду; журнал агента — источник истины по системным действиям.
- **Состояние применения** — агент фиксирует фазы (applied / rollback_pending / failed) в маркере; веб читает его при старте, чтобы понять реальное состояние. Прерванное применение не подтверждается вслепую.

## Демо-данные и лабораторный режим

- **Демо-данные (demo data)** — фабрикованное содержимое UI (`demoConfiguration`, `demoEvents`, `demoLeases` из `frontend/src/fixtures.ts`), ранее подставлявшееся как fallback при отсутствии сохранённой версии конфигурации. Полностью удалены (ADR-0001); в рабочей ветке не поставляются.
- **LAB_MODE** — флаг `bootstrap.sh --lab`, ставивший небезопасный plain-HTTP TCP-bridge (`vs-router-web-tcp.service` на :8080) и отключавший Secure-куки через `VS_ROUTER_COOKIE_SECURE=0`. Полностью удалён (ADR-0001).
- **Неконфигурированное состояние** — у панели нет сохранённой версии конфигурации (`version` равен null). Показывается пустая конфигурация + предложение пройти первичную настройку; никогда — фабрикованные данные.
- **Первичная настройка / onboarding** — мастер первого запуска (маршрут `/onboarding`), создающий администратора и начальный черновик сети. Доступен через пункт «Первый запуск» в UI.
- **Рабочая ветка / main** — продакшн-ветка; не содержит фабрикованных демо-данных и артефактов LAB_MODE.
